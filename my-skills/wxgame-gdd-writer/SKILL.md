# wxgame GDD 编写法（工作室验证过的四件套流程）

本 skill 属 wxgame 家族（管线顺序、优先级与冲突裁决见 `my-skills/INDEX.md`）；实例见文末「实例参照」。

## 总流程（顺序执行，前一步是后一步的输入）

1. **一页纸概念**（`<game>/design/concept.md`）
2. **系统索引**（`<game>/design/gdd/systems-index.md`）——全项目唯一真源
3. **逐系统 GDD**（`<game>/design/gdd/<system>.md`）——每系统一份
4. **设计评审**（`<game>/design/design-review.md`）——十项自查

## 1. 一页纸概念模板（十节）

```
# 《游戏名》一页纸概念
## 1. 一句话定位
## 2. 为什么是它（Demo 验证价值——这款游戏能验证框架哪些能力）
## 3. 设计支柱（≤3 条，后续所有决策对照这里）
## 4. MDA 分析（Mechanics 机制→Dynamics 动态→Aesthetics 美学，逐层推导）
## 5. 目标玩家（Bartle 类型：成就/探索/社交/杀手，注明主次）
## 6. 心流与难度曲线思路
## 7. 范围分层：MVP（验收线）/ Should / Could / Won't（明确砍掉+理由）
## 8. 视觉锚点（一句话，交给美术方向）
## 9. 决策记录（已裁定的关键选择）
## 10. 下一步
```

## 2. 系统索引模板（核心是 §3 冻结令）

```
# 系统清单与依赖索引
## 1. 系统清单（编号 S1..Sn，一行一个）
## 2. 依赖排序（拓扑序，决定实现顺序与团队并行度）
## 3. 全局数值基线 · ❄️ 冻结令
   （画布/安全区、场地、网格、实体参数、通用规则、可访问性、
    包体预算、分值表——所有数值集中在这，分小节 3.1..3.n）
## 4. 事件总线约定（供程序落码参考）
## 5. 与框架层的接口假设
## 6. 变更记录
```

**冻结令铁律**：§3 的常量一旦冻结，其他任何文档、代码与它冲突时**一律以 §3 为准**；
改动必须走变更记录并通知所有下游（程序/QA/美术）。包体预算要区分
「平台红线」（如微信主包 ≤4MB）与「内部目标」（更紧），勿混用。

## 3. 逐系统 GDD 八节模板（每系统一份，一节不多一节不少）

```
# GDD · S<n> <系统名>
## 1. 目标（这个系统为什么存在，一句话）
## 2. 机制（状态机/规则，优先用状态机图或表）
## 3. 输入（来自玩家/其他系统的什么）
## 4. 输出与反馈（画面/音效/数值表现）
## 5. 数值（引用 systems-index §3 的冻结常量，只写引用不抄写）
## 6. 边界条件（极端值、并发、非法输入）
## 7. 依赖（上游/下游系统编号）
## 8. 验收标准（可测试的硬判据——QA 直接引用此节造用例）
```

## 4. 设计评审十查（design-review 模板）

1. MDA 自洽性（机制推出的动态是否真能产生目标美学）
2. 支柱漂移（是否偏离 concept 的设计支柱）
3. 难度曲线平滑性
4. 主导策略检查（是否存在一招通吃的最优解）
5. 经济平衡（分数/货币/奖励闭环）
6. 认知过载（同时呈现的信息量）
7. 范围膨胀（MVP 里混进了 Should/Could）
8. 跨文档一致性（与 systems-index、美术、UX 互相引用是否对得上）
9. 待处理风险与建议（含已定案的方案记录）
10. 结论 + 附评审 Checklist

## 工作方式

- 写前必读 `systems-index.md` §3（如已存在）；数值永远引用、不复制。
- 每份 GDD 落盘前先跑一遍十查中与之相关的项。
- 实例参照：`games/breakout/design/`（concept / systems-index / gdd/*.md / design-review）。
