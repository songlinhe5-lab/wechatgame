# wxgame GDD 定期 review（漂移审计，只读）

本 skill 属 wxgame 家族（管线顺序、优先级与冲突裁决见 `my-skills/INDEX.md`）。
跨域或全流程请求先交 `wxgame-orchestration`；本 skill 只出评审报告，**不改 GDD、不改代码**
（修复按 `wxgame-gdd-writer` 或对应域 skill 另开施工单）。

核心原则：**真源只有一个——`systems-index.md §3`**；review 的价值是证明"代码、分册、验收"
三方仍然指向它，而不是重新发明一套数值。

## 0. 什么时候跑（触发节奏）

- 每次冻结常量（§3）变更后
- 每个 Sprint / 里程碑收口前
- 发布门 G2 前（与 `wxgame-quality-gate` 并行，互不替代）
- 用户说「review 一下 GDD」「防止跑偏」「查数值漂移」

## 1. 输入（只读）

| 层 | 真源 |
|---|---|
| 数值 | `games/<game>/design/gdd/systems-index.md` §3（冻结令） |
| 系统设计 | `games/<game>/design/gdd/<system>.md`（§8 验收标准） |
| 概念与范围 | `games/<game>/design/concept.md` §7 MVP / Should / Could / Won't |
| 既有自查 | `games/<game>/design/design-review.md` |
| 实现 | `games/<game>/src/**`（`tuning*`、关卡 JSON、`view/palette.ts`、系统代码） |
| 兄弟分册 | UX / 美术 / 音频规格（全部服从 §3） |

冲突裁决按 `AGENTS.md` §4：文档冲突先改文档；代码与 §3 冲突以 §3 为准并**登记漂移**。

## 2. 审计步骤（顺序执行）

1. **冻结清单化**：从 §3 逐条抄成表（小节、名称、值、单位）。不合并同类项、不四舍五入、不补默认值。
2. **找代码落点**：为每条冻结值定位实现（`file:line`）。找不到 = 数值未落地。
3. **值比对**：读代码常量 / 关卡 JSON / 调色板，逐条比对 §3。不一致登记「代码 ≠ §3」。
   **但数值三方对账（§3 ⇔ 落码 ⇔ 下游文档现行等式）已由 `pnpm run check:frozen-values` 机械守（WXG-T-456，已挂 `verify`）**
   ⇒ 本步不再逐常量手抄：先跑门取结论，人只做两件事——① 读它的 `SKIP·` 清单（派生式 / 非原子值 = 门看不见的，⛔ 不等于已验）
   ② 逐条判「该改文档还是走 §3 变更单」（改哪个属设计裁定，门不判）。
4. **反向查魔法数字**：代码里参与玩法/结算/经济的数字若不在 §3，登记魔法数字（热路径数值优先）。
5. **系统覆盖三角**：§1 系统清单 ↔ `src/` 实现 ↔ 逐系统 GDD 分册，三方缺一即登记。
6. **事件总线**：§4 事件名 ↔ 代码 `emit` / `on` 名称；多余、缺失、改名均登记。
7. **验收可测性**：每个分册 §8 判据能否用当前实现与现有测试判定；不能判定 = 验收不可测。
8. **范围核对**：MVP 项是否都有实现；Should / Could 是否偷偷进了主链路（范围蔓延）。
9. **兄弟分册一致性**：UX / 美术 / 音频文档里的数值、状态数、尺寸与 §3 不一致 = 文档漂移。
10. **机械门禁（只记录，不修）**：`pnpm run check:arch`、`check:frozen-values`、`levels:check`、`palettes:check`、
    `check:a11y`，以及该游戏单测（如 `pnpm --filter @wxgame/beads test`）。记录退出码与关键输出。

## 3. 漂移表（报告主体）

| # | 类型 | 真源（§3 / 分册） | 代码或文档现状 | 证据 `file:line` | 级别 | 建议归属 |
|---|---|---|---|---|---|---|

- 类型 ∈ 数值漂移 / 魔法数字 / 系统缺失 / 事件不符 / 验收不可测 / 文档自相矛盾 / 范围蔓延
- 级别：P0 = 玩家可感知的规则或结算错误；P1 = 冻结值不符或核心系统缺失；P2 = 文档、命名、次要数值
- 级别不写「待定」：判不了就降级，并在证据列写清缺什么证据

## 4. 结论与报告落位

- 结论三选一：PASS（0 个 P0/P1）/ CONCERNS（有 P1 但有明确修复计划）/ FAIL（有 P0，或 P1 无计划）。
  阶段裁决权在 `wxgame-orchestration`，本 skill 只给建议结论。
- 报告默认写 `games/<game>/design/gdd/review-YYYY-MM-DD.md`；**写前先与用户确认路径**
  （`AGENTS.md` 先问再写），并沿用上次 review 的路径保持可比。
- 报告必含：基线 commit、输入清单、漂移表、跑过的命令与结果、0–3 条沉淀候选。
- 修复纪律：改 §3 须用户裁定并回填 §6 变更记录；改代码走对应施工单，不在 review 里顺手改。

## 5. 纪律

- 只读：不改 GDD、不改代码、不新增任何数值。
- 每条结论必须给 `file:line` 证据；没有证据的「感觉」不进表。
- 工具调用透明：报告附命令表（命令 / 退出码 / 关键输出），沿用 `wxgame-quality-gate` 的报告表格式。
- 收尾跑 `kb:sync --task=<任务号>`，把新增 / 修改 / 激活 / 归档统计摘进会话结论。
