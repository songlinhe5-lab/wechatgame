## 2. ⑧·补：E1 P10 为什么要双列，以及「零和纠正」那笔账

WXG-T-036 q1（2026-09-13）复核发现：P10 单列会**虚高**。同批两口径读数——

- **严格口径 P10 = 45.4%**（样本 186，达标 ✅）
- **宽松口径 P10 = 30.1%**（样本 197，未达标 ❌）

差别来自 **11 次「有 `limit` 但无 `offset`」的近似整读**：旧判定式 `fullFile = offset == null && limit == null`
把它们算成**局部读**，于是它们的高节省率混进了 P10。收紧为**三分法**后（`full` /
`implicitFull` = 无 `offset` 且行覆盖 ≥95% / `partial`），**整读占比同时由 56.7% 升到 59.1%**
（270/457，含 11 次实质整读）——即 **P10 变好与整读占比变差同时发生**。

两条结论（规则本体已回写 ROUTES ⑧）：① 报 E1 必须**两列并看**；② 口径修正带来的变化**不得**当成
行为改善宣传（零和纠正）。附带事实：那 11 次实质整读涉及的都是**小文件**（543–1299 估算 tokens），
整读小文件本身更省，把它们挪出只是口径修正而非退化。

## 3. ⑧·补：样本代表性边界（为什么不可外推）

同一批复验（WXG-T-026 F-01 / F-02）记下的样本构成：

- 457 读事件**只来自 2 个根会话**：Cursor 根 `6f7a9a03…`（163 读 / 35.7%）+ WorkBuddy 根
  `d2983589…`（294 读 / 64.3%），其余 18 条为**子代理**会话。
- WorkBuddy 根当时是**进行中的活动会话** ⇒ 边写边采、样本非平稳、**重跑即漂移**；因此 E2/E3 的
  抖动与大文件判定改用**比率口径**而非绝对次数。
- 单仓库 + 非独立重复采样 ⇒ 上述任何比率**不可外推**到「一般 agent 工作流」。

明细见 `ctx/reads-summary.md`（生成物，按最新账本重算）。

## 4. ⑨ / ⑪·补：两处被回收的开销与一个假绿例子

- **⑨ 成对使用模式的附带收益**：默认模式（HEAD 锚定）下 A/B 项显示的是**已提交值**，本地已超标时会
  **假绿**——当时的实录是：改完 `AGENTS.md` 后默认模式仍显示旧值，工作树实际已 **1743 tokens**
  （该文件硬上限 2000）。⇒ 看真实体积必须 `ctx:build --working-tree` + `ctx:check --working-tree` **成对**跑。
- **⑪·补 选池改写的收益**：旧版「未收录」逐条列出 **84 条**（≈1270 估算 tokens），其中 **77 条**与路由
  读取无关（既未被 ROUTES 引用、也未命中热度/体积门槛）⇒ 改为「只逐条列 ROUTES 引用的落选文件 +
  其余给一行计数」，回收约 1270 tokens 的常驻开销。
- **⑪·补² 的回落史证**：`LIMITS.hotFilesMaxTokens` 于 WXG-T-292 由 5600 抬到 5800（尖峰只剩 1 tok 的
  事故源），同批登记回落条件；WXG-T-293 用「锚点标题截断 + 台账型条数上限」还债后**回落 5600**，
  实测该表 5793 → 5470 tokens、收录文件块 20 → 29、锚点条目 351 → 318（三数并报，防止只看 tokens
  误判「没生效」——预算腾出来会被生成器自动回填成更多文件）。
