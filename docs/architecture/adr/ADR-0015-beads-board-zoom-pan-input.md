## 1. 上下文（Context）

### 1.1 直接动因（用户真机反馈）

用户在微信真机验证后提出缺功：**「缺个功能，可双指放大缩小、单指左右移动」**（WXG-T-166 立项单原文）。范围已由用户钉死：

- **只有棋盘玩法区**缩放/平移；**HUD / 托盘 / 道具卡 / 各类面板不缩放**；
- 主菜单与元游戏页族（含拟建的图鉴）**不缩放**（用户 2026-09-18 裁定）；
- 缩放**只做双指捏合手势，不提供滑轨 / 按钮控件**——这条不是本轮新诉求，而是既有裁定：`concept.md` **D13**、`input-control.md` v2.2 §2.1 多点触控条、`ux-spec.md` v1.6 §2 注②（WXG-T-141，用户对参考竞品「放大镜 + 竖滑轨」的裁定），均列 **Should（未冻结未实现）**。

### 1.2 驱动它的更大系统：盘面小**不是数值保守，是被「不缩放必须塞进屏幕」倒逼的上限**

用户另一条反馈是「每关盘面珠子太少、缺少连续珠子」。经核实，这条批评的根因**不在数值表**，证据链在 `systems-index.md §3.3` 的两行注释里就是自证的：

| §3.3 常量 | 冻结值 | §3 给出的理由（原文） |
|---|---|---|
| `GRID_MAX_COLS` | 13 | `13×52−2 = 674 ≤ 可用宽 690` |
| `GRID_MAX_ROWS` | 12 | `12×52−2 = 622 ≤ PUZZLE_BAND 高 640` |

⇒ 上限是**几何容纳**推出来的（格宽被 `BEAD_CELL=50` + `BEAD_GAP=2` 锁死，画布被 `§3.1` 的 750×1334 与 `PUZZLE_BAND` 高 640 锁死），**不是**「13×12 更好玩」。代码侧同一事实：`games/beads/src/config/tuning.ts::gridLayoutFor()` 按「带内居中」派生，`config/levels.ts` 用 `GRID_MIN/MAX_*` 做 BOOT 期硬校验，越界即报错。

**结论（本 ADR 的立项理由）**：缩放能力是**解除该上限的前置条件**。没有「放大后仍看得清、点得准」的机制，任何扩容都会在「珠子小于 `TOUCH_MIN`、缝隙不可辨」处撞回原墙。

### 1.3 图鉴诉求，以及本文**不**决策的部分（诚实划界）

用户另希望在主页面做**图鉴**：每张图 = 9 宫格或 16 宫格，每格是一个由拼豆不同颜色拼成的拼图版面。现状核实：

- 图鉴已在 `systems-index.md` **S10** 元游戏页族挂号（设置/签到/**图鉴**/排行榜/名片/体力，WXG-T-164 批 0）；
- 其 GDD 正本 `games/beads/design/gdd/meta-ui.md` **待建、文件尚不存在**（S10 行原文即标「待建，WXG-T-164 批 0」；T-164 待办明写「`gdd/meta-ui.md` 与 ui-kit 未随批 0 落盘，归批 1 同批补」）。

**必须写清**：图鉴的**玩法与内容设计**、以及扩容后盘面的**尺寸/难度/供给数值**（含 `§3.3` 上限本身的修订、`tuning.ts::stageParamsFor()` 用 `GRID_MAX_COLS × GRID_MAX_ROWS` 当冲刺格数上界这一连带面）**是另一条设计轨的产出，应走 design-strategist 出 concept + GDD（§3 冻结变更），本 ADR 只解决「使其成为可能的输入能力与坐标机制」**。本文不预告任何数值，也不以「工程已支持」冒充「设计已定」。

### 1.4 三条既有约束（已逐字读过，本文正面处理）

**约束 A —— ADR-0011 坐标空间契约链。** 现行链路是**唯一**换算点，且只有两段：

```
宿主原生事件 →(adapters 归一化：÷dpr + 翻 y，纯函数 touch-normalize)→ 屏幕 CSS px·左上
            →(Viewport.screenToDesign：含设计空间 y 翻转 + 信箱偏移)→ 设计 750×1334·左下 y-up
            →(玩法层热区比较)
```

玩法层**不存在屏幕坐标**（`control-manifest §6`），DPR 永不进 core（L2）。真机点击偏移（BD-48）的修复由两半组成：WXG-T-161 的归一化公式勘误 + **Cocos 工程适配策略 SHOW_ALL**（`games/beads/cocos/settings/v2/packages/project.json`：`fitWidth:true` + `fitHeight:true`）。后者**当初无 §3 / changelog 登记，被按「查无出处」回滚后真机复验反证偏移仍在**，重开后 P0-A 通过——教训即 **K-054：「未登记」≠「已证伪」**。⇒ 任何新增坐标层都挂在这条**刚在真机上走通一次**的链之后，扰动它属于高危面（WXG-T-166 立项单「高危面声明」原文即点名为「BD-48/T-129/T-161 同一 hit-test 通道」）。

**约束 B —— ADR-0014 已有半套变换通道，但语义与本次诉求三处全不匹配。** 现状：`RenderModel.transform?: RenderTransform = { scale, anchorX, anchorY }`，语义 `p' = a + (p−a)·s`，缺省恒等、旧模型逐字节不变；类型层注释明写 **Translation/rotation are deliberately not offered**，G5 红线在类型上落实（判例 `ComboPseudoShake` 无 dx/dy 字段）。三处不匹配：

| 通道既有语义 | 棋盘缩放平移的实际诉求 |
|---|---|
| **整帧**（全局，且背景参与变换） | **只棋盘区**，HUD/托盘/面板不缩放 |
| **无位移**（类型层红线） | **要位移**（平移 = 位移） |
| 锚点固定 = 屏幕中心（G5 语义） | 锚点 = **捏合中点**，逐帧可变 |

⇒ 不能「顺手复用」。ADR-0014 §5-① 早已预告复评触发条件为「出现 scale<1 或位移/旋转需求」——**本文就是那次复评**。

**约束 C —— `core/input/input-manager.ts` 是单指针设计，无多点是硬前置阻塞。** 实测三处：`_ownerId` 首指独占（L85）；`case 'down'` 注释 **`Ignore secondary touches`（L99）**，次级触摸被丢弃；`InputSnapshot` 只暴露**一组** `x/y/dx/dy/holdTime/isDown/justDown`。⇒ 双指捏合在玩法层**无法表达**（WXG-T-166 立项单：「解锁需二选一（均需 ADR），未裁」）。

约束 C 还牵出**一条常被忽略的事实**：多点化不只是工程改动，它会**推翻两条已冻结的 GDD 判据**——`input-control §8-9`「多点触控（双指同帧）：仅第一触点生效，指令数 =1」与 `§8-10`「一个固定步内注入 20 次触摸，仅 1 条进入路由」。按 `AGENTS.md §4` 冲突裁决（文档冲突先改文档再改代码）⇒ **GDD 改版是本能力的施工前置，不是收尾补写**。

好消息（同一文件实测）：单指拖拽在今日玩法层是**空闲通道**——`games/beads/src` 内 `snap.dx / snap.dy / snap.holdTime / snap.isDown` **零命中**（玩法只读 `justDown`）。

### 1.5 本文交付物与验收边界

本文只交付三样：**能力**（多点输入）、**机制**（棋盘区域变换 + 命中一致性）、**约束**（不变式、钳位口径、回归面）。观感、倍率曲线、边界回弹、图鉴内容一律不裁定。

## 2. 备选方案（Alternatives）

### 2.1 多点触摸输入通道

**甲（原始表述）：扩展 `core/input` 支持多指针槽**，缩放/平移在手势层解算。
- 事实：`InputManager` 的输入已经是**归一化后的设计/屏幕坐标 + 数字 id**（`PointerSample {id,x,y,phase,time}`），core 从不碰 `wx` / `cc` / DOM 事件对象 ⇒ 加槽**不触 L2**（L2 禁的是引擎/宿主符号，不是「多一个指针」这件事）。harness 已经**逐指**转发 `event.pointerId`（`dev/harness/main.ts::pushPointer`），Node 侧 `input.push({id:2,…})` 直接可测 ⇒ 符合本仓「无真机也能推进逻辑」立场。
- 成本：`InputSnapshot` 是**全框架共用契约**（beads + breakout + harness + 既有测试）⇒ 全矩阵回归。

**甲′（本文推荐，甲的内核收窄）：core 只给 2 个指针槽与逐槽原始状态，手势语义（两指距离比 / 中点 / 捏合判定）留在游戏侧。**
- 依据 = **ADR-0013 判例**：「框架只认结构不认玩法」——音色表归游戏侧、clip id 不得进框架。同理，`pinch` 是**本作的交互选择**（D13），不是通用能力；`pinchScale` 进 core 会让 breakout 契约里出现一个它永远不会读、且语义属设计的字段。
- 槽数上限取 **2**：捏合只需两指；任意 N 指要引入槽数组、生命周期与事件缓冲，收益为零、热路径分配风险为正。
- 向后兼容红线：`x/y/dx/dy/isDown/justDown/justUp/holdTime` **语义一字不改**（继续只指 owner 槽）⇒ 旧消费者与 `§8-9`/`§8-10` 在**棋盘区之外**仍逐条成立（新事实：`§8-9` 的「仅第一触点生效」在棋盘区**不再**成立，见 §4.2-2）。

**乙：Cocos 适配层（`bindings.ts` / weapp）加第二条触摸通道，玩法或壳层自行解算手势。**
- 事实：绕开 core ⇒ 触 L3 精神（`games/*/src` 禁 `import 'cc'`，且玩法要读第二条通道就得开一条游戏专用服务口子）；`bindings.ts` **不进框架 barrel、harness 不可直接编译**（`control-manifest` 另记 + L15 镜像纪律）⇒ **canvas2d/harness 侧必须另写一份解算**，Node 侧也只能再 stub 一份。
- 否因：三条宿主（Cocos web / 微信真机 / harness）各自实现同一手势 = **双宿主语义漂移**的教科书形态；而这正是 ADR-0011 §3(e) 与 §17 用一次 P0（缺陷 C1，发布前夕、玩法整体不可用）换来的教训：**归一化与坐标语义必须单点收口且可 Node 行为测试**。乙 把语义放到**测不到**的那一侧。

**丙：不引入多点，改「离散缩放档位（双击 / 按钮切档）+ 单指拖拽」（单指拖 = 既有 `dx/dy`）。**
- 事实：改动最小（约等一个视图派生 + 一个档位状态），零输入契约变更，零 §8-9/§8-10 冲突。
- 否因（如实说明它砍掉了什么）：**它砍掉的恰是用户点名要的那件事。** D13 / `input-control v2.2` / `ux-spec v1.6` 三处已冻结裁定「**只做双指捏合手势，无滑轨/按钮控件**」⇒ 丙 的按钮切档属被排除的控件形态；双击切档不在裁定字面内，但它是「离散档位」而非「捏合」，且不解决「捏合中点即锚点」这条核心手感（用户诉求原话是「放大缩小」的连续手势）。丙 唯一能留下的部分是「单指拖 = 平移」，而**只平移不缩放解除不了 §1.2 的容纳上限**。
- 结论：丙 **不作为候选方案保留**，但被登记为 **C-1 被否决时的唯一降级档**（平移先行、缩放搁置、盘面扩容继续阻塞）——写清代价：§1.2 的根因不解，图鉴/大盘面继续卡在设计轨门口。

### 2.2 棋盘区变换落在哪一层

**丁-1：扩 `RenderTransform` 允许 translate（把 dx/dy 加进全局通道）。**
- 否因（三条，任一即足够）：① 破 ADR-0014 类型层「无位移」红线，而这条红线保护的正是 G5 规格（`§3.8` 屏震冻结令 + `§3.10` 伪震屏语义钉死），红线一旦被「顺手复用」磨掉，下条动效单就无从援引；② 全局通道即使带位移也**仍是整帧**，解决不了「只缩放棋盘区」——主诉求没满足；③ 两 adapter 都得改（Cocos 侧 `setPosition(a'(1−s)) + translate`），`bindings.ts` 是被 §17/K-054 标过的真机高危半。

**丁-2：给 `RenderModel` 加**命令分组**局部变换 + 裁剪通道（`beginGroup({scale,offset,clip}) / endGroup()`）。**
- 事实：架构上最正确、可复用（未来图鉴页「一屏 N 个独立缩放版面」正是同一形态）；canvas2d 侧 `save → translate/scale → rect clip → 画 → restore` 直接可表达。
- 代价：① `RenderModel` 是**共用契约 + 快照差分测试面**（`control-manifest §8` 坐标系约定要改写：命令不再恒在统一设计空间）；② **Cocos 侧无对称能力**——现状是**单个 `Graphics` 节点承接全部矢量命令 + 一个 `Labels` 池**（`bindings.ts::_buildGraph`），要分组就必须拆 Graphics 节点（draw call 上升，与 `§8`「尽量合并 draw call」逆行）并配裁剪（`Graphics` 无内建 scissor，需 `Mask`），而这半**在编辑器外不可验证**；③ 分组是热路径状态栈，零分配纪律要重新论证。
- 判定：**成本与本次收益不匹配**，但它是 §5-③ 的复评对象（图鉴立项时重新评估）。

**丁-3（本文推荐）：布局即相机（layout-as-camera）——把缩放/平移烘进网格布局派生，渲染与命中读同一份派生值。**
- 事实基础 = 本仓已有判例 **WXG-T-062**：`input-control §2.2` 对 `btn_expand` 的明写「**渲染与命中同源 `tuning.ts::expandButtonLayout()`，不存在「画出的框 ≠ 点击落点」漂移**」。而棋盘**今天就是这个形态**：`tuning.ts::gridLayoutFor(cols, rows)` 产出 `{left, top, cols, rows, colCenterX(j), rowCenterY(i)}`，视图 `view-model.ts` 与命中 `beads-game.ts::_hitGridCell` 都从它取格心（实测 `BEAD_PITCH` 在 `games/beads/src` 共 14 个命中行：`config/tuning.ts` 7 / `view/view-model.ts` 7）。给 `gridLayoutFor` 多接三个相机标量（`zoom, offsetX, offsetY`），缩放/平移即同时进渲染与命中。
- 关键收益：**不需要独立的 hit-test 逆变换通道**——逆变换无处错，因为它压根不存在第二套几何真源（详见 §3.3）。这是 §1.4 约束 A（刚修稳的坐标链）风险最小化的解法。
- 代价：通用性差（只服务「网格 + 派生自同一布局的绘制」这一类，不服务任意图元分组）；带外内容需处理（见下）；视图侧棋盘相关绘制点要全部参数化。
- **带外溢出与裁剪（纸面几何核算，承重前提）**：`zoom > 1` 后网格必然超出 `PUZZLE_BAND`。丁-3 不解 scissor，而是**逐格剔除**（格心不在可视窗 ⇒ 该珠不发命令）——珠子是**离散格**，天然可剔，不需要真裁剪。溢出量：按「格心在带内」剔除时，边缘珠最多外溢 `BEAD_CELL/2 = 25`；而 §3.1 的带间空隙为 **下方 `PUZZLE_BAND` 下沿 480 − `TRAY_BAND` 上沿 450 = 30**、**上方 `HUD_BAND` 下沿 1214 − `PUZZLE_BAND` 上沿 1120 = 94** ⇒ 25 < 30 且 25 < 94，**不压 HUD、不压托盘面板**（这正是 v1.20 把托盘上沿 420→450 腾出的那 30）。命中侧残余：边缘珠外扩命中盒为 ±33（66²），可比可视窗多伸 3px 越进 `TRAY_BAND` 上沿——由 **`input-control §2.1` 既有带级次序（4 托盘 先于 5 网格）天然短路裁决**，不需新增例外条。⇒ **本条核算成立是 丁-3 免掉 clip 通道的唯一理由，必须写进代码注释防后人把剔除判据从「格心」改成「格缘」。**

### 2.3 双指落子歧义的出路（本文最贵的一处，必须先摊开）

现行路由在**按下帧即提交**：`beads-game.ts::_readInput()` 只读 `snap.justDown` → `screenToDesign` → `_handleTap` → 选珠/落子/组选。⇒ **捏合的第一指落下就会先执行一次棋盘动作**，第二指才到达。这不是可以「实现时注意一下」的细节，是语义冲突（`input-control §2.1` 表头自述即「单指点击，无拖拽/长按」）。四条出路：

| 出路 | 事实与代价 | 判定 |
|---|---|---|
| **(a) 棋盘区提交延后到抬起 + 位移阈值区分 tap/drag** | 语义最干净（编辑器类产品的通行解），与「单指拖 = 平移」天然自洽；但**推翻 down 即反馈的既有规格**：`input-control §8` 判据 2/4/5/11/12、`core-loop §8-3` 时基口径、以及 **K-052 类**「时长常量决定事件发生在哪一帧」的时序判据（`bead:placed` 发射帧后移 ⇒ 落座回弹/扫光/过关判定帧全移）都要重跑。需 GDD 改版，归设计轨。 | **本文推荐**，但不替用户锁死（→ C-3） |
| **(b) 捏合即撤销上一颗落子** | 需要回滚能力。实测 `games/beads/src` grep `undo|撤销` **零命中** ⇒ 现无 undo；且落子可能已触发 `LEVEL_CLEAR`（不可逆穿越：结算已发、星级已记、关卡指针已进）⇒ 撤销要连带拆事件，工程上不安全。 | 否 |
| **(c) 接受「第一指先落一颗珠」** | 零改动。但错色落子走 `rejected` + 断连/耗时的实打实惩罚，每次捏合开局都误触一次。 | 否（列出仅为完整性） |
| **(d) 双指只能从带外空隙起手** | 与「在珠面上捏合」的直觉相悖，可用差；可作为 C-1 落地后临时降级档。 | 否（备档） |

## 3. 决定（Decision）

### 3.1 推荐组合（一句话）

**甲′（core 只加 2 个指针槽，手势解算留游戏侧）+ 丁-3（棋盘缩放/平移烘进 `gridLayoutFor` 派生，渲染与命中同源，不动 ADR-0014 全局通道）+ (a)（棋盘区提交延后到抬起）**；其中 **(a) 与 §3.5 C-1/C-2 须先由主理人与设计轨裁定，未裁不施工**。

### 3.2 多点输入（甲′）

1. `packages/framework/src/core/input/input-manager.ts`：内部指针槽从 1 扩到 **2**（slot0 = owner，slot1 = 次指），全部为**标量字段**（`_x1/_y1/_prevX1/_prevY1/_id1/_down1`…），`snapshot` 追加**扁平字段**而非数组对象（热路径零分配，`control-manifest §2`；判例 = ADR-0014 把 `setTransform` 的对象入参收窄成标量）。既有 8 个字段语义**不动**。
2. `justDown` **只在 owner 抢占时置位**（次指下按不产 `justDown`）⇒ 现有单指路由与 breakout 零改动。
3. **owner 迁移（工程自裁，登记 §5-⑤ 复评）**：owner 抬起后**不**把次指提为 owner，直到全部指针抬起才复位。理由：捏合中途抬走一指，若另一指接管成 owner，会把「捏合收尾」误读成「单指拖拽」⇒ 甩图。
4. `reset()` 同步清两槽（后台隐藏/切场景路径）。
5. **手势解算不进 core**：新增 `games/beads/src/systems/board-camera.ts`（纯函数 + 一个状态对象），读 snapshot 的两槽坐标，产出 `zoom/offsetX/offsetY` 增量。归属理由 = ADR-0013（框架不认玩法）。
6. L2/L3 合规自查：core 只加纯数据与标量比较；`wx`/`cc` 事件对象**不出现**；`bindings.ts` **零改动**（Cocos 的 `touch-start/move/end/cancel` 本就逐指回调，`readTouch()` 已带 `getID()`）——⚠ 但该「逐指」前提**未在编辑器/真机取证**（§4.3-③），施工首步须先实测并回写 §17。

### 3.3 区域变换与 hit-test（丁-3）

1. 相机状态 `BoardCamera = { zoom, offsetX, offsetY }`（三个标量），**权威存于玩法层**（`BeadsGame`）—— L5 合规：视图与命中都是**只读消费方**，这恰好是 L5 想要的形态（若把相机放视图侧，就会造出「画出的框 ≠ 点击落点」的第二真源）。
2. `tuning.ts::gridLayoutFor(cols, rows)` 扩为接收相机（或以可选入参保持恒等默认），派生：`pitch' = BEAD_PITCH · zoom`、`cell' = BEAD_CELL · zoom`、`left/top` 按带内可视窗 + `offset` 定位。**恒等档（zoom=1, offset=0）产出的数值必须与今天逐位相同**（旧关卡、旧断言、快照差分不得漂移）。
3. **hit-test 不新增逆变换通道**（这是 丁-3 的全部要点）：链路仍是 ADR-0011 的那一段——`Viewport.screenToDesign`（屏幕→设计，唯一）→ `_hitGridCell` 拿**已含相机的**格心做距离比较。缩放后不再有「第二套坐标系」可以错。
4. **命中半径必须随 zoom 缩放**（`GRID_HIT_SIZE · zoom`）。这不是打磨项，是保持既有判据为真的前提：`input-control §8-2` 的注（BD-23/WXG-T-091）明写「因 `BEAD_PITCH`(52) **<** 命中区(66)，网格内部外扩区必然重叠，一律按判据 4 最近格心裁决」；若半径不随缩放，`zoom = 1.5` 时 pitch′ = 78 > 66 ⇒ 网格内部**出现无命中缝隙**，§8-2「网格内部不存在带间隙处」的前提被破坏，§8-4 的「相邻两格中点 ±1px」构造也不再可比。半径同倍缩放后不等式 `52z < 66z` 恒成立 ⇒ 两条判据的**结构**在任意档位都保持（其**字面值** 66 需 §3.8 注记，见 §4.2-3）。
5. **视图侧参数化面**（施工最大一块，实测清单）：`view-model.ts` 的 7 个 `BEAD_PITCH` 命中行所在绘制点（`drawGrid` / `drawPuzzlePlate` 的 bandOut clamp 派生 / `drawSweep` / `drawComboVfx` 的格心换算）+ `bead-render.ts` 的珠体尺寸与 `BEAD_DRAW_INSET`（=6，真机裁定乙档）+ 快照 `gridLeft/gridTop` 下发。**⚠ 一处未裁的规格问题**：`BEAD_DRAW_INSET`、珠/垫圆角、描边宽是**绝对值**（assets-spec v1.5-r7 口径），缩放后「随缩」还是「不随缩」是**美术规格**问题——不随缩 = 放大后缝隙比例失真；随缩 = 与绝对值口径冲突。⇒ 交 art 轨裁定，本文不代答（→ C-5）。
6. 逐格剔除判据：**格心 ∈ 可视窗**。溢出核算与「不得改成格缘判据」的理由按 §2.2 丁-3 写进代码注释。
7. **不复用 `RenderModel.transform`**，`ADR-0014` 的类型、两 adapter、G5 语义**零改动**（本 ADR 不破例、不扩字段、不加 dx/dy）。

### 3.4 工程不变式与护栏（数值留空，由设计轨冻结）

- 相机只在 `shell.screen === 'play'` 且玩法相位 `playing` 时生效；`PAUSED / LEVEL_CLEAR / GAME_OVER / FINISH / BOOT` **一律旁路**（保持 §2.3 门禁与判据 8b/8c/8d 的「面板外零响应」不被扰动）；meta 页族（菜单/设置/签到/图鉴）不进相机（用户已裁）。
- 缩放/平移期间**不得改变带级次序**：齿轮 → 道具卡 → 扩展钮 → 托盘 → 网格（`§2.1` 既有短路序）。相机只作用在 5 的**几何**上，不引入新的优先级。
- 复位口径与复位点（**WXG-T-172 甲裁：以实现为准回写**；原列 5 点 ⇒ 实际 **2 点**）：
  - **复位档 = 相机归 `fit` 初始**，不是「归恒等 zoom=1」。`fit = min(1, 含边距适配)`，公式正本 = `systems/board-camera.ts::computeFitZoom`，落点 = `fitCamera`。小盘 `fit = 1` ⇒ 与旧「恒等档」**逐位相同**（§3.3-2 的恒等回归锚与旧关卡断言因此不漂移）；大盘 `fit < 1` ⇒ 开局即「居中不贴边」（= T-169 真机反馈③，正是它把初始视图改成适配档的）。边距与缩放上限的**具体数值 `[待确认]`**（`tuning.ts` 工程占位，冻结须走 §3 变更单，本文不携带）。
  - **实际复位触发点 = 2 处**（`game/beads-game.ts`，各调一次 `fitCamera`）：**`_setupLevel`**（换关 / 新局 / 重试 / 跳关共用）与 **`_loadStage`**（冲刺换 stage）。不变式是「**装配即复位**」——棋盘尺寸一变，相机必按新尺寸重算 `fit`，禁止跨关残留缩放（否则新一关的「带内居中」语义失真）。
  - **回菜单当帧不复位**：暂停面板次钮只上报意图 + 切屏归 shell（本局棋盘不保留），该路径**不触碰**相机；**后台隐藏（`onPause`）同样不复位**。两者均由**下一局装配时**经上面两点复位兜住——读 §3.4 时不得据此写出「回菜单后当帧复位」这类断言。
  - ~~`InputManager.reset()`（后台隐藏）~~ **不是**复位点（原文误列）：框架层不持有也不感知相机（`InputSnapshot` 无相机通道），相机权威按 §3.3-1 存于玩法层（L5），把它列进复位点在机制上无处落地。
  - **`resetCamera()` 保留**（`board-camera.ts:96`）：用途 = 测试 / 中立基线的恒等档工具，**不因本次回写作废**；但它**不在**游戏内复位路径上（游戏内复位走 `fitCamera`）。
- 钳位（**只给口径，不给数**）：`zoom` 下限受 `TOUCH_MIN=88` 与珠体可辨识度约束（z<1 会击穿无障碍口径，故 z<1 是否允许须设计轨先答）；`zoom` 上限与 `offset` 钳位受「可视窗 ⊂ `PUZZLE_BAND` ± 半格余量」（§2.2 核算）与「至少保留一颗完整珠在窗内可点」约束。数值 `[待 GDD]`。
- 热路径：相机三标量进快照（复用既有 `_snapshot` 对象扩字段，不 new）；`buildRenderModel` 只读；无 `Math.random`（L4 无关）。
- 镜像纪律：改 `core/input` + `tuning` ⇒ `framework:sync` 同批 + `framework:sync:check` 硬门（BD-20 判例）+ 两包 `cocos:check`。

### 3.5 待主理人 / 用户裁定的开放分叉（本文不锁死）

- **C-1｜多点通道**：甲′（推荐）／乙（适配层，否因 §2.1）／丙（无缩放降级档，否因 §2.1）。**否 甲′ ⇒ 缩放与盘面扩容整体搁置**，只可能先做「单指平移」。
- **C-2｜变换落位**：丁-3（推荐，§2.2 有免 clip 的几何核算）／丁-2（为图鉴预付通用性，代价 = 两 adapter + draw call + 契约改写）／丁-1（**不推荐**，破 ADR-0014 红线且不解决主诉求）。
- **C-3｜双指落子歧义**：(a) 抬起提交 + 位移阈值（推荐，但**须设计轨先改 `input-control`/`core-loop` 判据**）／(b)(c)(d) 否因见 §2.3。**这条不定，棋盘区捏合就不能开工**——它是手感与既有验收的正面冲突，不是工程可以单方决定的。
- **C-4｜§3 上限解除是否随本单**：本 ADR 只交能力；`GRID_MAX_*` 扩容与难度旋钮、图鉴宫格规格 → **design-strategist 出 concept + GDD（§3 变更单）**，另批施工。
- **C-5｜缩放后的描边/缝隙是否随 zoom（art 轨）**：`BEAD_DRAW_INSET`、圆角、1px 描边口径 → 归美术规格（assets-spec 侧），本文不代答；未答前施工按「不随缩」占位并**显式标注观感 `[R]/[P]` 未验**。

### 3.6 最小验证（本文只列判据，不落码；未做的一律标未执行）

## 4. 后果（Consequences）

### 4.1 正面

1. **多点能力一次进 core 且向后兼容**：槽位 + 扁平字段、旧 8 字段语义不动 ⇒ breakout 与既有路由零改动；harness 已逐指转发 `pointerId`，Node 可合成 ⇒ 「无真机也能推进」这条本仓立场对多点手势第一次成立。
2. **手势语义留在游戏侧**（ADR-0013 判例延续），框架不长玩法。
3. **G5 红线保住**：`RenderTransform` 的「无位移/旋转」不破例，`bindings.ts` 与两 adapter 零改动 ⇒ 坐标/变换高危面（§17 + K-054）扰动最小。
4. **命中与渲染同源 ⇒ 从机制上消除「缩放后点击偏移」这一类缺陷**（WXG-T-062 判例的推广）：不是补一条逆变换再测它，而是让逆变换无处存在。
5. **解除 13×12 容纳上限的工程前置到位**（注意措辞：前置到位 ≠ 已解除，数值仍冻结，见 C-4）。
6. 单指拖通道今日空闲（§1.4 实测零命中）⇒ 平移不抢占任何既有交互。
7. 恒等档逐字节不变 + 反例自检 ⇒ 本次改动自带判别力，不攒「正则式假绿」欠账。

### 4.2 负面（已知成本，白纸黑字，不是风险）

1. **双指落子歧义（C-3）无论如何都要付费**。若最终采 (a)，`bead:placed` 发射帧后移，牵动 `input-control §8` 多条、`core-loop §8-3` 时基与 K-052 类「时长决定事件帧」的时序判据 ⇒ **跨文档 + 跨测试迁移，不是一个 if**。这是本 ADR 最大的已知成本。
2. **推翻两条冻结判据**（`§8-9`「双指同帧仅第一触点生效，指令数=1」、`§8-10`「一帧 20 次触摸仅 1 条进路由」）：棋盘区不再成立、区外仍成立 ⇒ 一条契约被切成两段。GDD 未改版前，QA 五件套（其判据一律由 GDD §8 导出）与本实现**直接对撞**——按 `AGENTS §4`「先改文档再改代码」，这是施工阻塞项而非收尾项。
3. **引发 §3 冻结面漂移**：`§3.8` 冻结的是「名义尺寸外扩 8px ⇒ 网格 66² / 托盘 62²」，而 §3.3-4 要求命中盒随 zoom 同倍缩放 ⇒ 缩放态下命中区 ≠ 66。必须补 §3.8 注记或 GDD 澄清，否则评审按字面 66 硬判据打回。同类连带：`TOUCH_MIN=88` 在 `z<1` 档会破无障碍底线 ⇒ 工程钳位或明写「不允许 z<1」。
4. **带外剔除的观感是纸面结论**：几何核算（25 < 30/94）只保证「不压 HUD/托盘」，不保证「半颗珠在窗边被消失」可接受，也不保证 `drawPuzzlePlate` 的 bandOut 暖光环与剔除窗边缘的接缝观感。**归 art/playtest，本文标 `[R]/[P]` 未执行**。
5. **改动面比「加个缩放」字音大**：视图侧棋盘相关绘制点要全部参数化（实测 `BEAD_PITCH` 14 命中行 + `bead-render` 尺寸入参 + 快照下发 + 扫光/彩带/伪震屏与相机三者叠加的观感复验）；估源码 +200~350 行、测试另计。诚实：这是**立项时点推论**，落码后必须差分复算，不得沿用（K-051 判例）。
6. **包体/图元口径须重算**：估算运行时体积 <2KB（gzip 前，纯逻辑，零新资产）——但主包红线口径不得凭估：`verify` 现状已含 `check:size` 存量 FAIL（debug 产物超 4MB，归发布域挂账），本单新增量**混在存量漂移里无法归因**，须落码后单独出数。图元基线同样会变：剔除会减少当帧格数、而盘面扩容会增加格数 ⇒ `assets-spec` 基线（含 ④=1828 那条）在 C-4 批准后**全部重算**。
7. **多点输入是共用契约扩张**：`InputSnapshot` 被 beads + breakout + harness + 快照测试共同消费 ⇒ 回归面 = 全矩阵（framework/beads/breakout/harness + `check:arch` + `framework:sync:check` + 两包 `cocos:check`），跑绿前不算完（ADR-0014 §4.2-2 同口径）。
8. **面板手势歧义的残余未被本文消掉**：单指拖 = 平移，但拖的起点可以落在托盘/道具卡/齿轮热区内（这些区的点击语义不变）⇒ 位移阈值以下的抬起仍要按既有路由提交，阈值是**未冻结的 UX 参数**（→ 归 ux-spec/design 轨）。本文只承诺「次序不变」，不承诺「无歧义」。
9. **真机回归风险（K-054 直接适用）**：这条链（T-161 归一式 + SHOW_ALL `policy:2`）**目前只在真机走通过一次**，且 SHOW_ALL 那半边至今**无 §3/changelog 登记**（属引擎工程配置，登记面本就缺这一栏——K-054 规避④）。丁-3 刻意不加新坐标层，但 `design→格心` 的算式确是新的 ⇒ 真机首验 P0 必含「zoom≠1 的棋盘点击命中」；真机一旦偏，**先取证（debug overlay 三段读数）再判定**，不得凭纸面缺账回滚实证成立的改动（那会制造第二个 bug）。
10. **owner 迁移语义是我方自裁**（§3.2-3）：若真机反馈「抬走一指后想继续单指拖」被判为缺陷，`_ownerId` 策略须改 ⇒ 登记 §5-⑤，且届时 §8-9/§8-10 的迁移方案要重开。

### 4.3 中性 / 待观察

1. 图鉴若真做成「一屏 9/16 个独立缩放版面」，丁-3 的「一份相机配一张网格」可能不够 ⇒ 丁-2（分组变换通道）届时复评。**当前事实：`gdd/meta-ui.md` 不存在**，无法据以裁定通用性投资。
2. `[C]` **Cocos 多点派发形态未取证**（无编辑器）。若引擎在一次 `touch-start` 事件里给多触点，`bindings.ts::readTouch()` 需遍历 `getTouches()` ⇒ 触 §17 高危半，须按「纯函数 + Node 行为测试」补形态。施工首步 = 实测此项，未实测前 甲′ 视为**未证可行**（诚实：这是本文唯一可能翻车的工程前提）。
3. `PointerSample.id` 口径不统一：文件头注释写「mouse is 0, touches >= 1」，harness 实际转发 `event.pointerId`（浏览器鼠标常为 1）。⇒ 槽位分配按「**先下先占**」实现，**不得假设 id 有序**；注释顺手改正（属文档债清偿，非功能变更）。
4. 本文与 ADR-0014 的关系是**分层共存**而非取代：全局通道 = 整屏动效（G5/G8/G9 类），区域相机 = 棋盘语义。这条分界是否长期清晰，看下一条动效单会不会试图「顺手」用它。
5. `safeArea` 仍未纳入坐标契约（ADR-0011 §4.3）；高屏适配规则（`§3.1` 锚点吸收）与相机可视窗的耦合（拼图带贴 HUD 时窗高变化）在真机高屏档下未推演。

## 5. 复评触发条件（Review Triggers）

1. **C-3 被裁定为 (a)** ⇒ `input-control` / `core-loop` 时序判据重跑，本文 §3.3-4（命中半径随缩放）与 §2.3 需一并复评（抬起提交会改变 tap 与 drag 的耦合口径）。
2. **出现整屏级 scale<1 / 位移 / 旋转需求** ⇒ 走 **ADR-0014 §5-①**（不是把位移塞进本 ADR 的区域相机；两者语义分层不得互串）。
3. **图鉴 / 多宫格立项（`meta-ui.md` 落盘）** ⇒ 复评 **丁-2**（分组局部变换 + 裁剪通道）与本文 丁-3 的分工；若一屏需 N 个独立变换版面，丁-3 的「单相机」前提失效。
4. **真机可得（AppID + `build:cocos:wx`，ADR-0009 P2 解除）** ⇒ 必须复核 §4.3-2 的 Cocos 多点派发形态、zoom≠1 的命中偏移、dpr=3 档、带外剔除观感；这四项是本文 `[R]/[C]` 的唯一解除路径。
5. **`GRID_MAX_COLS/ROWS` 被设计轨解除** ⇒ 连带复评 `config/levels.ts` 校验边界、`tuning.ts::stageParamsFor()` 的冲刺格数上界、`assets-spec` 图元基线与包体（§4.2-6）。
6. **出现第三个宿主 / 第二个引擎适配器** ⇒ 多点归一化须按 §17 同形态复刻（纯函数 + Node 行为测试 + 端到端「两档 dpr 同一可见点落点一致」判据）。
7. **`_ownerId` 迁移策略被判为手感缺陷** ⇒ 重开 §3.2-3 与 `§8-9/§8-10` 迁移方案。
8. **art 轨对 C-5 给出裁定**（描边/缝隙随缩或不随缩）⇒ 回写 §3.3-5，并按结论复算图元与 LOD 相关绘制点。
