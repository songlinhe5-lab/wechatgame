# ADR-0001 — 引擎选型：Cocos Creator 3.8 LTS

- **状态**：已接受（Accepted）
- **日期**：2026-09-11
- **决策人**：主理人游承峰 / 技术负责人程基岩
- **影响范围**：整个微信小游戏矩阵（框架层、每款游戏的渲染与输入适配层、构建流水线）

---

## 1. 上下文（Context）

我们要交付的不是**一款**游戏，而是一个**矩阵**：一套共用框架 + 若干款独立小游戏，全部发布为微信小游戏。

在选引擎之前，先把约束钉死——这些约束比"哪个引擎更好用"更能决定答案：

| 约束 | 具体数字 / 事实 | 来源 |
| --- | --- | --- |
| 主包体积 | **≤ 4 MB** | 微信小游戏官方口径 |
| 主包 + 分包合计 | **≤ 30 MB** | 微信小游戏官方口径 |
| 运行环境 | 微信小游戏 JS 运行时（无 DOM、Canvas/WebGL 可用、`wx.*` API） | 平台硬约束 |
| 目标机型 | 低端 Android 为主（微信小游戏真实分布） | 平台分布 |
| 团队规模 | 小工作室，多人/多 AI 会话**并行**开发同一仓库 | 本项目工作方式 |
| 交付形态 | 一套框架 + N 款游戏，长期迭代 | 用户（Stephen He）目标 |
| 我们的知识储备 | 参考文档以 Cocos / Unity / Unreal 为主 | 工作室能力 |

由此提炼出三条**真正的选型标准**，按权重排序：

1. **微信小游戏官方导出链路成熟度**——包体、API 兼容性、真机表现。
2. **2D 游戏的生产效率**（弹球打砖块这类 2D 玩法占矩阵绝大多数）。
3. **多人/多 AI 并行协作下的仓库可维护性**（这一条经常被忽略，但它是本项目最大的隐性成本）。

---

## 2. 备选方案（Alternatives）

### 方案 A：Cocos Creator 3.8 LTS（3.8.8，2025-12 发布）

- 微信小游戏官方支持的最好的一档：一键导出、`wx` API 桥接、子包/远程包配置齐全。
- 2D 能力成熟（`Graphics` / `Label` / `UITransform` / 物理 2D）。
- 编辑器 + 运行时同源，TypeScript 直接写。
- **代价**：`.scene` / `.prefab` 是**索引化的二进制/JSON 结构**，脚本化编辑极易冲突；构建需要编辑器（CLI 也依赖已安装的编辑器）；一个工程天然对应一款游戏。

### 方案 B：Cocos Creator 4（2025-11 开源）

- 更新、架构更现代，长期看是方向。
- **否决理由**：开源时间距本决策不足 1 个月。微信小游戏导出插件、真机表现、第三方生态均**未经验证**。把矩阵的地基压在一个刚开源的版本上，风险与收益严重不成比例。这不是"技术保守"，而是"不拿交付日期做赌注"。
- **保留态度**：写进观察清单，等 4.x 的微信导出链路被大量项目验证后再评估迁移（迁移成本被 ADR-0002 的分层设计大幅降低）。

### 方案 C：Unity（WebGL 导出 → 微信小游戏转换）

- 编辑器体验、DOTS、生态最好；团队对 Unity 最熟。
- **否决理由（硬伤）**：Unity WebGL 产物**空工程**就远超 4 MB 主包上限。即使走微信的转换工具 + 分包 + 资源外置，启动时间与内存占用在低端 Android 上不可接受。这不是优化问题，是量级问题。
- 顺带一提：Unity 的 `.unity` 场景文件同样是 GUID + 索引引用，合并冲突比 Cocos 更糟。

### 方案 D：Unreal Engine 5

- **否决理由**：包体、内存、启动时间与"微信小游戏"这一形态根本不相容。UE 的 Nanite/Lumen 在这个平台上没有任何发挥空间。列在此处仅为记录"我们评估过"。

### 方案 E：PixiJS + 自研编辑器壳

- **它是本次最有力的挑战者**，值得认真对待：
  - 纯代码、无场景文件 → **彻底消除 `.scene` 合并冲突**，完美契合我们的并行开发方式。
  - 包体可控（tree-shaking 后核心 ~150 KB）。
  - 社区有 `pixi-miniprogram` 之类的微信适配层。
- **否决理由**：
  1. 微信适配层是社区维护，**版本跟进与官方支持度都不如 Cocos**。一旦微信基础库更新导致兼容问题，我们是在替一个第三方库打工。
  2. 没有编辑器意味着**策划/美术无法自查产物**——所有可视调整都要经过程序员。对"矩阵"这种需要快速试错的形态，这是持续的人力税。
  3. 音频、加载器、资源分包、真机调试链路都要自己拼装，隐性工作量被低估。
- **但它的思想被我们采纳了**：见 ADR-0003（空场景 + 全代码构建）。我们用 Cocos 的运行时，却尽量只吃它"代码优先"的那一半能力。

### 方案 F：LayaAir / Egret

- LayaAir 的微信小游戏支持其实很好，2D 也够用。
- **否决理由**：生态规模、文档质量、招人难度均弱于 Cocos；且我们的参考知识库以 Cocos/Unity/Unreal 为主，选择 LayaAir 等于放弃已有的知识杠杆。

---

## 3. 决定（Decision）

**采用 Cocos Creator 3.8 LTS（当前 3.8.8）作为整个小游戏矩阵的引擎。**

并且，为了**对冲** Cocos 在并行协作上的核心缺陷，同时钉定三条配套决策（分别落在 ADR-0002 / ADR-0003 / control-manifest）：

1. **框架与引擎解耦**：游戏逻辑不依赖 `cc`，绝大部分代码可在 Node 下用 vitest 验证（ADR-0002）。
2. **空场景 + 全代码构建**：`.scene` 里只挂一个 Bootstrap 脚本，其余节点全部代码创建（ADR-0003）。
3. **禁止手工编辑 `.scene` / `.prefab`**：写进控制清单，作为可执行的评审规则。

也就是说：**我们选 Cocos 是为了它的微信导出链路，而不是为了它的编辑器**。凡是能用代码表达的东西，就不放进场景文件。

---

## 4. 后果（Consequences）

### 4.1 正面

- 微信小游戏导出是官方一等公民：分包、远程资源、`wx` API 桥接、真机预览都有成熟路径，**不需要我们自研平台层**。
- 2D 渲染与 UI 能力开箱可用，矩阵里的小游戏可以在几天内做出可玩版本。
- TypeScript 全链路，与框架层的类型系统天然贯通。
- 编辑器对美术/策划友好，弥补了方案 E 的短板。

### 4.2 负面（必须诚实记录，这些是**已知成本**，不是风险）

- **`.scene` 合并冲突极其糟糕。**
  Cocos 的 `.scene` 是 JSON，但节点 `id` 是**相对顺序索引**。在场景任意位置插入一个节点，会导致文件中数百处引用被重新编号——一次 diff 变成几百行，多人并行时几乎必然冲突且难以人工判读。
  *对策*：ADR-0003，场景里不放节点。
- **编辑器的强依赖。**
  生成/更新 `.scene`、`.prefab`、`.meta`、导入资源、构建，都必须有编辑器。这让**纯 CLI 的 CI 无法从零产出可运行产物**——CI 只能跑类型检查、单测、静态校验，构建必须依赖一台装有 Cocos Creator 的机器（或预生成好 `.meta`）。
  *对策*：把可自动化的一切（typecheck / test / bundle 体积校验）放进 `tools/scripts`，把"必须点编辑器"的步骤显式列进 `docs/engine-reference/cocos/VERSION.md` 与 `games/breakout/cocos/README.md`。
- **"一个 Cocos 工程 = 一款游戏"与 monorepo 天然不友好。**
  Cocos 假设工程根就是项目根；我们却希望 `packages/framework` 被 N 个游戏共享。
  *对策*：框架包不通过 Cocos 的依赖系统引入，而是通过**源码/构建产物拷贝**进入工程（详见 ADR-0002 与 `games/breakout/cocos/README.md` 中标注为"待编辑器验证"的部分）。
- **`.meta` 文件必须与资源同生共死。**
  手工挪动资源目录会导致引用失效（红色感叹号）。资源目录调整只能通过编辑器。
- **版本锁定成本。**
  3.8.8 之后升级 3.8.x 通常平滑，但跨到 4.x 可能需要重写渲染适配层——这正是 ADR-0002 分层要隔离的东西。

### 4.3 中性 / 待观察

- Cocos 4 的微信导出成熟度（观察项，触发条件：官方发布微信小游戏导出文档 + 至少 2 个公开项目验证）。
- `cc` 类型定义只在编辑器内提供，Node 侧无法获得真实类型（我们用 `types/cc.d.ts` 占位，见 ADR-0002 的缺口清单）。

---

## 5. 复评触发条件（Review Triggers）

出现以下任一情况，应重开本 ADR：

1. Cocos 4 的微信小游戏导出被官方文档明确支持，且有 2 个以上公开项目验证真机表现。
2. 微信小游戏主包上限放宽（会改变方案 C/D 的结论）。
3. 项目从"矩阵"收缩为"单款游戏"（会削弱方案 B/E 的劣势）。
4. 出现 3.8 LTS 无法承受的性能/包体问题，且无法通过分包与优化解决。
