# ADR-0004 — beads 关卡数据形态：BEAD_CHARSET 行字符串数组

## 1. 上下文（Context）

beads 关卡 = 图案矩阵（≤13×12 格）+ 元数据（LEVEL_TIME、SPAWN_INTERVAL、杂色数、供料池）。systems-index §3.2 已冻结 `BEAD_CHARSET = .x1-9A`（`.`=空位、`x`=锁定、`1-9`+`A`=色板索引 1–10），并指明校验函数形态"沿用 breakout `validateLevel()` 判例"。BOOT 期需静态校验拒绝非法关卡（core-loop §2.1"不允许带病进入 PLAYING"）。需决定关卡 JSON 的承载形态。

## 2. 备选方案（Alternatives）

**方案 A：行字符串数组（BEAD_CHARSET）**
```json
{ "id": 3, "cols": 10, "rows": 8, "time": 300, "spawnInterval": 4.0,
  "decoys": ["6"], "pattern": ["..11..", ".x112.", "..."] }
```
- 事实对比：单关体积约 300–600 字节；人眼可直接对照参考图审阅；diff/评审友好；校验 = 字符集 + 行宽断言，breakout 已有同判例实现（`core/config/level.ts`）可直接复用；解析在 BOOT 一次完成，运行期持有解析后的矩阵。
- 局限：字符集上限 16 种语义（当前 12 个字符，色板索引最大 10，`BEAD_COLOR_MAX=8` 有余量）；第 10 色 `A` 可读性稍弱，需查表。

**方案 B：矩阵对象（`cells: number[][]`，0=空/−1=锁定/1–10=色）**
- 事实对比：运行时零解析、类型直读；但 JSON 体积膨胀约 5–8 倍（每格 3–4 字符 vs 1 字符）；策划/美术对照参考图核对方阵困难（数字无视觉形态）；丢失"字符集即校验器"的判例复用，需另写校验；与 systems-index §3.2 已冻结的 `BEAD_CHARSET` 定义冲突，需回写设计文档。

**方案 C：双轨（JSON 行字符串 + 构建期编译为二进制/Int8 数组资产）**
- 事实对比：兼得体积与运行时零解析；但 8 关 × 600B 的解析成本在 BOOT 一次 <1ms，**性能收益不存在**；多一条编译链与产物管理成本，对 demo 是纯负债。

## 3. 决定（Decision）

选**方案 A**：关卡以 `BEAD_CHARSET` 行字符串数组 + 元数据字段的 JSON 承载，BOOT 期 `validateLevel()` 一次性校验并解析为运行时矩阵。判例与 breakout 完全对齐。

## 4. 后果（Consequences）

**4.1 正面**
- 校验器直接复用 breakout 判例（字符集 + 行宽 + 硬约束断言），两游戏校验心智一致。
- 关卡文件可读、可 diff、可由策划/美术直接审阅对照参考图。
- 8 关 demo 数据体积可忽略（<5KB），主包预算无压力。

**4.2 负面（已知成本，如实记录）**
- 色板被字符集**硬编码上限锁死在 16 语义内**；若未来色板超 10 色需扩展字符集（如小写字母）并迁移存量关卡数据。
- 运行期拿到的是解析后矩阵，调试时需保留行号→格坐标的映射才能反查关卡源；`validateLevel` 错误信息必须带关卡 id + 行列（S1§8-9 已要求）。
- 字符形态无类型保护，手写关卡时 `l`/`1`、`O`/`0` 类混淆只能靠校验器在启动期拦截，编辑期无提示。

**4.3 中性 / 待观察**
- 方案 C 在关卡数量上量（>50 关或含美术资产引用）后可重新评估。

## 5. 复评触发条件（Review Triggers）

- `BEAD_COLOR_MAX` 需要超过 10（字符集 1-9+A 用尽）→ 复评字符编码扩展方案。
- 关卡数 > 50 或引入分关资产 → 复评方案 C 编译链。
- 策划侧引入"每格多层/多珠"类新语义（当前一格一珠）→ 字符集不再够用，复评矩阵对象。
