# ADR-0016 — beads 照片转拼豆：调色板扩编与单关用色数的边界（生成侧保形 vs 可玩性聚集）

- **状态**：**Proposed（草案待裁）** —— 本文只给方案与实测证据，**不替主理人 / 用户拍板**。甲案零冻结变更、可立即执行；乙 / 丙两案须先有 playtest 与 a11y 判断。
- **日期**：2026-09-20
- **关联**：ADR-0004（关卡数据 rowstrings，`BEAD_CHARSET`）/ `systems-index §3.2`（`BEAD_COLOR_MAX` 冻结行）/ `art-bible §3.2`（10 色调色板 + 三重编码，美术真源）/ `view/palette.ts::BEAD_PALETTE`（实现真源）/ `accessibility`（色 + 符号 + 明度三重编码）/ 任务 `WXG-T-179`（前置 spike）
- **上位诉求（用户 2026-09-19/20）**：①「豆子尽量同色大块集中，以触发连续填充」；②「颜色限制太少了，看不出来形状了」；③ 提供真实拼豆品牌色数调研（Artkal 200+ / Perler 100+ / Hama 60–90 / Nabbi 30–50 / IKEA-Pyssla 10–20），并要求「根据这个方案进行调优」。

## 1. 上下文（Context）

### 1.1 现状：三条被冻住的边界（逐条引真源）

| 项 | 现值 | 真源 | 语义 |
|---|---|---|---|
| 调色板 | **10 色** | `view/palette.ts::BEAD_PALETTE`（美术真源 `art-bible §3.2`） | 每色绑 **符号 + 明度档** ⇒ **三重编码** |
| 单关用色上限 | **8** | `tuning.ts::BEAD_COLOR_MAX`（`systems-index §3.2` 冻结行） | 一关最多用 8 种（demo 关实际 3–8） |
| 色索引字符集 | `.x1-9A`（1–10） | `tuning.ts::BEAD_CHARSET` + `levels.ts` 校验 | 关卡 rowstring 只能表达 **≤10** 色（ADR-0004） |

**关键澄清（本轮实测前普遍被误解）**：`BEAD_COLOR_MAX = 8` 是**单关用色数上限**，不是调色板大小 —— 调色板有 **10 色**，一关从中挑 ≤ 8 色即合规。此前生成侧只用了**前 8 色**，把两个暗色（深棕 `#6B3E1E` / 炭黑 `#33333D`）弃之不用 ⇒ **照片暗部无落点**，是"看不出形状"的重要来源之一（低成本的错，已修）。

### 1.2 动因：照片 → 拼豆的两难

真实拼豆的制图流程（用户调研）= **大色板选色 → 手动限制用色数**：色数越少越好做，但越少越不像。游戏侧面对同一对矛盾，并额外受上述三条冻结边界挤压。

### 1.3 本轮实测（`WXG-T-179` 前置 spike，`temp/beads-gen.mjs`）

两个正交旋钮（**色板大小** × **限色数**）+ 两个量化判据（**色差** = 每格最终色 vs 原图均色的距离均值，越小越保形；**同色相邻率** = 相邻同色边占比，越大越成块）：

| 配置 | 实际用色 | 色差 ↓ | 同色相邻率 ↑ | 合规 |
|---|---|---|---|---|
| 调色板前 8 色（**旧口径**） | 7 | 74.7 | 0.846 | ✅ |
| 10 色板 + 限 8 色 + error 选色 | 8 | **70.4** | 0.783 | ✅ |
| 10 色板 + 限 8 色 + error + 强聚集 | 8 | 71.4 | 0.807 | ✅ |
| 10 色板 + 限 6 色 + error + 强聚集 | 6 | 73.3 | 0.826 | ✅ |
| 程序化 32 色板 + 限 6 色 + error | 6 | 63.3 | 0.844 | ❌ 超 charset / 无对应珠色 |
| 程序化 53 色板（不限色） | 20 | **47.6** | 0.712 | ❌ 同上 |

三条由数据支撑的结论：

1. **保形度上限由「色板大小」支配，色数只是放大器** —— 8 色板即使**完全不限色**也止步 74.7；53 色板可达 47.6。
2. **保形与聚集是一对直接冲突**：色多 ⇒ 暗部/过渡被切成多档 ⇒ 色块变碎。上表八个配置里两者始终反向。
3. **游戏约束内（10 色 / ≤8）的最优 = 「限 8 + error 选色 + 强聚集」**，色差 71.4 / 聚集 0.807 —— 相对旧口径 **色差 −3.3、聚集 −0.039**，属**有限净改善**。

### 1.4 诚实划界（本文证据的效力边界）

- spike 色板为**程序化近似**（HSL 最远点采样），**不含品牌实测 hex** ⇒ 绝对值只读**趋势**，不得当成"某品牌能达到 X"的结论；
- 对比口径**不完全公平**：色板变化会改"四边框最常见色"的背景判定 ⇒ 可填格数不同（1177 / 1013 / 1103）；
- 色差 / 相邻率均为**代理量**，**未经人眼验证** —— 屏幕观感是唯一终审（K-037：可证层级）。

## 2. 备选方案（Alternatives）

### 2.1 甲：不动冻结值，只优化生成侧（**推荐立即执行**）

- 用满 10 色板（含两个暗色）；`--colors ≤ 8` 保证合规；选色改**误差最小**（贪心 k-medoids）而非频次优先；再加众数滤波 / 碎块并入做聚集。
- 成本：**零冻结变更、零 charset 变更、零游戏代码改动**（生成器是独立脚本）。
- 收益：色差 74.7 → 71.4；聚集可调回 0.807。
- 代价：**改善幅度有限**，且聚集仍略低于旧口径的 0.846。

### 2.2 乙：只扩「单关用色上限」`BEAD_COLOR_MAX` 8 → 12/16

- ≤10 色**无需动 charset**；>10 色须扩 `BEAD_CHARSET`（如 `.x1-9A-F`）⇒ **动关卡数据格式**（ADR-0004）与 `levels.ts` 校验。
- 收益：生成侧可选色变多（暗部 / 肤色更有落点）。
- 代价：① 单关色数变多 ⇒ 上手与辨识成本上升，**与"更好做"的初衷相反**；② 会**加剧碎片化**（§1.3 结论 2）。

### 2.3 丙：扩「调色板」`BEAD_PALETTE` 10 → 16/24

- 必须连带：**新符号**（现 10 个符号已一一占用）、**新明度档**、`art-bible §3.2` 重写、`accessibility` 复核、`BEAD_CHARSET` 扩展。
- 收益：保形度上限显著抬升（§1.3 结论 1）。
- 代价（**本文最需被看见的一条**）：三重编码（色 + 符号 + 明度）是 a11y 的**根**，而符号集与明度档都是**有限资源**；色数扩编会**稀释每个色在符号 / 明度上的唯一性** ⇒ **等于以牺牲可访问性换取保真度**，与 `accessibility` 的 D1/D2 精神直接冲突。

### 2.4 丁：双轨（游戏内不动；生成器开放大色板，产物外用）

- 游戏内维持 10/8（可玩性优先）；生成器开放 `--palette N`（**已实现**），大色板产物用于**参考图 / 实体拼豆导出**，**不入关**。
- 成本：几乎为零（能力已具备，只需明确用途与"不可入关"标注）。
- 收益：正面回应"真软件体验"的诉求，且**不给游戏侧背 a11y 债**。

## 3. 决定（Decision）

- **推荐：甲（立即执行）+ 丁（作为产品方向）**；**乙 / 丙挂起**，不进本轮。
- **本文明确不裁**：乙的取值（12 还是 16）、丙是否做 —— 须先有 a11y 复核结论 + 用户对"像不像 / 好不好做"的 playtest 判断。
- **甲案落笔清单**：生成侧 ① 用满 10 色板；② 默认 `--colors ≤ 8`（合规）；③ 选色默认 `error`；④ 报告**并列**输出「色差 / 同色相邻率 / 用色数 / 合规性」四项 —— **禁止只报单一指标**（否则会重演"只看色数就砍到 3 色"的误判）。
- **工具归属**：生成器现为 `temp/` 下 spike（**不入库**）⇒ 甲案若要长期使用，须**转正入 `tools/scripts/`** 并另领施工单。
- **本文不改动的文件**（诚实划界）：`systems-index §3.2`、`tuning.ts`、`view/palette.ts`、`art-bible §3.2`、`accessibility`、`levels.ts` —— 乙 / 丙未裁前一律不动。

## 4. 后果（Consequences）

### 4.1 正面

- 甲案**零冻结变更**即可改善（"暗部落点"是此前最便宜的一处遗漏）。
- 生成侧获得两个可解释的量化判据与两个正交旋钮 ⇒ "调优"从手感变成**可复算**。
- 丁案让"照片转拼豆"体验有了**不伤游戏侧**的出口。

### 4.2 负面（已知成本，白纸黑字，不是风险）

- **甲案改善有限**：色差 −3~4，且以聚集度小幅下降为代价。用户若要"明显更清楚"，**甲给不了**。
- **乙 / 丙的代价是结构性的**：乙动数据格式，丙动 a11y 的根 —— 两者都不能"只加个数字"。
- 本文数值来自**程序化近似色板 + 单张样图**，**不得**当产品结论；换图或换品牌色板，结论可能漂移。

### 4.3 中性 / 待观察

- 真机观感（唯一终审）仍待用户看图 / playtest。
- 若未来引入「实体拼豆导出」或「品牌色板选择器」，丁案升格为正式轨，届时需补**品牌实测 hex** 数据源。

## 5. 复评触发条件（Review Triggers）

1. 用户对甲 / 丁产物给出**人眼判断**（"能不能看出形状 / 好不好做"）—— 这是解锁乙 / 丙的前置。
2. 若结论含"要明显更清楚" ⇒ 先评估**丙**（连带 a11y 复核），而非只抬 `BEAD_COLOR_MAX`。
3. 若出现**实体拼豆导出**需求 ⇒ 丁升格，并补品牌实测色值。
4. a11y 复核若证明三重编码可安全扩编（符号 / 明度仍有富余）⇒ 丙的负面后果降级，可重评。
