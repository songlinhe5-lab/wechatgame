# IMPACT-0020a — 「5mm ↔ 32px 硬映射」vs 渲染域 50/52：跨域影响评估

- **类型**：**影响评估（Impact Assessment）**，**不是 ADR** —— 本文不产出 §3 Decision，不占用 ADR 编号。
- **状态**：待裁（本文所有「推荐」均为工程侧意见，对 §3 冻结数值无裁定力）
- **日期**：2026-09-24
- **关联任务**：WXG-T-206 姊妹单（本体 = `ADR-0020-beads-board-debug-zoom-focus.md`，本目录，状态 Proposed / **git untracked**）
- **上游裁定（用户，本任务单转述）**：「5mm 物理拼豆 ↔ 32 dip/pt 是硬映射，应按此标准做」
- **本文不改**：`systems-index §3`、`games/` `dev/` `packages/` `apps/` 任何代码（任务单硬约束）

## 摘要（一页结论）

1. **两套尺子属实，但不是两套、是三套，且其中一套已是 Accepted 裁定**：源图域 32px/珠（`levels-spec §3.1` v1.8）· 渲染域 50/52（`§3.3`）· **`ADR-0018` §3.4 L153 已将 `BEAD_CELL=50` 定为「5mm Midi 豆的等比参照（zoom=1）」，状态 Accepted**。用户本轮「5mm ↔ 32 硬映射」与第三条直接冲突 ⇒ **先裁口径冲突（§6.1 W0），再谈数值**。（另：任务单用的单位「dip/pt」在本仓**查无实据**，需重述后才能施工，§2 注。）
2. **改 32 基不会修好用户看到的症状**：fit 缩放会把变小的尺子**除回去** —— 14×18 盘屏上 pitch 为 32.96（52 基）vs 33.00（34 基），差 0.12%。真因是 `drawTargetTile` 不吃缩放（`bead-render.ts:290-301`），属 ADR-0020 附录 A 甲案，**不改 §3 即可修**。
3. **最大三个代价**（均工程可自证）：① **LOD 档结构性失效** —— 阈值 `BEAD_LOD_CELL=45` 在 32 基下需 `zoom 1.406`，而 `computeFitZoom` 含 `Math.min(1,…)` ⇒ **默认视角恒降档，中心孔质感在入口屏永久缺席**；② **绝对地板塌缩** —— `BEAD_DRAW_INSET=6` 与 `minStroke=2` 不随缩，32 基下珠面占格从 73.1% 跌到 58.8%（面积 53%→35%）、所有质感线宽一并被钳到 2px，而 `inset=6` 本身是**真机可读性裁定值**（不可纯比例化）；③ **命中结构不变式重验** —— `HIT/PITCH` 从 1.269 跳到 **1.941**，`§3.8`「外扩 8px」论证与 `ADR-0015 §3.3-4` 的 `52z<66z` 理由均需重写。
4. **对 (B) 有利的两项零成本发现**：① 关卡 JSON 只存 `cols/rows/pattern`（**不含 px**）⇒ **不需重烤任何已生成关卡**；② src 侧直读 `BEAD_PITCH/BEAD_CELL` 的只有 **2 个文件 15 行**（`board-camera.ts` / `bead-render.ts`），`view-model` 全程走 `snap.grid*` ⇒ 代码爆炸半径远小于 `ADR-0015 §4.2-5` 立项时估的 200–350 行（丁-3 已付清）。代价不在代码，在**冻结值与需真机/art 的判定**。
5. **工程侧推荐：先走 (A)**（统一文档口径 + 单独修 tile 缩放 bug），(B) 归设计轨。理由：(A) 完全可逆且不触 §3；(B) 的三大风险均落在本环境**不可自证**区（无设备无 AppID），且需重开一条 Accepted ADR。(B) 的真实收益（恒等档容纳 13→20 列）**不在用户症状上**。
6. **双尺子的真正病根是「镜像无守卫」，与选哪把尺无关**：已发现三例现成漂移——`board-render.js:38 RADIUS 0.22` vs 游戏 `0.30`（§3.9）；`assets-spec`/`accessibility.md` 基线 1828 vs 实测 1587（§3.7）；`scene-vfx.test.ts:242` 注释数值 49.68 已过期（实算 41.04，§3.10）。⇒ **即使本轮不改数值，也应先建机制（§7.2）**。

## 2. 问题陈述：确实是「两套尺子」吗？

是，但**比口号更微妙——而且是三条互斥口径**。本仓现存尺子如下：

| # | 域 | 尺子 | 真源位置 | 用途 |
|---|---|---|---|---|
| ① | **源图/做图域** | 1 珠 = **32 px** | `levels-spec §3` L73 / §3.1① L101–109（路径 `games/beads/design/levels/levels-spec.md`，**任务单写的 `design/levels-spec.md` 不存在**） | 决定「一张源图能推成几格盘面」—— 只在**导入/推断**时生效 |
| ② | **渲染域（设计空间）** | `BEAD_CELL=50 / GAP=2 / PITCH=52` | `systems-index §3.3` L98–100 → 镜像 `tuning.ts:121/123/125` | 决定「一颗珠在 750×1334 画布上占多大」 |
| ③ | **格数上限** | `GRID_MAX_COLS/ROWS=32` | `§3.3` L101/102 → `tuning.ts:140/142` | 单图/组合图（Plate）分界线 = 切块阈值 |
| ④ | **物理↔渲染映射（已被裁过！）** | `BEAD_CELL=50` 设计 px ≡ **5mm Midi 豆的等比参照**（`zoom=1`） | `ADR-0018`（**状态 Accepted，2026-09-20 用户拍板**）L24 表行 + **§3.4 L153** | 触控/取景基准；ADR-0017 LOD 满层判定与 `art-bible` 十层卡尺寸「均以 zoom=1 为基准」 |

> ⚠️ **本次评估最重要的更正**：「5mm 物理尺寸 ↔ 渲染域」的映射**在本仓不是空缺，而是已经被裁定过一次——裁定值是 50，不是 32**（`ADR-0018:24/153`）。因此用户本轮「5mm ↔ 32 是硬映射」与一条 **Accepted ADR 的基准定义直接冲突**；(B) 的真实代价包含「推翻 ADR-0018 §3.4」，见 §4.9。

**三条口径的互斥关系（须裁一条，工程侧不代答）**：

| 口径 | 内容 | 出处与状态 |
|---|---|---|
| (i) | 5mm 参照 = **50** 设计 px（zoom=1 即实物比例） | `ADR-0018` §3.4 L153 + L24，**Accepted** |
| (ii) | 5mm 域硬映射 = **32**（本轮裁定转述）；源图标准 32px/颗 | 本任务单 + `levels-spec` v1.8 L472（用户 2026-09-22） |
| (iii) | 32 属源图域，与游戏内几何**无换算关系**（「文本巧合，须排除」） | `ADR-0020` §1.3 L80（本仓上一轮草案，Proposed） |

⇒ (i)(ii)(iii) **不可能同时为真**。这不是工程能消解的矛盾，是**语义裁定**，已上升为 §6.1 W0。

> ⚠️ **前提级事实核对（不承接未经验证的转述）**：任务单里的单位「**dip/pt**」在本仓**不存在**——全文检索（`dip\b` / `dip/pt`）仅命中三处：本文与 文策渊 草案（两处均在**引用任务单原话**）与一个 QA 探针局部变量（`production/qa/beads/beads-browser-probe.mjs:816`，无关）。⇒ 不代表用户意图错，但代表**该裁定现在无法直接施工**：需先用仓内已有术语重述（“1 格 = 1 颗 5mm 豆；源图 32px/格；渲染域参照待 W0”），否则任何实现都会变成各 自解释。本条与 文策渊 草案 §0（L30）独立得出同一结论，算**双方互证**。

**关键澄清（若 (i) 或 (iii) 胜出则成立）**：①与③**已经**统一在「32」上（`tuning.ts:130` 注释自证：「与每颗像素标准 32px 严丝合缝：1024 源图 → 32×32 最大单图」）。而 ① 的单位是**源位图像素**（磁盘上的 PNG），② 的单位是**设计像素**（`tuning.ts:10-12`「Units are *design-space* units」，750×1334 虚拟画布），两者之间**本来就必须有一个缩放**（`fit`），因为它们量的是不同的东西。

⇒ 用户裁定「按 32 硬映射做」的正确落点，取决于要修的是哪一类症状。本文 §5.1 给出结论：**症状真因不在尺子，在 `drawTargetTile` 不吃缩放**（见 §5.1 理由 1 与摘要第 2 条；修法 = ADR-0020 附录 A 甲案；口径冲突裁定位 = §6.1 W0）。

## 4. 走 (B)（渲染域整体改 32 基）的代价与风险

### 4.1 头号反直觉结论：**改尺子修不好用户看到的症状，也不改变观感大小**

Node 复算（附录 B）：

| 盘面 | 52 基 fit / 屏上 pitch / 珠体 | 34 基（cell32+gap2）fit / pitch / 珠体 |
|---|---|---|
| 14×18（MVP） | 0.6338 / **32.96** / 19.69 | 0.9705 / **33.00** / 19.06 |
| 18×18 | 0.6338 / 32.96 / 19.69 | 0.9705 / 33.00 / 19.06 |
| 22×18 | 0.6147 / 31.96 / 18.74 | 0.9410 / 31.99 / 18.11 |
| 29×29 | 0.3931 / 20.44 / 7.65 | 0.6016 / 20.46 / 7.25 |
| 32×32 | 0.3562 / 18.52 / 5.81 | 0.5451 / 18.53 / 5.44 |

（珠体 = `BEAD_CELL*z − 2*BEAD_DRAW_INSET`，inset 为**绝对值不随缩**；`bead-render.ts:397/398`）

⇒ **屏上 pitch 两基几乎逐位相同（差 0.12%，肉眼不可辨）**。原因直白：`fit` 的定义就是「把 natW 塞进 702 宽」，把尺子改小只是让 `z` 变大，**乘积不变**。所以 (B) **不会**让珠变大，也不会让「错位/重叠/露底色」变好 —— 那些症状与尺子无关（§6.1）。

(B) 的**真实**收益只有一条：**zoom=1（恒等档）可用范围扩大** —— 原生容纳从 **13 列 / 11 行** 升到 **20 列 / 17 行**（含 2×24 边距）。这解释了为什么历史上 `GRID_MAX_COLS` 曾等于 13（`ADR-0015:31/32`：`13×52−2 = 674 ≤ 690`）—— **那不是玩法偏好，是 52 反推的几何容纳**。

### 4.2 LOD 档在 32 基下**结构性失效**（工程可自证，最硬代价）

- 阈值语义：`BEAD_LOD_CELL = 45` 的来历 = 「zoom 0.9 × **50**」（`tuning.ts:840`，`ADR-0017:4`）。
- 34 基下 `cell = 32*z` ⇒ 达 45 需 `z = 1.406`；而 `computeFitZoom`（`board-camera.ts:92`）含 **`Math.min(1, …)`**，缩放下限是 fit、上限是 `fit*2.5` ⇒ `z=1.406` 只在已放大到 fit 之上很多时才可达。
- 后果：fit 档与所有中小盘常态视角下 `cell < 45` **恒成立** ⇒ **恒降档**，满层档永不可达。用户 2026-09-23 刚拍板的 K1 `radius 0.30`、L1c 中心孔质感（识别红线）在默认视角**永久缺席**。
- ⇒ `BEAD_LOD_CELL` 与 `BEAD_LOD_HYST` 必须**重冻结**（不是等比换算能了事的：滞回 2.5 设计px 在 50 基是 5% 带宽，在 32 基是 7.8%）。**这条属 §3.3/ADR-0017 双真源，须 文策渊 + art 联裁。** `[需真机确认降档边界观感]`

### 4.3 `BEAD_DRAW_INSET=6` 与 `minStroke=2` 的**绝对地板塌缩**（工程可自证 + 观感待真机）

- `inset` 与 `minStroke` 都是**绝对设计 px**，不随 `size` 缩 ⇒ 它们与尺子的比值会变：

| 量 | 52 基 @z=1 | 34 基 @z=1 |
|---|---|---|
| 珠体 size | 38 | 20 |
| 珠体占 pitch | 73.1%（面积 53.4%） | **58.8%（面积 34.6%）** |
| 暗倒角 5/64 | 2.97 | 1.5625 → **钳成 2** |
| 亮倒角 4/64 | 2.375 | 1.25 → **钳成 2** |
| rim 3/64 | 1.78 → 2 | 0.94 → **2** |
| 圆角 `round(size*0.30)` | 11 | 6 |
| 中心孔半径 | 6.84 | 3.60 |

- ⇒ 34 基 @z=1 时**所有质感线宽同时塌到 2px 地板**，暗/亮倒角的**方向性信息在恒等档即消失**（K1/K4/K5 层差被抹平）。诚实补一句：52 基在 fit 档（size 19.69）**其实也已经塌**（暗 1.54→2）—— (B) 的净代价是「**把塌缩从缩放态推到恒等态**」。
- 若要保比例，`inset` 须随尺子降到 ≈3.84 ⇒ 但 `inset=6` 是 **WXG-T-162 真机可读性裁定的地板值**（2 在 scale 0.5 下 ≈1 CSS px 看不见），**不能纯比例化**。这道「绝对地板 vs 比例尺子」的张力是 (B) 的核心未解项，**属 林绘澄 域**。`[需 art/真机]`

### 4.4 命中语义破裂（工程可自证）

- `GRID_HIT_SIZE = 66 = 50 + 2×8`，「外扩 8px」的论证**依赖 BEAD_CELL**（`systems-index §3.8` L161；`tuning.ts:437-441`）。
- 结构不变式 `52z < 66z`（`tuning.ts:1085`；`ADR-0015:152` 引 `input-control §8-2`「因 BEAD_PITCH(52) < 命中区(66) ⇒ 网格内部外扩区必然重叠，一律按最近格心裁决」）。
- **HIT/PITCH 比值：52 基 = 1.269，34 基 = 1.941** ⇒ 相邻命中盒重叠从「略重于格距的 1.27 倍」跳到「近 2 倍格距」：最近格心裁决的**负担与误触面显著变化**，`§8-2`「网格内部不存在带间隙处」的字面理由需重写（不变式仍真，但**论证的强度变了**）。
- 若要保 1.269，需 `GRID_HIT_SIZE ≈ 43` ⇒ **跌到 `TOUCH_MIN=88` 之下更远**（现在已有 `ADR-0015 §3.4` L167 的「z<1 击穿 TOUCH_MIN」钳位议题）。这是无障碍底线条款的连带，**属 §3.8 冻结面，须 文策渊**。

### 4.5 缩放/平移界全表重算（工程可自证，机械但面广）

- `computeFitZoom`（`:88-92`）、`boardPx`（`:77-78`）、`clampCamera` offset 夹取（`:177-181`）、`applyPinch` 上下限（`:144`）四处派生量随 PITCH 变。
- 溢出核算（`ADR-0015:117` §2.2 丁-3 免 clip 的**唯一理由**）：「边缘珠最多外溢 `BEAD_CELL/2 = 25` < 带间空隙 30 / 94」。34 基 → 外溢 16，**该不变式仍真且更宽**（对 (B) 有利）。
- 但 `§3.3` L104「左右留边 ≥ (750−674)/2 ≈ 38」的 674 与 `GRID_MAX` 历史 13/12 的推导全部失效 ⇒ **§3.3 表内 4 处派生说明须同批重写**（L100/101/102/104/107/108）。属真源文本，工程侧不能代改。

### 4.6 图元数与包体（**对 (B) 中性偏有利**，工程可自证）

- 程序化渲染（ADR-0005）⇒ 改尺子**不动任何位图资产、不动包体**。
- 每帧图元**条数不变**（层集不变，§11.2 基线 1587 = 结构计数，与绝对尺寸无关）⇒ `check-bundle-size.mjs` 无需改。
- 但 §11.2 基线是**特定夹具（13×12）+ 特定尺子域**的计数；若 34 基改变「一屏可见格数」则同屏命令数会变（可见集变了），须按 K-051 重跑差分复算，**不得沿用 1587 作新基线**。

### 4.7 已生成关卡**不需重烤**（对 (B) 有利的零成本结论，工程可自证）

- 关卡 JSON 只存 `cols/rows/pattern[]` 字符行串（`ADR-0004` rowstrings），**不含 px**；`levels.ts:120-121` BOOT 校验只查格数。
- ⇒ 改渲染域单位**不影响任何已生成关卡数据**。需动的只有**文档口径**：`levels-spec §3` 表「源图推荐 px」列（L73/79/101）与 studio 推断阈值（`index.html:391-393`、`server.mjs:296-301`）—— 而那属**源图/做图域**，与 32 标准本就一致，改渲染域反而**不需要动它们**。

### 4.8 beads-studio：必须同批改，否则漂移扩大（工程可自证，**已有实证**）

### 4.9 会推翻一条 **Accepted** ADR 的基准段（工程可自证，**本文初稿漏检项**）

### 5.1 工程侧推荐（**不代裁**，供主理人与 文策渊/林绘澄 决策）

**推荐：先做 (A)，并把 (A) 拆成两个可独立执行的批次；把 (B) 记为「有明确收益但收益不在用户症状上」的设计轨议题，暂不进入 §3 变更通道。**

理由（按承重排序）：

0. **先解口径冲突，再谈数值（W0）**：`ADR-0018` §3.4（**Accepted**）已将 50 设px 定为 5mm 实物等比参照。若本轮裁定意图是推翻它，必须**先走一张作废单**，而不是在渲染代码里默改常量（判例 K-057：状态行与裁定需成对核销）。本文不假设任何一方已胜。

1. **用户的症状归 (A) 侧的一个 bug，不归母尺**：`drawTargetTile` 不吃缩放（`bead-render.ts:290-301`，签名无尺寸入参；调用点 `view-model.ts:800/901`）⇒ tile 恒按 52 画、格心缩放后仅 32.96 ⇒ 相邻 tile 重叠 19.04（占格 58%）、珠体 19.69 只覆盖底图 38% —— 「错位 / 相邻糊成一片 / 露不出底色」三条现象同源。**改 32 基既不必要也不充分**（两基屏上 pitch 差 0.12%）。修法见 ADR-0020 附录 A **甲案**（tile 传 `snap.gridPitch`），代价仅 `bead-render.test.ts:116/117/120`、`fill-pop.test.ts:183-186`、`view-model.test.ts:103/122/266` 三条钉死 pitch 的断言须改写为「tile 边长 = `layout.pitch`」。
2. **(B) 的最大风险恰好落在本环境不可自证的区间**（§4.2/§4.3/§4.4 三条都需真机或 art 判读）。在无 AppID、无设备、Cocos 构建链未通的前提下推 (B)，等于把 §3 冻结值交给一组 `[R]` 结论。
3. **(A) 可逆、(B) 半可逆**：数值冻结的回退成本远高于文档口径的回退成本；(A) 之后仍可无损升级到 (B)。
4. **真正的病根是「镜像无守卫」，不是「52」**：`RADIUS 0.22/0.30` 与「基线 1828/1587」两例漂移都发生在**不改数值也会漂**的地方。先建机制（§6.2），再谈统一数值，顺序不能反。

若 文策渊 认为「恒等档可用范围（13→20 列）」本身值得付这笔账，(B) 是**可做但须整批**的：§3.3 + §3.8 + LOD + studio + 夹具 + 真机判定表为**一个不可拆的变更单**（拆开即 ADR-0015 §4.2-3 登记的「§3 冻结面漂移」翻版）。

### 7.1 换算链（建议以 `systems-index` 新增**非冻结注记**（§3.3 表下注）为唯一真源，其余全部引用它）

```
[物理域]  5 mm 豆径（Midi 标准方盘 29×29）
   ↕  映射 M1：1 格 ≡ 1 颗豆（物理档位 → 格数；ADR-0018 裁定可玩档位）
[格数域]  cols × rows ∈ [6×5, 32×32]（§3.3 GRID_*）—— 关卡 JSON 唯一存的几何量（ADR-0004 rowstrings）

[源图域]  PNG ≤ 4096²，前端不缩图直传；beads-gen 每格 8×8 采样（= 每采样点 4 源像素）

## 附录 B — 复算脚本（原样可跑）

// node /tmp/ia-recompute.mjs（本文实算所用）
const DW = 750, BAND = 1120 - 480, M = 24;         // tuning.ts:17 / :27 / :1036
const fit = (c, r, P, G) =>
  Math.min(1, (DW - 2 * M) / (c * P - G), (BAND - 2 * M) / (r * P - G)); // board-camera.ts:88-92
for (const [t, S] of [['52基', {P:52,G:2,C:50}], ['34基', {P:34,G:2,C:32}]]) {
  for (const [c, r] of [[14,18],[18,18],[14,14],[22,18],[29,29],[32,32],[13,12],[10,10]]) {
    const z = fit(c, r, S.P, S.G);
    console.log(t, `${c}x${r}`, 'fit=' + z.toFixed(4),
      'pitch=' + (S.P * z).toFixed(2), 'cell=' + (S.C * z).toFixed(2),
      'bead=' + (S.C * z - 12).toFixed(2),      // bead-render.ts:397-398（inset 绝对，不随缩）
      'hole=' + ((S.C * z - 12) * 0.36 / 2).toFixed(2));  // :509
  }
  console.log(t, 'HIT/PITCH=' + (66 / S.P), 'maxCols=' + Math.floor((DW - 2*M + S.G) / S.P),
              'LOD需zoom=' + (45 / S.C).toFixed(3));
}
```
