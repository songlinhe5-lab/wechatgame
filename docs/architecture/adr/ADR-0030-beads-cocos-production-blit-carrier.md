## 0. 结论（先给一句话与账）

**推荐 = 丙′「同源 Canvas2D 帧通道」：在 Cocos 宿主里实例化现役 `Canvas2DRenderer`（与 harness 逐字同一份代码），
把 `TintSpriteCache` 的合成产物作为 blit drawable，整帧画进一张离屏 canvas，再上传为一张 `Texture2D` 由 Cocos 显示。**
**前置 = 丁「blit carrier 抽象」**（S1，与载体选型解耦，无论最终用谁都要写那一次）。

三条支撑（都可被本仓文件核验）：

1. **它是唯一天然满足用户诉求本体的候选**。诉求 = 「同一套绘制」，不是「某个更快的 Cocos 载体」。
   甲′/乙 都是**第二套实现**（一次重新解释观感），只有丙′ 是**同一套代码在两个宿主里跑**。
   而且它把 `ADR-0022 §4.2-2` 当年主动放弃的「harness 与 Cocos 逐像素等价」契约**买回来**（§4.1-3）。
2. **复用率 > 新增率**：`Canvas2DRenderer` / `TintSpriteCache` / `tint-blit-resolver` / `compositeTintMask` /
   `mask-field` **全部已在 Cocos 镜像内或纯 TS**；`bake-surface-impl.ts:107` 甚至已在 Cocos 工程里
   `new Canvas2DRenderer(...)`。真正新增只有**宿主层一个 carrier 文件**（canvas 工厂 + 纹理上传）。
   对比：甲′ 需新增「运行时 `SpriteFrame`/图集构造 + 逐珠节点池 + 材质」；乙 需新增「盘面索引纹理通道 + `.effect` 扩 mask 采样 + 布局 uniform 接线」。
3. **它把 ADR-0029 §0 的推迟前置（真机帧时间与显存）从「采纳门禁」降级为「换代门禁」**——理由见 DEC-9，
   并给出取数批 S2。**诚实声明**：丙′ 的性能账**没有数据**，它的正当性来自「一致性 + 复用面 + 回退成本」，
   不是来自「它更快」。若 S2 读数否决它，换代路径已写死（S6 → 甲′/乙）。

仍缺的数据（全部标 `[待实测]`，⛔ 不得由桌面档外推，ADR-0028 T2' 纪律）：
每帧 CPU 2D 填充 ms、canvas→GPU 上传 ms、满幅纹理显存字节、真机 draw call、离屏 2D canvas 在 wx 宿主的可得性。

> **⚠ 2026-10-06 修订（S0 第 2 步已出数）**：上列前四项已在 **`[E]` 桌面档**拿到真读数（§5.0.1），
> 结论方向与本节初稿不同：**丙′ 在本档确实最快，但采纳门禁（S0 第 1 步：wx 离屏 canvas + canvas→纹理）未过，
> 且每帧上传实测 5.75 MiB** ⇒ 本单推荐改为「先脏帧门控 → 主选 甲′ → 丙′ 降第二候选」。
> 本节初稿的「诚实声明（丙′ 的性能账没有数据）」已不成立，**有数据了，数据不站在它那边**（在移动端量级未知这一意义上）。
>

### 1.2 症状与真因（不重复推翻编排者取证，只做定性）

真机"画出来是矢量臂"**不是缺陷，而是当前架构的正确行为**：F-2 + F-3 + F-4 三件事叠加 ⇒
Cocos 路径上 tint 与 blit **结构上不可能发生**。所以「解决」的性质是**补一段从未存在的生产通道**，
而不是修一个坏掉的东西。这一条必须写清，否则后续会把"真机没珠子"错记成回归缺陷。

## 2. 备选方案

### 2.0 选型纪律（先问「这是否需要存在」）

四条尺子，按权重排序：①**观感一致性**（= 用户诉求本体）②**改动面与复用率**③**真机成本风险**④**未验证引擎面**。

两条淘汰结论，直说不绕：

- **「逐珠 Sprite/SpriteFrame 池 + `customMaterial`」的原始形态（甲的原版）不需要存在**——它已被
  `ADR-0022 §2.1` 否决（大概率逐颗断批、fill 零改善、正面冲突 §8 合并 draw call），本单**不复活**；
  活下来的是它的改形 **甲′**（按色合批），且甲′ 的归属是 **S6 换代候选**，不是本批主选。
- **「carrier 抽象（丁）」不是竞品**：它是甲′/乙/丙′ 的**共同前置**（F-3 证明 Cocos 侧连注入缝都没有）。
  把它列进对比表只为说明**它单独不能解决用户的问题**（有缝没载体 = 仍然 warn-skip）。

### 2.1 丁｜Cocos 侧只补齐 blit carrier 抽象（框架层，选型无关）

- **做法**：给 `CocosRendererOptions` 加一条宿主注入的 **carrier 槽**（与 canvas2d 的 `blitResolver` 对称的**结构类型**，
  不 import `cc`）；`case 'blit'` 由「warn-skip」改为「有 carrier ⇒ 交出去；无 carrier ⇒ 行为与今日逐字节相同」。
  纹理/mask/canvas 的 IO 全部留在 adapter 层（L2/L3/L5）。
- **事实与锚**：`canvas2d-renderer.ts:107/112/131` 已是同一形状的先例（`textureRegistry` / `blitResolver`，
  缺省回落注册表，且渲染器**不认识效果语义**——`ADR-0029 §8.1/§8.2` 的收口口径）；
  `cocos-renderer.ts` 的 `CocosGraphicsLike` / `CocosColorFactory` / `transformHost` 三条**结构类型先例**证明
  「宿主能力用结构类型注入、`cc` 只出现在 bindings」这套写法在本目录已成立。
- **单独的价值**：把 F-2 从"永久跳过"变成"可扩展"，并让 `ADR-0029 §6` 触发器 5 的命中变成**可插拔事件**而非架构改动。
- **单独不够**：一致性 0、观感 0 变化 ⇒ 它必须是 S1，不能是答案。

### 2.2 丙′｜同源 Canvas2D 帧通道（**推荐**）

- **做法**：宿主创建一枚离屏 2D canvas（尺寸 = 盘面/帧的**逻辑尺寸 × dpr**，见 §4.2-4 的物理像素坑）
  ⇒ 用**现役 `Canvas2DRenderer`**（注入同一个 `createTintBlitResolver(tintCache, maskSource)`）把 `RenderModel` 画进去
  ⇒ 把该 canvas 上传成一张 `Texture2D` ⇒ Cocos 侧只贴这一张（1 个图元）。Cocos 的 UI/HUD 仍走原 `Graphics` 宿主不变。
- **为什么它与 harness「逐字同源」**：三件都在同一份镜像里（F-7）且 `bake-surface-impl.ts:107` 已在 Cocos 工程内
  跑过 `new Canvas2DRenderer(ctx, viewport, {...})` ⇒ 差异**只剩 ctx 来源与上传**，绘制语义零差异。
  `TintSpriteCache` 的合成产物本来就是 `Uint8ClampedArray` + 离屏 canvas（`tint-sprite-cache.ts` 的
  `compositeTintMask` → `putImageData`），harness 画它、Cocos 也画它 ⇒ **同一个函数、同一份字节**。
- **必须诚实写的代价**：
  1. **每帧（脏帧）一次 canvas→GPU 上传**。缓解 = 脏帧策略（沿用 `ADR-0025` 的缓存语义与 harness 的
     `showDirtyBead` 口径），但**上传字节与填充耗时全部 `[待实测]`**。
  2. **zoom 二难**（本方案最硬的结构性张力）：若"缓存纹理 + 靠 `transformHost` 的节点缩放放大" ⇒ **违 §19「⛔ 运行时放大」**
     且放弃矢量臂最大优点（zoom 天然锐利，`ADR-0017`）；若"每帧按当前变换重画 canvas" ⇒ 保锐利、保同源，
     但**每帧必上传**。**本单裁 = 后者**（保锐利优先，同源是诉求本体），代价登记为 §4.2-1 并交 S2 取数。
  3. 小盘面/空盘面时满幅纹理是纯浪费 ⇒ carrier 必须按盘面 bounding box 定尺寸，⛔ 不得钉视口尺寸（DEC-5）。
- **未验证引擎面（新增，须 S2 实测）**：① Cocos 宿主内可得的**离屏 2D canvas**（`wx.createCanvas()` 在 Cocos
  wechatgame 目标下的适配行为 / 是否存在 DOM shim，⛔ 不得由 web-mobile 浏览器档外推）；② **canvas → `Texture2D`
  的运行时上传 API 与逐帧更新成本**（F-9：本仓零实测，F-10：取证面无覆盖）。

### 2.3 甲′｜按色图集 + Sprite 池（`ADR-0029 §9` 已采纳的载体形态）

- **做法**：`TintSpriteCache` 的 `(maskId, tint) → 合成图` 直接喂进一张**按色图集**（≈色数 7 张 128² = 458 KB），
  每珠是一个引用图集子帧的 `Sprite` ⇒ draw call ≈ 色数（同材质同纹理合批）。
- **优势**：显存有界且小；层级 = 1；与 §9 的既有裁定同向；**合成字节仍与 harness 同源**（吃同一个 `compositeTintMask` 产物），
  一致性仅次于丙′。
- **劣势（为何不作本批主选）**：
  1. **观感一致性要靠一次新的对拍才能成立**，中间多了一段**宿主专有链路**：`SpriteFrame` 的 UV/Trim、
     节点尺寸与 blit 矩形 `x/y/w/h` 的**半像素对齐**、纹理 filter/wrap、以及**朝向**——`ADR-0029 §8.5` 教训 2
     已证「blit 翻转与帧级翻转相抵 ⇒ flip=0 才对」是**A/B 实测**结论，Cocos 侧 sprite 通道必须**重新 A/B**，
     ⛔ 不得由 canvas2d 结论外推（`tint-mask-sprite.ts` 的 `@property` 形态不涉 flip，无法直接沿用）。
  2. **运行时 `SpriteFrame`/图集构造 = 本仓零实测**（F-9）；且 `tint-mask-sprite.ts` 记录过
     「材质实例 effect layout 不热刷新 ⇒ `illegal property name`」这类编辑器侧坑（Spike 期已踩，落码期仍在）。
  3. 逐珠节点面回来 = **打破 F-1 的单 Graphics 现状**，CPU transform/动画成本回升（`ADR-0022 §2.1` 对甲的第 1 条批评，
     合批后减轻但未消失）。
  4. `ADR-0029 §1.2` 载体代价表列 Sprite 池 = **841 draw call**（逐珠）；甲′ 靠按色合批把它压到 ≈色数，
     但**该压缩在 Cocos 里未实测**（`ADR-0022 §7 D6` 判据至今未跑）⇒ `[待实测]`。
- **归属**：**S6 换代首选**（当 S2 读数证明丙′ 的上传/填充不可接受时接管）。

### 2.4 乙｜整盘单 quad + shader 内按格采样 mask

- **做法**：承 `spike/bead-field-host.ts` 的**载体②已实测形态**（独立 `Graphics` 节点 + 一枚满幅 rect，
  `gfx.customMaterial`，`?spike=1` 默认关，`ADR-0022 §11.3-2`），在 `bead-field.effect` 里新增：
  盘面索引纹理（一格一纹素 RGBA8，运行时上传，29×29×4 = 3.4 KB/帧上限）+ **mask 纹理（128²）**，
  片元按「像素 → 格 → 局部 UV」采样 mask 并按 `ADR-0028 §2.1` 编码做 `rgb = base·d + (1−base)·l`。
- **优势（事实性）**：真机成本最省的一条——`ADR-0022 §11.2 D5` **已实测** = 整盘 10×10 珠 ⇒ **+1 draw call / +2 三角**
  （对局态基线 8/666 → 9/668），而叠层矢量臂实测 **21917 三角/帧**（`§11.3-5`）。α 叠层归零、任意 zoom 天然解析锐利。
  且 spike 已把「`.effect` 导入→编译→挂载→出图」这条链路走通（D3/D4 全绿，`glGetError()=0`）。
- **劣势（为何不作本批主选）**：
  1. **它与用户诉求本体不同向**：这是**第三套实现**（GPU 重解释观感）。harness 无法与之逐像素对齐
     （`ADR-0022 §8.2` 的三层验收体系正是为此设计的）⇒ 用户要的「同绘制逻辑」只能退化成「同观感近似」，
     且需美术逐档复评（`ADR-0028 §2.3` 戊分支「单 pass shader」至今未过 art 评审）。
  2. **Fill Rate 账本未翻篇**：`ADR-0022 §11` 的结论是「**赢在层数，不是赢在像素数**」——整盘 quad 的三角数
     从 21917 降到 2，但成本单位变成**屏幕覆盖面积 ≈43.5 万片元**；小盘面/空盘面用满幅 quad 反而浪费
     （同 DEC-5 的批评，对乙同样成立）。低端 TBDR 上 `discard` 破坏 early rejection（**P-4**，已钉「用 α=0 不用 discard」）。
  3. **Uniform 预算红线（P-1/P-2）与本仓历史教训**：GLSL ES 100 只保证 16 个 `vec4`，而引擎内建块实测已吃 **50+**
     ⇒ 色板**必须**走纹理通道（本设计已如此），且 D7 只在桌面取到 1024（`[E]`），**真机分母未测**。
  4. **precision（P-5）与 sRGB（P-6）**：`highp` 非普适 ⇒ 必须传格内局部坐标；
     ⚠ 即便不走 shader，**P-6 的色彩空间口径对丙′/甲′ 同样适用**（纹理采样与 `Graphics` 顶点色的 sRGB 路径不同源，
     实测 v2「四色明显发闷」是 `[E]` 现象、成因为 `[R]` 待证）⇒ 取色实算校准是**三条候选共同**的必交判据。
  5. 载体改动面大：`.effect` 归 L1 管辖（编辑器产 `.meta`）、`bindings.ts` 未验证面扩大、验收体系永久双轨
     （`ADR-0022 §4.2-1/2`：双轨 + 像素等价作废）。
- **归属**：**终局性能路线**（`ADR-0022 §3-1` 的原文地位不变），触发条件 = S2 真机数据 + `ADR-0022 §3-2` 的 G1/G2 双门禁。

### 2.5 四路对比表

| 维度 | 丁 carrier 抽象 | **丙′ 同源 canvas** | 甲′ 按色图集 Sprite 池 | 乙 整盘 quad + shader 采样 |

## 3. 决定（Decision）

> 编号 DEC-1…DEC-10，沿用 `ADR-0029` 写法。**本批只裁方向与门禁，不落任何实现。**

1. **DEC-1｜采纳 丙′（同源 Canvas2D 帧通道）为 Cocos 生产通道的 tint/blit 载体**，形态 =
   「`Canvas2DRenderer` 在 Cocos 宿主内产帧 → 上传一张纹理 → Cocos 显示」。理由 = §0 三条支撑。
   ⛔ 本决定**不推翻** `ADR-0029 §9`（§9 裁的是 tint 合成产物进 GPU 的载体形态，丙′ 不在其射程，见 §1.3）。
   ⚠ **2026-10-05 用户裁定：本条暂不生效**——先跑 **S0 性能评估**（§5.0）产出三候选的量级对比与丙′ 的单点故障二值结论，
   再回来看「是否与 harness 同源」值不值这个成本。本节保留为**候选推荐**，⛔ 不得当已裁开工。
   ⚠ **2026-10-06 S0 第 2 步已出数**：[E] 档读数是「丙′ CPU/GPU 最优、但每帧 5.75 MiB 上传，且采纳门禁（wx 离屏 canvas）未过」
   ⇒ **数据侧推荐已改为 甲′ 主选**（§5.0.1）。本条 DEC-1 的「采纳 丙′」与 §5.0.1 推荐**不一致时以 §5.0.1 为准**，
   但两者都**不是裁定**——改裁仍归用户/主理人（§7 Q1）。
   ✅ **2026-10-05 第十一刀：本条已改裁 = 采纳 甲′（按色图集 + Sprite 池），且实施形态 = 甲″ 三层**（静态底图 / 动态珠层 / UI 层）。
   裁定理由（逐条对应本单实测）：① 甲′ **零未证平台能力**（丙′ 押的 `S0-1` 二值门至今未过，⛔ 不得拿桌面档外推）；
   ② `[E]` 档甲′ CPU 1/3、tris 1/11、**零每帧上传**；③ 甲″ 分层上界已数（§5.0.3）：`dc 15 → 2`；④ 地基已清（§5.0.2 门控 + §5.0.4 `fx` 入门 ⇒ 甲′ 静置期 tick **0.40 ms**）。
   **三条伴随义务**（裁定本体的一部分，⛔ 不得只拿好处）：
   **(i)** 观感一致性 = **同字节产物 + 一次新的 Cocos sprite A/B**（UV/Trim、半像素对齐、filter/wrap、**朝向 flip**），
   判据 = S3 两端同帧对拍（原为「可选」⇒ 现为**必做**）；**(ii)** ⛔ 不得把非珠层每帧全量重放带进生产（否则等于白拿 13 dc）；
   **(iii)** 280 个 `Sprite` 节点的内存与遍历成本需进 `[R]` 低端机预读项。原「采纳 丙′」文本与理由段**原样保留**作决策改道证据。
   ⛔ 丙′ 未出局：若日后 `S0-1` 二值门过且移动端上传实测可接受，可凭 §5.0.1/§5.0.4 数据重开（本单推荐序的「第二候选」地位不变）。
2. **DEC-2｜S1 先落 carrier 抽象（丁）**，且**它必须先于任何载体实现**：`CocosRendererOptions` 增一条宿主注入的
   blit carrier 槽（结构类型，⛔ 不 import `cc`、不进 core、不进框架 barrel）；`case 'blit'` 改为
   「有 carrier ⇒ 交出；无 carrier ⇒ 与今日 warn-skip **逐字节等价**」。
   ⛔ 效果语义仍全在注入的 resolver 里（`ADR-0029 §8.1/§8.2` 收口不动，core 零改动）。
3. **DEC-3｜同源 = 同代码，不是同规格**。允许作为「同源」证据的只有：
   同一 `Canvas2DRenderer` 实例类、同一 `createTintBlitResolver`、同一 `TintSpriteCache`、同一 `compositeTintMask`、
   同一 `computeMaskField`。⛔ 禁止在 Cocos 侧写第二套合成公式（含「看起来等价」的 shader 近似）。
   ⛔ 禁止 `globalCompositeOperation: multiply/screen` 外推真机（**X5**，`wxg-t-228:81` 原话）。
4. **DEC-4｜mask 来源 = 主包内 PNG 资产（2026-10-05 用户裁定，推翻本单初稿推荐的「运行时程序化」）**：
   「mask 从主包里来，以后要变更皮肤时用增量包替换这个 mask 纹理，换肤功能之后再实现」。
   - **包体实测**（`pnpm run check:size`，2026-10-05）：beads 主包 = **2866.8 KB / 32 文件**（gzip 1334.6 KB）
     ⇒ 距**平台红线** 4096 KB 余 **1229 KB**；⚠ **已超内部目标** 2000 KB（超出 866.8 KB），守卫只 WARN 不阻断
     ⇒ 「位图很小所以无所谓」是错话：19 KB 相对红线可忽略，相对内部目标是**在已超标之上再加**。
   - **资产实测**：4 张 128² mask = `bead-hole` 8,750 B + `bead-holeless` 4,210 B + `grid-hole` 3,395 B + `grid-holeless` 2,872 B
     = **19.2 KB**；`cocos/assets/textures` **未标 bundle**（`textures.meta` = directory importer、`userData` 空）
     ⇒ 构建落 `assets/main` **计入主包** = 正是用户要的形态。
   - **档位规范（2026-10-05 用户裁定，决策 II 因此关闭）**：`MASK_CANONICAL_SIZE = 128` 为**唯一投放档**，
     规范尺 = `BEAD_CELL 30 × zoom 2.0 × dpr 2 = 120 ≤ 128`（在册算术，`tuning.ts:316`；安全包络 `zoom × dpr ≤ 4.27`）
     ⇒ **不特别做 dpr3 资源**（不加投 256²）；dpr3 真机高 zoom 段的 1.41× 放大如何处理 → **已裁 (A)**（见 §7.1）。
   - **(A) 的落地账**：`TINT_LOD_MAX_UPSCALE` **保持 `null` = 零代码改动**（现状即此），且回退**机制与单测没有删**
     ⇒ 「之后有问题再调整」的阀门保留（填 `1.0` 即恢复回退，无需重写）。⛔ 代价 = **§19 例外须登记**（附录 A 文案）
     与 **`tuning.ts:310`「不靠『显式豁免』绕过」一句在本裁定下语义反转** ⇒ 列为 **S1 顺带更正项**（含镜像副本同步，⛔ 不在本批动代码）。
   - **`computeMaskField` 不删，只挪到构建期**：它仍是 mask **正本的产地**（py↔TS `mask:diff` 逐字节对拍），
     从「运行时现算」改为「烘进仓内 PNG」⇒ 免掉冷启动 CPU 成本，换来包体增量与 §5.1 例外登记义务。
   - **换肤/增量替换的前置（长期诉求）**：要把 mask 整包可替换，须将 `textures` 目录**改为 bundle**
     （编辑器勾选 → 构建产分包，运行期 `assetManager.loadBundle`）；⛔ 目录标记与 `.meta` 由编辑器生成（L1 禁手编/禁脚本伪造）
     ⇒ 这是一次**编辑器动作**，不是代码活；微信口径 = 主包 ≤4 MB 且主包+分包 ≤30 MB。当前 `game.json` **无 `subpackages`** 字段（零分包现状）。
   - **本裁定触发的门禁（不可跳）**：投放位图 = 命中 `control-manifest §19` 硬前置 ⇒ 须先过 `TC-TINT-18`
     （V-9：先证包体守卫**能红**）且 `verify` 带 `--strict`；未过则该腿禁止开工。
     另需一笔文档回写：`architecture.md §5.1`「首屏 0 图片」是刻意锚，**本裁定主动突破它**
     ⇒ 必须登记例外（首屏唯一位图 = 四张 mask），⛔ 不得留作隐性漂移。
   - **现状缺件**：`bead-hole`/`grid-hole` 已有 `.meta`；两张 `holeless` 的 PNG 本会话已拷入正本（sha256 与
     `tools/mask-preview/cocos-assets/` 逐字节一致），**`.meta` 待编辑器导入** ⇒ 这是 (b) 路线今天唯一真阻塞（一次编辑器动作可解）。
5. **DEC-5｜carrier 纹理尺寸 = 「可见区 ∩ 盘面 bbox」× dpr**（2026-10-05 补严：初稿只写 bbox × dpr，
   在 zoom > fit 时会多出一倍白画的像素）。实测锚：`BEAD_PITCH=32 / BEAD_GAP=2`、视口带 = 702×512 设计 px
   （`DESIGN_W` 750 − 2×`BOARD_FIT_MARGIN` 24 × `PUZZLE_BAND` 高 560−48），`CAMERA_ZOOM ∈ [0.2, 2.0]`，fit 档 `min(1, fitW, fitH)`
   ⇒ 典型盘 fit 时纹理 ≈ 446×414×3 = **6.6 MiB**，zoom 顶到 2.0 时被视口 clip 钉住 ≈ 702×512×3 = **12.9 MiB**（均 = RGBA 4 B/px）。
   尺寸变更走脏标记，⛔ 每帧重新分配（§2 热路径零分配）。**这组字节数是 S0 的核心待验成本。**
6. **DEC-6｜zoom 口径：每帧按当前变换重量绘 canvas，⛔ 不得用「节点缩放一张已上传纹理」代替**。
   这是 DEC-1 的**强制伴随条款**（否则违 §19「⛔ 运行时放大」并放弃 `ADR-0017` 的锐利性）。
   代价 = 每帧上传 ⇒ 由 S2 取数、S6 裁是否换代。允许的安全优化只有「**空闲帧不重画不上传**」（脏帧），
   ⛔ 不允许「降分辨率合成后放大」（**D2**，仍撞 §19）。
7. **DEC-7｜新宿主必须与输入侧同口径**（在案判例：渲染 SHOW_ALL vs 输入 contain ⇒ 真机点击偏移）。
   三条硬约束：① 适配策略与 `viewport.fit` 同源；② 归一化 ÷dpr + 翻 y，dpr 取 `screen.devicePixelRatio`
   （`control-manifest §17`、`bindings.ts:257–267`）；③ **离屏 canvas 尺寸 = 物理像素，但 blit 矩形按逻辑尺寸**
   （微信生态坑：不显式指定逻辑尺寸 ⇒ 整图放大 dpr 倍发糊）。渲染与命中必须同出 `gridLayoutFor`（**K-054**）。
8. **DEC-8｜朝向/滤镜/色彩空间一律 A/B 实测，⛔ 不接受推理**（`ADR-0029 §8.5` 方法论铁律）。
   必测三件：① 纹理上传后的 **flip 方向**（不得沿用 canvas2d 的 flip=0 结论）；
   ② 纹理采样 filter（线性 vs 最近）与 128² 档位在真机 dpr 下的放大率（**D5/D6**，`TINT_LOD_MAX_UPSCALE` 现值 `null`）；
   ③ **取色实算校准**（sRGB 发闷，P-6）：取样点色值与 harness 同点位 ΔE 落表。
9. **DEC-9｜「真机帧时间与显存」从采纳门禁改为换代门禁（正面回应 `ADR-0029 §0`）**。
   说明（不含糊）：丙′ 的**采纳依据**是一致性（DEC-3）、复用面（F-7）、回退成本（§6）与包体零增量（DEC-4）——
   **四条都不依赖真机性能数据**；真机数据只决定「**是否换成更省的载体**」⇒ 因此把它写成 **S6 换代触发器**。
   ⚠ 边界条件（必须守住才成立）：**丙′ 在 S2 读数出来前，不得成为默认开**——按 `ADR-0022 §8.1` 判例走
   呈现层开关、**默认关**，关 = 与今日逐字节等价。故本决定的实际交付是「一条可用的同源通道 + 取数批」，
   不是「真机默认换皮」。
10. **DEC-10｜L1–L5 落位继承 `ADR-0022 §8.1` 那张表，逐字不改**：触 `cc` 的宿主代码只住
    `games/beads/cocos/assets/scripts/`（与 `bindings.ts` 平级新文件，属 **Q2 之 (b)**，本单沿用）、
    ⛔ 不进 framework 镜像、⛔ 不进框架 barrel、被 Node typecheck 排除（由 `cocos:check` 覆盖）；
    数据契约用纯函数保 `[N]` 可测；材质/纹理一律代码创建，⛔ 不做 `.material`/`.spriteFrame` 资产挂场景。

## 4. 后果

### 4.1 正面

1. **真机第一次有与 dev 通道同源的珠子质感**，且「两端不一致」这类问题的**产生条件被消除**
   （不是被对齐，是不再有两套实现）。
2. **`harness` 恢复为真机的可信预览**。这是本单最大的架构收益：`architecture.md §2` 说 canvas2d 适配器
   「不是玩具，它是这套架构的证明」；此前它只是**逻辑**证明，同源通道让它第一次成为**像素**证明。
3. **撤销 `ADR-0022 §4.2-2` 的放弃**：在 tint 臂射程内把「两路径逐像素等价」契约买回来，
   历史「两路径一致」隐性契约**不需要作废登记**（乙 路线则必须作废，这是丙′ 的实质优势）。
4. **引擎价值判断被反向验证**：Cocos 退化为「一张纹理的显示器」——框架侧改动为 0（除 DEC-2 那一条缝），
   与 ADR-0002/0003 的引擎解耦方向**同向**。
5. **包体零增量**（DEC-4）+ **§19 与 `.meta` 阻塞解耦**（F-5）。
6. 低端机 shader 专属坑（P-1/P-2 uniform 预算、P-3 首帧编译、P-5 mediump 格索引）**在本路线上不存在**；
   ⚠ 但 P-4（fill/TBDR）与 P-6（sRGB）**不适用≠已解决**，见 4.2-5。

### 4.2 负面（诚实记录，⛔ 不许删）

1. **每帧一次 canvas→GPU 上传 + 一次 CPU 2D 填充**是本方案的结构成本。`[待实测]`；
   若不可接受 ⇒ S6 换代（甲′/乙）。**这条是本 ADR 最大的未知**，DEC-9 的降级处理只是让它不阻塞开工，
   ⛔ 不是让它消失。
2. **新增两个未验证引擎面**（§2.2 末）：离屏 2D canvas 在 Cocos wechatgame 下的可得性、canvas→`Texture2D` 上传。
   ⛔ **不得由 web-mobile 浏览器档（有 DOM shim）外推为 wx 可用**（`ADR-0028 T2'` 纪律原话）。
   若任一不通 ⇒ 丙′ 直接不可行，S6 提前触发。**这是本方案的单点故障**，必须在 S2 第一批验。
3. **Cocos 侧渲染不再走引擎的 2D 合批/裁剪体系**：满幅纹理覆盖区域与 UI 层的叠放次序需要盯住
   （P-7 合批顺序教训的镜像形态：层级每穿插一次多一次批次切换）。
4. **显存新增一帧满幅 RGBA**：按 DEC-5 的 clip 口径 = **dpr3 档 6.6 MiB（fit）－12.9 MiB（满 zoom）**（原稿只写「待实测」，本批把字节数算出来了），
   与 `TintSpriteCache` 的 2.5 MiB 预算**叠加**计账，⛔ 不得只报缓存侧数字。**量级上它比 `ADR-0029 §9` 否掉的「整盘单图元 55 MB」小一个数量级，
   但不是零** ⇒ 这是 S0 必测项，⛔ 不得拿「比 55 MB 小」当达标证据。
5. **验收体系新增一条对拍轨**（S3），且必须防「fake ctx 宽松导致测试全绿而真产出为零」这类
   已踩过的假绿谱系（`ADR-0029 §8.5` 教训 1）⇒ 判据必须打在**真实像素**上，不是打在 mock 调用计数上。
6. **同源通道会让 canvas2d 适配器成为生产依赖**：过去它是「无编辑器时的逃生路径」，
   现在它进了主包关键路径 ⇒ 它的任何行为变化同时影响 dev 与真机。**风险从「两路不一致」换成「单点影响面扩大」**。
7. `bindings.ts`/宿主层**未验证面继续扩大**（该文件头注自认 UNVERIFIED，需 3.8 编辑器才能编译验证；
   `ADR-0012` 的 ES5 展开语法契约对它是**手工自查**，守卫扫描不覆盖）。
8. 冷启动代价：`computeMaskField` 走 512² 超采样 + 两遍 LANCZOS ⇒ 首帧/加载页 CPU 成本 `[待实测]`，
   口径归宿主 HUD（**D8**：预热 N 条 / X ms）。
9. **矢量臂永久双轨**：S1 的「carrier 缺省 = 今日逐字节」是回归保护的地基，但也意味着
   `bead-render.test` 的 12 命令序列回归锁**原样保留、不为 tint 改写**（`ADR-0022 §8.2` 末判例）。
10. **`[R]` 真机腿仍被环境阻塞**（F-11）：S2 的桌面档只能证「可行与量级」，
    不能证「低端机可接受」。⛔ S2 桌面绿 **不得**被写成「真机通过」（K-037/K-054）。

## 5. 实施路线（S1…S6）


### 5.0 S0｜性能评估先行批（2026-10-05 用户裁定新增，⛔ 前置于 DEC-1）

用户口径：「**Cocos 生产通道的 blit 载体先评估方案的性能后再决定是否与 harness 同源**」⇒ 载体裁定**押到 S0 出数之后**。
S0 的定位不是「测一下丙′ 快不快」，而是**给三个候选同口径的量级对照**，并且**先用二值试验砍掉不可能**。

**纸面账（本单已可算，无需实测；实测只用来验这些算术在真机上是否成立）**：

| 候选 | 一次性成本 | **每脏帧**成本 | 相对今日矢量臂 |
|---|---|---|---|
| 今日基线（矢量臂） | 0 | ≈ **2031 条命令**在单枚 `cc.Graphics` 上**每帧 `clear()` 全量重放**（`cocos-renderer.ts:137–139`）；实锚 = **12 命令/珠 · 4 真 α 混合层 · 21917 三角/帧**（`ADR-0022 §1.1`、`§11.3-5`） | — |
| **丙′** 同源帧通道 | 离屏 canvas 常备 | **整幅纹理上传 = 可见区 × dpr** ⇒ dpr3 档 **6.6 MiB（fit）～12.9 MiB（zoom 2.0 clip）** ≈ **0.4–0.8 GiB/s @60fps**，外加一次 CPU 2D 填充 | ⚠ **不是「省掉命令重放」**（本单初稿此处不准确，2026-10-05 更正）：命令**条数**确实大降 —— tint 臂把 12 命令/珠压成 **1 条 `blit`**（`bead-render.ts:779`；格面同理 `:995` 直接 return），但**重放这件事照样发生**，只是执行者由 `cc.Graphics` 换成 Canvas2D。真实收益在 **GPU 侧**：21917 三角 → **2**、屏幕 α 混合 4 层 → **1 层**（⚠ blit 带透明边则仍算 α 层，**收益上限 = 1**，`ADR-0022 §2.4` 原话）。**净增项只有「每帧上传」这一笔**；`TintSpriteCache` 已保证合成不逐帧重算（40 条 LRU / 2.5 MiB） |
| **甲′** 按色图集 + Sprite 池 | 图集 ≈ **458 KB**（≈色数 7 × 128²） | **0 上传**；draw call ≈ 色数（≤7） | 命令条数**真归零**（每帧只动节点变换）；但三角数 = 2×珠数（非 2）、珠间重叠的 α 混合照旧 ⇒ **治 H-CPU 更彻底，治 H-FILL 不如丙′/乙** |
| **乙** 整盘 quad + shader 按格采样 | mask 128²（16–64 KB） | **0 上传**；draw call = **1** | 两侧都治（0 命令 + 1 层不混合 + 2 三角），最省；但是**第二套实现**（观感需重新 A/B），且不满足「同绘制逻辑」的诉求本体 |

4. **两个无判别力的读数（如实登记）**：开档 `draw p50` 反而更高（5.2–7.3）——样本只剩 2–3 帧，⛔ 不得与关档 3.0–3.9 比大小；
   `frame p50` 三档恒 ≈16.6–16.8 ms（vsync 锁定）。判收益只看 `tick p50` 与 `drawn`。
5. **截图差分不归因为缺陷**：开/关两档 0.25–0.34% 非零像素，全部落在 HUD 计时文本 + 托盘三小簇（盘面中段逐像素为 0）；
   控制对照（门控**前**的截图 vs 今日两档）差异同带且同量级 ⇒ = 运行间自然漂移（抽珠 RNG + 计时），**非陈旧帧**。

**对载体选型的影响**：门控先吃掉了三臂静置期的**无效重放**（V 不再白烧 3 ms、C 不再白传 6 MB/帧）
⇒ 换臂的**增量收益需按「门控后」重算**；§5.0.1 里「V ↔ C/A 混有换模型收益」的干扰降低一档，**C ↔ A 的纯载体对比此时才干净**；
但 **DEC-1 的裁定面不变**（丙′ 的 `S0-1` 二值门仍未过、每帧上传量级仍未在移动端得到验证）⇒ 回 `§7 Q1` 时推荐序仍为「主选 甲′、丙′ 第二候选」。

### 5.0.3 甲″ 分层上界实测（2026-10-05 · WXG-T-249 · 用户择 (A)「开 甲″ 三层工程单」）

> **定位**：本批**零生产改动**。`DEC-1` 未裁 ⇒ 实装面限于 `?bench=1` 取证面（一个开关 + 一行分支），
> 目的是把「甲″ 三层到底能省多少」先钉住，而不是先接线。⛔ 分层的生产接线仍属裁后的 S1/S2。

**机制（一句话）**：`carrier-bench` 新增 `--layers=full,beads` 维度（仅对 `atlas` 臂有意义）：`full` = 在册 甲′（珠面走 Sprite 池，
非 blit 命令照旧每帧喂 `cc.Graphics` + `Label` 池）；`beads` = **非珠层整体不提交**。
⚠ 为什么必须**关组件**而不是「不喂命令」：`CocosRenderModelRenderer.draw()` 里才做 `g.clear()`，不喂只会让上一帧内容继续提交
⇒ 读数就成了「冻住的矢量层」而非上界。两处显隐共用 `_syncLayers()`（⛔ 两处各写一遍必漂）。

**静置档实测**（`[E]` Apple M4 · dpr2 · 824×1830 · frames=150 warmup=40 · gate=on · 证据 `carrier-bench/layers-ab/`）：

| zoom | layers | dc | tris | draw p50 | GPU p50 | tick p50 | drawn | chg |

|0.6|full|15|3354|1.00|2.15|1.40|**150**|4|
|0.6|beads|**2**|**740**|**0.10**|**0.81**|0.90|**150**|4|
|1.0|full|15|3354|0.90|2.17|1.30|**150**|3|

**读数结论（五条）**：

1. **甲″ 三层的收益真实且大**（上界 = 非珠层完全不提交）：`dc 15 → 2`、tris 3354 → **740**（−78%）、
   draw CPU 0.9–1.0 → **0.10 ms**（−90%）、GPU 2.15–2.26 → **0.42–0.81 ms**（−63～−81%）。
   ⇒ 非珠层（静态底图 + HUD 矢量）在甲′ 里占了 **13 个 dc + ≈0.8 ms CPU + 1.3–1.8 ms GPU**，而且**三档 zoom 恒定**（与内容无关）。
   这一刀零平台押注（纯节点树形态），**值得从「推荐项 4 的一句话」升格为可实装形态**。
2. **归因更正（§5.0.1 结论 7）**：`dc 16/15` 不是「`Sprite` 与 `cc.Graphics` 交错 ⇒ 合批被打断」，而是**相加**：
   非珠层 13 + 珠池 **2**（280 个 Sprite 自己就合成了 2 批 ⇒ 图集/合批已在本档得到实证，`ADR-0022 D6` 的怀疑桌面部分可销）。
   所以待修项不是「避免打断」，而是「**别让非珠层每帧全量重放**」。
3. 🔴 **本批最重的意外读数 = 脏帧门控对含 `blit` 的模型恒判脏**：两档 `drawn` 都 = **150/150**，而 `chg` 只 3–4。
   成因是 `render-model.ts:500` 的在册规则（含 blit ⇒ 掺 `_frameSeq`，**宁多画不漏画**）与其旁 `ponytail:` 注释登记的理由
   （「它们的成本在上传不在重放 ⇒ 损失小」）——**该理由本批被实测推翻**：甲′ 的 `onRender` 一旦进珠池分支，
   非珠层 13 dc + 0.9 ms CPU 照样每帧重放 ⇒ **甲′/丙′ 目前完全拿不到 §5.0.2 的门控收益**。
   ⇒ 下一口最小收益单 = `signature()` 逐键走 `fx`（blit 可判脏），收益上限就是本表 `beads` 那行（静置期 0.1 ms）。
   可行前提（已核）：blit 身份字段（`textureId` 等）本就是字符串、已被现有 `for...in` 混入，缺的只是 `fx` 这一层对象（当前只混 number/string ⇒ 对象被跳过）。
   ✅ **本条已于同日由 WXG-T-250 关闭**（`fx` 逐键入门 ⇒ 恒判脏规则删除），实测读数见 **§5.0.4**；本表旧行（`drawn=150`）保不动，它是「修前」那一侧的对照。
4. **抖动如实登记**：本次 `full` 档 `dc = 15`，§5.0.1 那次 A 臂 = 16 ⇒ 差 1 批（节点态/Label 属件抖动）；⛔ 不得据此说「改动生效」。
5. **档位与形态限制**：本组全部 `[E]`（⛔ 不是低端机达线证据）；`beads` 档**画面不完整**（底图/HUD 均消失，截图已存）
   ⇒ 它只给**上界**，⛔ 不得当作「可 shipped 形态的性能证明」。

**对载体选型的影响**：`DEC-1` 若改裁 甲′，实施面应按 **甲″ 三层**写（静态底图烘一次 1 quad / 动态珠层 = Sprite 池 / UI 层仅脏帧重放），
否则等于把 13 dc 的非珠层重放直接带进生产；但 **§5.0.1 的推荐序不变**（甲′ 主选 / 丙′ 第二候选），
且新增一条硬前置：**blit 可判脏之前，门控对 C/A 两臂无效**（✅ 该前置已由 **WXG-T-250 / §5.0.4** 满足）。

**未证项（下一刀需补的数）**：非珠层里「**静态底图**」与「**真 HUD**」各占多少（本批只给了合并上界）
⇒ 需第三档（只烘底图、UI 照旧重放）才能定甲″ 的实际接线拆分比例；`[R]` 低端机仍未跑。


### 5.0.4 `fx` 入门：blit 帧可判脏（2026-10-05 · WXG-T-250 · 承 §5.0.3 结论 3，✅ 已落地）

> 一帧框架侧改动（`packages/framework/src/core/render/render-model.ts::signature`）+ 镜像同步。
> 它不是「第四臂」，而是把 §5.0.2 的门控收益**从只覆盖 V 臂扩展到覆盖 C/A 臂**。

**改了什么（一句话）**：字段遍历由「只混 number/string」改为**一个递归 `mixVal`**（number/string/boolean/对象与数组按插入序逐键走），
同时删除 `_frameSeq` 与 `if (hasBlit) mix(this._frameSeq)` ⇒ **含 blit 的帧不再恒判脏**。
为何合法：`BlitFx` 的值域本就是 JSON 安全的封闭联合（`string | number | boolean | readonly number[]`），
且键序由构造方固定（类型文档规则 4）⇒ 与「命令字段按插入序混」同一口径，无需逐键名 switch。

**静置档实测**（`[E]` Apple M4 · dpr2 · frames=150 warmup=40 · gate=on · zoom 1.0 · 证据 `carrier-bench/gate-blit-ab{,-disturb}/`）：

| 臂 | 修前 `drawn` | **修后 `drawn`** | 修前 tick p50 | **修后 tick p50** | dc | tris | 上传 B/帧 |
|---|---|---|---|---|---|---|---|
| V 矢量（无 blit，**对照组**） | 2–3 | **3** | 1.30 | 1.30 | 14 | 38194 | 0 |
| C 丙′ | **150** | **3** | — | **0.40** | 2 | 182 | 6,031,680（仅 3 帧） |
| A 甲′ `full` | **150** | **2** | 1.30 | **0.40** | 15 | 3354 | 0 |
| A 甲′ `beads`（上界档） | **150** | **2** | 0.90 | **0.40** | 2 | 740 | 0 |

**五条结论**：

1. **§5.0.3 结论 3 的缺口已堵**：丙′/甲′ 静置期从「每帧重画」降到 **2–3 帧/150**（与 V 臂同待遇）
   ⇒ 甲′ 整帧 CPU **1.30 → 0.40 ms**（−69%），且**上界档不再是纸面**：`beads` 那行的形态（非珠层不重放）现在在静置期自然成立。
2. **丙′ 的硬代价被门控砍掉 98%**：每帧 5.75 MiB 上传 → 150 帧窗口里只发生 **3 次**（≈ 18 MiB 而非 862 MiB）
   ⇒ 对「每脏帧一次满幅上传」的担忧需按此重读：风险不在静置，在**逐帧动画期**（见第 4 条）。
3. **对照组无退化**：V 臂不含 blit ⇒ 本批对它只多了一个 `typeof` 分支，tick 1.30 / dc 14 / drawn 3 与 §5.0.2 同值。
4. **最坏档（每帧都变）代价极小**：`gate-blit-ab-disturb` ⇒ tick V **5.10** / C **1.40** / A **1.40** ms，
   与 §5.0.1 的逐帧基线（V 3.0–3.9 重画 + 门控代价）同量级 ⇒ **递归走 `fx` 本身不贵**（每 blit 一个键）。
   ⚠ 但 V 本轮 5.10 vs §5.0.2 的 4.80（同档同 zoom）= **运行间漂移**，⛔ 不得归因为本批改动（V 无 blit）。
5. **无判别力的列（承 K-101）**：开档后 `draw p50`/`gpu p50` 的样本只剩 **2–3 帧**（`n=2–3`）
   ⇒ 本表只引用 `tick p50` 与 `drawn`；`draw 7.50`（V）与 `gpu 1.93`（A）**不得**与满样本档比大小。

**正确性证据（而非只靠数）**：单测两条换档——`render-model.test.ts`（同内容 blit 同指纹 / `fx` 值与数组载荷变则脏 / 有无 `fx` 不同）
与 `app.test.ts`（blit 帧四 tick 只画 1 次，改 `fx` 后必再画）；另用取证截图目测确认 `drawn=2–3` 时**画面仍完整**（盘面 128 珠 + HUD 均在）。
⚠ **新的在册上限**（已写进 `signature` 的 `ponytail:`）：指纹计的是纹理**引用**（`textureId`）而非像素 ⇒
若将来有生产者**就地重烘**同 id 的纹理内容，门控会看不见；今日两条链安全（tint：内容 = `f(textureId, fx.base)`；bake：`bake:<styleId>:<colorIdx>` 且 `BAKE_CANONICAL_SIZE` 为常量）。

**对选型的影响**：§5.0.1 推荐项 2/3 的**排序不变**（甲′ 主选 / 丙′ 第二候选），但两条账重读：
甲′ 的「不吃门控」劣势已消失；丙′ 的「每帧上传」风险从带宽总量改为**只在动画期发生**（其 `S0-1` 二值门仍未过，不得默认开）。
⛔ **`DEC-1` 本体仍待用户改裁**（`§7 Q1`）；本批只修地基，不改载体形态。

2. **层序**：L0/L1/L2 的 z 序与 Cocos 渲染顺序；现网背景是**每帧 Graphics 填色** ⇒ 归哪层（归 L0 则背景不得动；有背景动效就得回 L2）。

**几何口径（用户 2026-10-05 三刀回话后定，原话为准）**：

> 「格子合成纹理的**画布设定为 33dp**，但是 mask 图片**只是绘制 32dp 的区域、在画布居中绘制**，

  像素域 = 128² 画布里装 `round(128 × 30/33) = 116px` 内容（off 6px）⇒ **图集格零改动、零显存增量**。

  1. 呈现层开关关（默认）⇒ 不注入 resolver ⇒ **整臂 = 今日矢量**（逐字节等价，S5 判据）。
  2. mask 不可得 / `computeMaskField` 未就绪 ⇒ 白名单 `getMaskId` 返回 `undefined` ⇒ 该格走矢量臂（DEC-5）。
  3. 放大率超阈（`TINT_LOD_MAX_UPSCALE`，现值 `null` = 永不回退）⇒ `[待真机 D5]` 裁定后填值。
  4. **已命中的单条 blit 合成失败** ⇒ **跳过该条 + 负缓存**（`ADR-0029 §8.3` / **X4**）。
     ⛔ **不得**在这一步退矢量臂——那是第二套渲染路径。矢量臂的开关在**运行时注入层**（步骤 1/2），不在逐条降级层。
  5. **carrier 在 Cocos 侧不可用**（S2 验不过离屏 canvas / 上传）⇒ 撤掉宿主文件 + 关开关 ⇒ 回到 F-2 的
     warn-skip，真机 = 今日。**回滚成本 = 删 1 个宿主文件 + 1 个开关 + `bead-render` 零改动**。
- `bead-render.test` 的 12 命令序列回归锁**原样保留**（守 Graphics 路径 = 守回退阀，`ADR-0022 §8.2` 判例）。

### 7.1 zoom 三口径到底在动什么（2026-10-05 应用户「解释清楚再决定」所求）

**先说一个必须纠正的直觉**：丙′ 的纹理**不是「每颗珠一张图」**，而是**整幅盘面帧**（矢量底图 B0 + 坑沿 + 珠 blit 全画在同一张离屏 canvas 上）。
所以「zoom 时糊不糊」来自**两个互相独立的分辨率源**，Q2 的三选项只管其中第一个：

| 源 | 决定什么 | 由什么控制 |
|---|---|---|
| **源 A｜帧纹理的空间分辨率** | **矢量部分**（格缝、底图边缘、坑沿）锐不锐 | Q2 的 (a)/(b)/(c) |
| **源 B｜单颗珠的 mask 档位分辨率** | **珠子本体**锐不锐 | 投放哪一档 mask PNG（128²/256²）+ `TINT_LOD_MAX_UPSCALE` |

**源 A 三档的字节账**（实测锚：视口带 = 702×512 设计 px，`CAMERA_ZOOM ∈ [0.2, 2.0]`，fit 档典型盘 ≈ 446×414，dpr 取 3）：

| 口径 | 每帧做什么 | dpr3 上传量 | 矢量部分观感 |
|---|---|---|---|
| **(a) 每帧按当前变换重量绘** | 重绘整幅 canvas + 上传 | **6.6 MiB（fit）～12.9 MiB（zoom 2.0 被视口 clip 钉住）** ≈ 0.4–0.8 GiB/s @60fps | **全程 1:1 锐利**（与今日矢量臂同级） |
| **(b) 缩放期不重绘，停稳重量绘一次** | 手势期间只把已上传纹理按节点缩放放大 | 手势期 **0**，仅 settle 帧 1 次 | 手势期间**整幅发糊**（含底图），松手即恢复；糊的时长 = 手指按着的几百 ms |
| **(c) 常态节点缩放** | 纹理永远按 fit 烘，之后只缩放节点 | 0 | zoom > fit **全程糊**，放大率随 zoom 线性恶化；⛔ 直接违 `control-manifest §19`「运行时放大」 |

**源 B（珠子本体）—— 2026-10-05 用户已裁**：「**按 `BEAD_CELL × zoom 2 × dpr 2` 规范实现 `MASK_CANONICAL_SIZE`，小程序兼顾高低设备，不特别做 dpr3 的资源**」
⇒ **128 为唯一档，不加投 256²（决策 II 关闭）**。本单初稿把这一刀当成「待裁」，此处改登为已裁；**两套在册注释与单测早已逐字算过同一笔账**
（`tuning.ts:316–318`；`bead-tint-arm.test.ts:384–389` 钉住 `120 ≤ 128` 与 `180 > 128`）⇒ 本裁定是**把在册算术升格为规范**，不是新数值决策。
与源 A 的关系保持不变：**选 (a) 不会让珠子变锐利**（它只保住矢量底图）、**选 (b) 也不会让珠子更糊**（(b) 的代价只是底图与格缝在手势期间糊）。

⚠ **口径订正（待用户确认用词，⛔ 不改结论）**：用户原话写 `BEAD_CELL 32`，但 `32 = BEAD_PITCH`（格距），**`BEAD_CELL = 30`**（= PITCH − GAP 2）才是 blit 外框边长正本；
本档与单测一律按 **30** 记账。**两者不是学术差别**：按 30 ⇒ 安全包络 `zoom × dpr ≤ 128/30 = 4.27`（dpr2 时 zoom ≤ 2.13 ⇒ 满区间且有 **13% 余量**）；
按 32 ⇒ 包络收到 `≤ 4.0`（dpr2 时 zoom 2.0 **恰好压线 = 零余量**，取整/适配边差即翻向微放大）。⇒ 登记必须用 30。

**本裁定唯一未覆盖的事实**：「不做 dpr3 资源」是**资产决策**，管不住真机 DPR —— dpr3 机器上 `30×zoom×dpr` 照算，zoom>1.42 那段依旧发生 **1.41× 运行时放大**。
⇒ 它等价于「**接受 dpr3 高 zoom 段的放大**」，而 `tuning.ts:310` 与 `control-manifest §19` 的在册口径是「⛔ 运行时放大 ⇒ 该帧回矢量臂，**不靠显式豁免绕过**」
⇒ 两者正面冲突，曾列三选（⚠ 真机 DPR **在册零实读**（`[QA-PERF][ID]` 只有模板行），且 web 档 DPR **引擎封顶 2**（`TC-COORD-03` / `ADR-0011 §3(e)-3`），小游戏真机**无封顶**
⇒ **桌面/模拟器取证永远看不到 dpr3 这条腿**）：

**✅ 2026-10-05 用户已裁 = (A)**（「直接 (A)，之后有问题再调整」）：

| 选 | 做法 | 代价 | 附带影响 |
|---|---|---|---|
| **(A) ✅ 已裁** | `TINT_LOD_MAX_UPSCALE` 保持 `null`（= 现状）⇒ dpr3 高 zoom 段接受 1.41× 放大 | ⚠ **须登记 §19 例外**（推翻在册「不靠豁免」口径）；代价 = 糊（LANCZOS 下采样后的 128 再放大到 180） | 零资产、**零代码改动**、零回退跳变、两端仍同源 |
| **(B)** | 填 `1.0` ⇒ dpr3 机 zoom>1.42 整帧回矢量臂 | 守 §19、零新资产；⛔ **降级正好落在主判低端机**（畅享 90 Pro Max 若为 dpr3）⇒ 矢量臂 = 21917 三角 + 4 真 α 层 = **在册最重路径**（性能与观感两头都受损）；切换需滞回 | 需一次真机目测定阈值 |
| **(C)** | 降 `CAMERA_ZOOM_MAX` 2.0 → **1.4** ⇒ dpr3 全程不放大 | 根治（零资产、不违 §19、无跳变）；⛔ 属 **§3 冻结常量变更**（需 §6 变更记录 + 主理人确认），且放大倍率是**玩家功能** —— v1.59 刚从 2.5 缩到 2.0（用户知情拍板），再缩到 1.4 = **二次缩水** | 玩法面代价最大 |
| ~~(D)~~ | 加投 256² 档 | — | ⛔ **2026-10-05 用户已否**（不做 dpr3 资源） |

**(A) 生效后的三条后续义务（不代裁，但必须记账）**：
① **§19 例外登记**：文案已进附录 A；`control-manifest §19` 正本由工程单落表 ⇒ **未落表前 S5 真机接线不得默认开**（新硬门禁）。
② **DPR 实读仍必采**（§5.0 第 3 步）：用户口径是「之后有问题再调整」⇒ 调整的前提 = 知道 dpr3 真机到底占多少、糊到什么程度；
   另建议顺手用**定性口径**取一次证（同机同点 tint vs 矢量对比截图），⛔ **本仓无「放大率 ↔ 可接受度」的换算数，不得自造 JND 阈值**。
③ **本例外跟「mask 只有 128 唯一档」走，不跟载体走**：将来若 S6 裁到 甲′/乙，`BEAD_CELL × zoom × dpr > 128` 这笔账照旧成立
   ⇒ **(A) 继续适用**，⛔ 不得因为换了载体就当作已解决而重开决策 II。

**旧建议（已采）**：真机腿顺手取 DPR + 目测一瞥 —— 现在它从「定档依据」降为 **(A) 的复评依据**（S0 真机腿必采项不变）。

**S0 如何把 Q2 变成可裁的**：唯一需要实测的量 = **「上传 ms 占单帧 JS ms 的比例」**（在册 `D8b` 正是这条腿，且明文「无通过线，只登记」）。
- 该比 ≪ 1 成 ⇒ (a) 近乎免费，直接选 (a)，(b)(c) 属无谓复杂度；
- 该比占到两三成 ⇒ (b) 才第一次有意义，届时由 art 复评「手势期间底图糊」是否可接受；
- 无论哪种，**决策 II 与 Q2 无关，可同批一起裁**，省一次来回。

⛔ 三条不变（无论选哪档）：选 `(c)` 须显式豁免 §19；离屏 canvas 尺寸 = 物理像素但 blit 矩形按逻辑尺寸（DEC-7-③ 微信坑）；
渲染与命中必须同出 `gridLayoutFor`（K-054，在案真机点击偏移判例）。
