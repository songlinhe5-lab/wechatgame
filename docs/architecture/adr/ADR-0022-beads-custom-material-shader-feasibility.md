# ADR-0022 — 珠体质感改走自定义材质（fragment shader）的技术可行性：乙案「整盘单 pass」有条件采纳，本轮不落码

- **状态**：**Accepted（评估与排期裁定）** —— 本 ADR 只冻结「值不值得做、走哪条路、卡在哪、怎么判」，**不含任何实现**；实施须先过 §3 门禁与 §7 判据。
- **日期**：2026-09-25 · 执笔：程基岩（engineering-lead） · 委托：主理人直派任务单（无 WXG-T 号）
- **关联**：ADR-0005（程序化渲染，本案是其 §5 复评的「质感升级」分支）、ADR-0017（zoom LOD，红线承接）、ADR-0019（`BeadMaterial` **CPU 参数表**——与本 ADR 的 GPU material **同名不同物**，见 §1.5 消歧框）、ADR-0016（色板）、ADR-0014/0015（变换通道与「布局即相机」）、ADR-0012（ES5 语言契约）、ADR-0009（MCP 定位与 P2 修正）、ADR-0011/控制清单 §17（坐标口径）
- **证据**：`temp/beads-facet/`（本轮视觉验证实测脚本与图，gitignore 内，可引用为试验证据，不可提交）

---

## 0. 结论一句话

**值得做、但不是现在做**：三条路线里只有**乙（整盘 1 个 quad + 程序化/SDF fragment shader，GLSL ES 100 下限）**能同时兑现「质感上限」与「fill rate 下降」，甲被支配（断批 + 节点成本，质感无独占收益），丙不解决质感（烘的就是现在的平涂层）；**先手是零风险的路基甲案（CPU 高适合度风格，3–7 命令/珠、0 真 α 层）**，乙案以「编辑器进程上线 → D3–D5 Spike」+「真机证实 fill-rate 假设 → D1/D2」双门禁挂起，判据全绿前不立项目。

> **⚠️ 2026-09-25 实测回写（见 §11，效力高于本文早先文本）**：编辑器进程已上线 ⇒ G1 门禁的 D3/D4/D5 已跑完并**部分改判**——① §2.2 的「两条载体候选」不等价，**载体①（换 `cc.Graphics` 材质）已被实测否证**；② 「不依赖 `fwidth`」的保守裁定**撤销**；③ 新增**载体② 最小形态 = 独立 Graphics 节点 + 一枚满幅 rect**，实测整盘 10×10 珠 = **+1 draw call / +2 三角**（对照：真实棋盘自身 = 21917 三角）。

## 1. 上下文（Context）

### 1.1 问题

现渲染路径下珠体质感由 CPU 叠层逼近（现状九层叠珠 = **12 命令/珠、4 真 α 混合层、7 次圆角曲线展平**；一格含 B0 底图 = 13 枚，实测见 `temp/beads-facet/`）。低适合度材质（毛毡 22 命令/20 真 α 层、磨砂 16/16、夜光光晕跨格污染、珍珠虹彩因 `mix()` 只有黑-白轴而**原理上做不到**）在 CPU 路径上没有出路。问题是：**改走自定义材质（GPU shader）是否值得、怎么做、卡在哪。**

### 1.3 实测证据与两个瓶颈假设

`temp/beads-facet/` 本轮验证（脚本 `ab.mjs` / `lowcost.mjs` / `styles.mjs` + SVG 对照图）：

| 样本 | 命令/珠 | 真 α 层 | 曲线展平 |
|---|---|---|---|
| 现状九层叠珠 | 12 | 4 | 7 |
| 高适合度五风格（四棱刻面 / 18 线稿描边 / 16 明度阶梯 / 13 双色对角 / 07 复古像素） | 3–7 | **0** | 像素风 0 |
| 低适合度 11 套程序化近似（均值） | 9.9 | 6.8 | — |

由此形成两个**待真机裁判的瓶颈假设**（本 ADR 不预设结论）：

- **H-FILL（本单主判断，倾向成立）**：低端微信机的第一瓶颈是 **fill rate（α 叠层次数 × 覆盖面积）**，不是命令条数。旁证：高适合度风格命令数降 ~50% 且 α 层归零，收益里两者耦合；而 `assets-spec §1.6.9/§1.8` 的核算口径只数**图元/层级**，**系统性低估 fill rate**（α 层的每像素混合代价在 CPU 计数口径里不可见）。
- **H-CPU**：瓶颈在每帧 Graphics 重建（命令生成 + 曲线展平 + tessellation）。旁证：ADR-0017 落码记录 zoom 降层使命令 7403→5187（−30%）但**真机 FPS 未验**——降幅与帧率的因果从未被测量闭环。

**这两个假设的裁判判据（D1/D2，见 §7）同时决定乙案的立项优先级与 ADR-0005 §5 方案 C 的触发**——所以「先测再写 shader」不是拖延，是唯一能排序这笔投入的顺序。

### 1.4 约束（引用，不重开）

- **L1**：场景只 `GameRoot` + `Bootstrap`；`.scene/.prefab/.meta` 禁手编 ⇒ `.effect` 资产必须由编辑器导入产 `.meta`（ADR-0009 P1 闭环）；**不允许为试错在主工程里建测试场景**。
- **L2/L3**：shader 需求不得把 `cc` 带进 core / 玩法层。
- **L4**：禁 `Math.random()`；shader 内程序化噪声是 GPU 端像素坐标的确定函数，不触碰 JS 层 L4，但**它与 CPU 侧 `createRng` 值不通用**（见 §4.2-5）。
- **L5**：渲染不持状态 ⇒ **动画相位必须从快照派生后经通道传入 shader**，shader/材质侧不许自走时钟。
- **§8 渲染契约**：五原语 + 合并 draw call（「所有矢量图形进同一个 Graphics」）+ 热路径零分配。
- **包体**：微信主包红线 4096 KB；实际产物 2.8 MB ⇒ 余量约 1.2 MB（内部目标 v1.51 已与红线合流，缓冲消失——任何增量都要记账）。
- **零外部美术资产支柱**：ADR-0019 丁案（真实贴图）已否决，**本 ADR 不重开**；乙案的程序化纹理由运行时生成（数据来自快照），不引入资产文件，与支柱兼容。
- **ADR-0017 红线**：中心孔、符号（L5）、目标色垫（L11）属信息层，任何路线（含 shader）不得砍。

### 1.5 术语消歧框（必读，防后续会话混用）

| 词 | 所指 | 住哪 |
|---|---|---|
| **`BeadMaterial`（ADR-0019）** | **CPU 侧数值参数表**（frozen 单例，喂 `drawFilledBead` 的系数） | `games/beads/src/view/`（玩法镜像） |
| **自定义材质 / `cc.Material` / `.effect`（本 ADR）** | **GPU 侧引擎对象**（shader + uniforms 载体） | `games/beads/cocos/assets/`（工程资产）+ 宿主层代码 |

两者**同名不同物、可以共存**：若未来乙案落地，`BeadMaterial` 表**恰是 shader uniforms 的数据源**（CPU 表 → 逐帧上传），一个管"参数是什么"，一个管"参数怎么到像素"。**引用时一律写全称或加注（CPU 表 / GPU 材质），禁止裸用「材质」二字。**

## 2. 备选方案（Alternatives）

### 2.0 路基｜甲案先手：不碰 GPU，在 CPU 路径内换「高适合度风格」

- **做法**：把 `temp/beads-facet/` 已证可达的五风格（3–7 命令、0 真 α）落成默认观感 = **ADR-0019 已裁的表驱动路线（S1–S3）+ 美术选型**，工程零新面。
- **事实**：风格选型属 art 域（assets-spec / bead-visual-style-spec 管），本 ADR 只登记「这是所有质感路线里唯一**今天就有效**的收益」；虹彩/柔光/磨砂/透光类质感它**给不了**（§1.1 的低适合度名单正是它的天花板）。
- 这不是"第四条技术路线"，是**排序决策**：先吃确定性收益，再用真机数据决定要不要买 GPU 上限。

### 2.1 甲｜逐颗珠一个自定义材质实例（每珠 uniform 不同）

- **机制推演（引擎行为，标待实测）**：Cocos 3.8 的 2D 批处理按「材质 + 纹理」归批；每珠独立材质实例（不同 uniform 值）按该口径**大概率逐颗断批 ⇒ draw call 从 1 涨到 N（156~841）**。引擎对同 effect 多实例是否存在 2D 自动 instancing 合并，本会话无法验证 ⇒ 用一次性判据 **D6** 关闭此争议（见 §7）。
- **即便断批为真不成立（引擎自动合批），甲仍被乙支配**：
  1. 需要 N 个逐珠节点 + 逐珠 Sprite（打破 F-5/F-6 的单 Graphics 现状，新增整个组件面）；节点 transform/动画成本回到 CPU；
  2. **fill 成本零改善**——每珠材质内部再省，珠间 α 混合叠加照旧（柔高光跨珠重叠、光晕跨格污染一个都不少）；甲的质感收益乙全部都有，且乙是 1 draw call；
  3. 与 §8「尽量合并 draw call」铁律正面冲突（`cocos-renderer.ts` 头注的立项理由就是它）。
- **裁决：否决**（不是"难"，是"被支配"——没有任何一件甲能做而乙不能做的事）。

### 2.2 乙｜整盘一个 quad + 程序化/SDF fragment shader（推荐终态路线）

- **做法**：盘面区域由**单个**挂自定义 effect 的 2D 渲染器承载（可能载体：给 `Graphics` 直接换材质，或整盘 quad + `Sprite` 类组件换材质——**两条载体的具体组件属性可用性均 [待编辑器实测 D3]**，本单不认定任何未验证 API）；珠形、倒角、柔高光、磨砂、透光、虹彩、中心孔全部在片元里按「像素 → 格 → 局部 UV」解析计算。
- **数据通道**（L5 合规形态）：
  - **布局 uniform 只从 `gridLayoutFor` 输出生成**（渲染与命中同源——K-054/ADR-0015 教训：手写第二套坐标逆变换 = 画的不等于点的）；
  - **盘面纹理由运行时程序化生成并上传**（零资产文件）：RGBA8 · 一格一纹素，R=色板索引、G=动画相位（量化 8bit）、B=状态位（selected/hint/wrong）、A=保留。pattern 变化按脏标记局部上传；相位由快照计时器派生（同 `_liftElapsedMs` 判例），**每帧全量上传至多 29×29×4 = 3.4 KB**（成本 [待实测 D8]，备选 = 全局相位标量 + 格坐标派生偏移，多数动画可行，逐珠独立相位需纹理）；
  - 色板：10 色 ≤ 10 个 `vec4` uniform——GLSL ES 100 **保证** fragment 侧 uniform 数组可动态索引，但 `MAX_FRAGMENT_UNIFORM_VECTORS` 规范下限仅 16，**很紧**；实际低端机普遍 ≥64，D7 实测登记，装不下则色板也移进纹理。
- **为什么它同时解质感与 fill**：单 pass 无逐珠 α 叠加（4~20 层混合 → 1 层），每像素恒定成本；质感要素（连续高光、噪声、色相轴虹彩、邻格采样消光晕跨格污染）恰是 CPU 五原语做不到的。**任何 zoom 天然解析锐利**——ADR-0017 的「降层」语义在此改写为「降参数」，红线三件（中心孔/符号/目标色垫）转为 shader 的**强制输出不变式**（判据 D4 覆盖）；符号需一张程序化生成的符号子纹理（矢量符号烘进运行时图集，仍零资产文件）。
- **平台下限（必答项）**：
  - **不能赌 WebGL2**。事实链：微信小游戏 runtime 的 canvas 是否给到 `webgl2` 取决于基础库版本 × iOS/Android 系统版本，覆盖面无本仓实测 ⇒ **`[待真机实测 D7]`**；Cocos 3.8 在拿不到 WebGL2 时按 WebGL1 路径运行（引擎标准降级行为，具体到 wechat 平台的上下文申请逻辑本会话不可验证 ⇒ D3/D7 一并取证）。
  - 因此**设计下限钉死 GLSL ES 100（WebGL1）**：循环必须有常量上界（本设计**无需逐像素循环**——一格一查表绕开该约束）、无 texture array（用一维图集切片替代，本案不需要）、sampler 不可动态索引（同上，不需要）、`discard` 可用、**不依赖 `fwidth`/导数**（ES1 需扩展且跨实现不稳——AA 宽度改由「布局 uniform 里的格像素尺寸」解析给出，这是本仓自己传得起的量）。ES300 特性**只作加分项，首版不写一行依赖它的代码**。
- **代价**（详 §4.2）：验收体系换轨、per-pixel 成本无法靠 LOD 削减、全仓唯一 `cc` 文件的未验证面扩大、包体增项入账。

### 2.3 丙｜运行时烘焙（RenderTexture / 动态图集）

- **诚实定性：它不提升观感上限**——烘的就是现在这些平涂层，一像素不多。**它是性能手段不是质感手段，别当质感方案卖**（本 ADR 正式登记此语）。
- 价值域 = 降帧耗（12 命令/珠 → 1 次 blit；blit 若带透明边缘仍是 α 层，收益上限 = 层数→1）；成本域 = 纹理内存、烘焙时机、zoom 档位切换的清晰度损失（与乙的"任意缩放锐利"正相反）、动画态仍走 Graphics 双轨合成。
- **归属明确**：这是 **ADR-0005 方案 B/C 的既有领土**（其 §5 触发条件 = 真机 <30fps 且 profile 指向 Graphics 重建）。本 ADR **不重开**，只做接线：若 D2 判据裁定 **H-CPU 成立**，按 ADR-0005 §5 走升级评估（届时丙优先于乙——性能问题用性能方案，不必买质感重构）。

### 2.4 四路对比表（含路基）

| 维度 | 路基 甲案CPU换皮 | 甲 逐颗材质 | 乙 整盘单 shader | 丙 运行时烘焙 |
|---|---|---|---|---|
| draw call | 1（不变） | **1→N**（大概率断批 [待D6]） | **1** | 1（blit）+ 原 Graphics |
| 真 α 叠层/fill | 12→3–7 命令、**0 α**（高适合度款） | 珠间叠加照旧 | **单 pass ≈1 层** | 叠层→1 层 blit |
| 质感上限 | 受五原语封顶（虹彩/柔光/磨砂做不了） | =乙（但成本更高） | **上限最高**（per-pixel 任意） | **零提升**（只快不美） |
| zoom 清晰度 | 现状（矢量，天然锐） | 纹理档会糊 | 解析式，天然锐 | **放大必糊**（位图） |
| 新增引擎风险面 | 无 | Sprite+材质+节点（大） | `.effect`+材质+纹理上传（中） | RenderTexture（中） |
| 验收体系冲击 | 无（判据沿用） | 大 | **大**（像素等价失效，§8 方案） | 中 |
| 触碰铁律 | 无 | §8 合并 draw call（正面冲突） | L5/§2 需通道化设计兜住（可合规） | 无（但触发 ADR-0005 复评） |
| 结论 | **先做**（零风险先手） | **否决**（被乙支配） | **有条件采纳**（终态路线，过门禁） | 登记为性能阀（非质感方案） |

## 3. 决定（Decision）

1. **质感升级的终态路线 = 乙（整盘单 quad + 程序化/SDF shader，GLSL ES 100 下限）**；甲**否决**（被支配）；丙**仅**登记为性能阀、归属 ADR-0005，**不得**在 any 场合以质感方案名义复用。
2. **本轮不落码**。实施双门禁（AND 关系）：
   - **G1（编辑器门禁）**：编辑器进程上线 ⇒ §7 的 D3/D4/D5 Spike 全绿（一次性、时限预算建议 ≤1 个人日，超预算即记入 §4.2 复评）；
   - **G2（数据门禁）**：D1/D2 真机数据裁定 **H-FILL 成立**（若裁得 H-CPU ⇒ 按 ADR-0005 §5 走丙/方案 C，乙优先级降档，回 §5 触发条件）。
3. **先手 = 路基甲案**：高适合度五风格走 ADR-0019 已裁的表驱动通道（S1–S3）落地为默认观感——工程零新面、今天可排。风格选型裁定归 art 域，本 ADR 只冻结「工程侧已具备承载它的架构」。
4. **分层落位三条裁定**（细则见 §8）：
   - shader 代码（`.effect` + 触 `cc` 的宿主 TS）**住游戏工程宿主层、不进框架 barrel、不进 framework 镜像**；
   - **`RenderModel` 现阶段不新增第六原语、不加聚合命令**——Spike 与试点期用宿主注入的 provider 回调传盘面数据（framework 零改动）；正式通道形态（sideband 字段 vs 聚合命令）留待实施 ADR 另裁（判例：ADR-0014 的 `RenderModel.transform` 通道就是先带后裁）；
   - canvas2d harness 与 Cocos 出图**放弃逐像素等价**，换 §8.2 三层验收（数据层机检 / 参考实现 / 截图判据清单）。
5. 本 ADR 生效后，`bindings.ts` 头注 "the ONLY file in the framework that imports `cc`" 的口径需随实施核定（是扩写 bindings.ts 还是并列新宿主文件，交主理人拍，见 §10 Q2）；未落地前该文件保持唯一 cc 面不变。

## 4. 后果（Consequences）

### 4.1 正面

1. 质感与性能**同向**：乙案第一次让「更好看」与「更省 fill」是同一笔投资（单 pass 替 4~20 层混合），不再互斥。
2. 架构收敛：`BeadMaterial`（CPU 表）天然成为 uniform 数据源（§1.5），ADR-0019 的 17 风格表与乙案共用一套参数词汇——两套"材质"最终是一条管线，不是分叉。
3. ADR-0017 的 LOD 问题在 shader 路径下大半消解（zoom 无关锐度、无逐珠层数），红线以输入不变式继承；`§1.6.9` 图元核算口径的系统性偏差（低估 fill）被 D1/D2 的测量补上，**无论乙做不做，这个口径修正都留下**。
4. 排序纪律保住：先路基甲案（确定性收益）→ 数据门禁 → 终态路线，避免「为质感重构把整个验收体系押在未验证的编辑器链路上」。
5. 漂移登记（DR-1/DR-2）修正了「构建阻塞」的过时口径，后续会话不再按假前提排期。

### 4.2 负面（已知成本，不是风险——白纸黑字）

1. **验收体系永久双轨**：`bead-render.test` 钉的「12 条图元逐 kind 序列」只在 Graphics 路径上有像素意义；shader 路径需要另建一套判据（§8.2）。双轨 = 每次观感改动两处回归，**这是 ADR-0019 §4.2-2 已预告的成本形态的完全体**。
2. **harness 与 Cocos 出图不再逐像素等价**：历史建立的全部「两路径一致」隐性契约作废；"harness 里看着对"不再是"Cocos 里对"的充分证据，跨实现 diff 能力失去 ⇒ 回归保护降级为语义断言 + 截图判据清单（§8.2 给了方案，但方案的保护强度**低于**被放弃的像素等价——这是买质感上限付出的对价，不是可以忽略的细节）。
3. **per-pixel 成本不随 LOD 下降**：缩得再小片元照算；唯一的省法（按风格/档位的分支早退）在低端 GPU 上的收益是未知数 [待 D8]。乙案的帧率下界与盘面大小**解耦**（好消息），与风格复杂度**耦合**（坏消息）——方向与现路径恰好相反。
4. **全仓唯一 `cc` 文件的未验证面扩大**：`bindings.ts`（或新增宿主文件）将叠加 Material / 纹理上传 / 自定义 effect 一整串未验证 API；该文件被 Node typecheck 排除、无自动测试覆盖（头注自认 UNVERIFIED）——**全部错误只会在编辑器/真机暴露**，正是本仓历史上最贵的一类盲区（G1–G9 判例）。
5. **确定性口径改写**：同 seed ⇒ 输入数据（RenderModel/provider payload）字节级一致可保，但**输出像素只在同 GPU/驱动下稳定**——shader 内哈希与 CPU `createRng` 不同值，跨机型截图可能不同。这是固有属性不是缺陷，但一切「字节相同」判据的措辞都要显式改写，改写不到位 = 假绿。
6. **虹彩/符号/无障碍对比度需新建实测温度的工具链**：a11y B2「图形对珠面 ≥3:1」从「代码可推导」变成「截图取色实算」（shader 色相轴不在 `palette.ts` 里）；本仓现无此工具（ADR-0019 §4.2-3 的欠账在乙案下**翻倍**）。
7. **`.effect` 是新增资产类型**：受 L1 精神管辖（`.meta` 必须编辑器生成）⇒ 在编辑器上线前，shader 路线连"一个能编译的文件"都造不出来——这不是本 ADR 能绕的，是工作流的硬前置。
8. **D6 反例测试本身有成本且不许在主工程做**（L1：禁测试场景）⇒ 只能仓外一次性小工程或运行时造节点两种形态之一，多花的半天属于给历史争论买的保险。

### 4.3 中性 / 待观察

- 微信各机型 WebGL2 覆盖矩阵（D7）——只影响「以后能不能放宽下限」，不影响首版（首版钉 ES 100）。
- Cocos 自定义 2D effect 的官方支持度与跨版本兼容性（effect 语法随引擎版本演进）。
- 包体增量（effect 编译产物 + 宿主代码，KB 级预期，构建后以 `check:size` 实测登记）。
- 每帧 3.4 KB 纹理上传与 841 格相位通道在真机上的实际开销（D8）。

## 5. 复评触发条件（Review Triggers）

1. **G1+G2 双门禁过**（D3–D5 绿 且 D1/D2 裁 H-FILL）⇒ 本 ADR 转「实施中」，另立实施 ADR（定正式通道形态）+ 交 wxgame-epic-split 拆 Story。

3. D4/D5 证伪「1 draw call」（发现不可绕的断批/引擎限制）⇒ **乙案失效**，回 §2 全表重选。
4. ADR-0019 Q1 用户裁定 (b)「放宽新原语」⇒ 渐变/模糊/ellipse 的原语扩容与本 ADR 乙案**合并复议**（乙案正是这些"新原语"的更便宜替身：shader 里全是免费的）。
5. 真机帧率 <30fps（任一路线、任一形态）⇒ 与 ADR-0005/0017 的既有触发**并单复核**，勿三条 ADR 各自复评打架。

8. `§1.6.9` 图元核算口径若被修订（加入 fill 维度）⇒ 回写本 ADR §1.3 引用处。

## 8. 分层落位与验收方案（本 ADR 的落码边界，非落码）

### 8.1 代码与资产住哪（核心理由：镜像纪律 + L1–L3 现状原样保持）

| 件 | 落位 | 理由 |
|---|---|---|
| `.effect` 源（GLSL） | `games/beads/cocos/assets/effects/`（编辑器导入产 `.meta`） | 工程资产，不属 framework 镜像；`games/*/src` 与 framework 仓**不放任何 shader 文本**（L2/L3 + F-6 现状） |
| 触 `cc` 的渲染宿主（建材质/上传纹理/挂 uniform） | **`games/beads/cocos/assets/scripts/` 宿主层新文件**（与 `bindings.ts` 平级，例：`beads-board-shader.ts`），**不进** framework 镜像、**不进**框架 barrel、被 Node typecheck 排除（同 bindings 待遇） | 保持「framework 镜像内唯一 cc 文件 = bindings.ts」的原语；若改把玩进 `packages/framework/src/adapters/cocos/` 则镜像纪律与「唯一 cc 文件」口径双破坏——**不采** |
| 盘面数据契约 | Spike 期：game 侧纯函数 `buildBeadFieldPayload(snap, layout, out)`（产出 provider 回调消费的 TypedArray/复用对象，**零新依赖**）；正式期：是否升格为 `RenderModel` sideband 字段或聚合命令，**另立实施 ADR 裁**（判例 ADR-0014 先通道后契约） | 纯函数可在 Node 单测（`[N]`），玩法层不碰 `cc`（L3 安），framework core 零改动（L2 安）；热路径零分配靠复用 scratch（WXG-T-128 裁定 B 先例） |
| 材质创建方式 | 代码 `new Material()` + 按 effect 名初始化（**确切 API [待 D3 实测]**），**不做 `.material` 资产** | `.material` 资产需编辑器面板挂接（人工场景侧），与 L1「一切代码构建」精神相悖；且少一类要管 `.meta` 的资产 |
| 开关 | `tuning.ts` 呈现层开关（如 `BEAD_SHADER_RENDERER`，默认关） | 回退成本 = 一行；关 = 与现路径逐字节等价，双轨期回归保护的地基 |

### 8.2 「像素等价」放弃后的验收方案（最易被忽略、必须给的那条）

**三层，从上到下保护强度递减、成本递增**：

1. **数据层机检（`[N]`，CI 可跑，主防线）**：验收对象从「出图像素」前移到「shader 输入」——`buildBeadFieldPayload` 纯函数断言：pattern→纹素映射逐格相等、红线三件（中心孔/符号/目标色）是通道字段的硬不变式（缺失即红）、LOD 档位参数合规、脏标记只在 pattern 变更时置位、同 seed 同快照 ⇒ payload **字节级一致**（确定性判据的新载体，替代旧「RenderModel 字节一致」在 shader 路径的失效部分）。
2. **参考实现层（harness `[N]/web`）**：canvas2d 适配器对**同一通道**做 CPU 近似实现（SDF/叠层皆可，语义对齐、不求像素对齐）⇒ harness 保留「观感评审」职能；**显式撤销**一切跨实现像素 diff（历史契约作废登记处，见 §4.2-2）。
3. **出图层（`[E]/[W]/[R]`，人眼 + 取色）**：截图判据清单，二值判据（可见/不可辨，不做像素阈值）——中心孔可见、符号在最小格径下可辨、目标色与非目标色可区分、光晕不跨格污染、文字/图形对比度**取色实算 ≥3:1**（a11y B2 的 shader 版测温法：截图采样工具，随 D4 一并产出）。证据落 `production/qa/`，引用 `temp/beads-facet/` 为方法先例。

**历史判据迁移**：`bead-render.test` 的 12 命令序列回归锁**原样保留**（守 Graphics 路径 = 守回退阀），不为 shader 改写——两轨各钉各的，这正是 ADR-0019 §4.2-2 预告的双轨形态。

### 8.3 与既有裁定的相容性自检（不推翻已裁的）

- ADR-0005：本 ADR 是其 §5「新 VFX 使指令数倍增/复评」路径的质感侧延长线，方案 A 在触发前**维持现行**，不冲突。
- ADR-0017：红线三件在 shader 路径转为输入不变式 + 截图判据（§7-D4）；「降层」语义改写为「降参数」已声明，**层集冻结权仍在 art**，本 ADR 不代裁。

### 11.3 改判条目

1. **§2.2 载体①「给 `cc.Graphics` 直接换材质」—— 否证。** 实测：全场景只有 **1 个渲染组件**承载 UI（`Canvas/GameRoot/GameRoot/Graphics`），面板 / 按钮 / 托盘 / 背景 / 珠场**共用同一张 Graphics** ⇒ 换材质 = 整个 UI 被重绘成珠子（截图为证）。⇒ 载体①只能用于「逐图元换片元」，**不能**用于「整盘 SDF」。
2. **§2.2 新增载体②最小形态（推荐实施形态）**：**独立 `Graphics` 节点 + 只画一枚满幅 rect**，片元按格原点/格距解析整盘。优点：不引入 Sprite/内置图集/`UIMeshRenderer` 等未验证 API，顶点流仍是 Graphics 那一套（`a_position / a_color / a_dist`，与本 effect 属性完全对齐），代价仅 +1 draw call。
3. **撤销「不依赖 `fwidth`」的保守裁定。** 引擎自带 `builtin-graphics.effect` 本来就用 `#pragma extension([GL_OES_standard_derivatives, __VERSION__ < 300])` + `#if __VERSION__ < 300` 双路；实测本 effect 的 `glsl1` 版自动展开为带 `#extension … : enable` 守卫的合法源码。**AA 可以吃导数，但必须保留常量降级分支**（无扩展时 `aa = 0.6` 一类）。
4. **新增不变式（实测踩到）：格原点必须由布局真源供。** v1 只传 `cellSize` 不传原点 ⇒ 以节点/屏幕中心为基准做 `fract` ⇒ 盘面格相位错位（图案边缘珠子被切歪，截图可辨）。⇒ 「布局 uniform 只能从 `gridLayoutFor()` 输出生成」不是建议，是**硬约束**（同 K-054「画的不等于点的」判例族）。
5. **新增口径：三角数。** §1.6.9 / §1.9.5 的图元核算只算**命令条数**，从未算**三角/顶点数**。实测对局态 = **21917 三角/帧**（现状九层叠层 + 圆角曲线展平的真实产物），而载体②同一片盘面 = **2 三角**。⇒ 本案的性能卖点从「命令数 −46%」升级为「三角数 −4 个数量级 + α 叠层归零」；**测量单与图元口径表都须补这一列**。

### 11.4 低端机坑清单（本轮新增，按危害排序）

| # | 坑 | 证据档 | 规避 |
