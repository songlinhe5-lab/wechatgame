# ADR-0007 — beads 供料计时与暂停冻结：dt 管理归游戏侧（S1 状态机门禁），不改框架

## 1. 上下文（Context）

beads 有两个"持续流逝"的计时器：S4 供料心跳（累计 dt ≥ SPAWN_INTERVAL 触发供料）与 S5 关卡倒计时（`remaining -= dt`）。GDD 冻结的暂停语义是**选择性冻结**：`game:paused` 冻结 S4 心跳与 S5 计时（S5 §2.3），但**表现层不冻结**（告急脉冲动画帧继续，PAUSED 中被面板遮挡不误导）。breakout 的判例是全冻结 + 终局慢放 0.3×——两游戏语义不同。框架 `FixedStepLoop`（core/loop）提供固定步长 dt，无任何暂停/时钟缩放概念。需决定：冻结/计时管理放框架 core 还是游戏侧。

## 2. 备选方案（Alternatives）

**方案 A：框架 core 增加 PauseClock / TimeScale 服务（统一时钟层）**
- 事实对比：core/loop 增加 `pause()/resume()/scale`，S4/S5 从框架拿"已过滤 dt"。
- 代价：beads 要"逻辑冻结但表现层不冻结"，breakout 要"全冻结 + 慢放"——统一时钟层必须同时表达三档（逻辑/表现/缩放），接口膨胀；`App.tick` 的固定步长累加器与暂停交互（暂停期间真实 dt 丢弃还是累计）语义复杂化；改框架 = 改已验证代码（226 单测基线），违反本轮"不改框架"纪律。

**方案 B：游戏侧持有计时器，S1 状态机做单点门禁（本轮采用）**
- 事实对比：S4 心跳与 S5 计时都是游戏实体（`systems/timer.ts`、`systems/spawner.ts` 内的累加器），只在 `update(dt)` 中按**当前状态机状态**决定是否累计——`PAUSED` 时 S1 不调用二者的 `tick`，表现层动画参数照常推进；breakout 的 `game-loop` 无需任何改动。
- 冻结语义集中在 state.ts 转移表 + update 编排一处，跨系统漏冻结面最小。

**方案 C：事件驱动冻结（`game:paused` 广播后各系统自行停表）**
- 事实对比：GDD §4 确有 `game:paused/resumed` 事件（S9 → S4/S5）。但"订阅事件后各自停表"意味着冻结纪律分散在 N 个订阅方，漏订阅 = 漏冻结（正是 R4 风险）；且事件是通知语义，承载"状态权威"违反矩阵"事件只通知、状态机是裁决者"的判例。

## 3. 决定（Decision）

选**方案 B**：S4/S5 各自持有 dt 累加器（游戏侧实体），**S1 状态机是冻结唯一裁决点**——`PAUSED` 状态下 S1 的 update 编排跳过 `spawner.tick()` 与 `timer.tick()`，表现层推进不受影响。`game:paused/resumed` 事件照发（§4 契约），但只作**通知**（HUD/面板/表现层消费），不作为冻结机制。框架 core 不动。

## 4. 后果（Consequences）

**4.1 正面**
- 框架零改动：226 单测基线不动，breakout 不受任何影响；beads 在纯 Node/vitest 下即可验证全部冻结判据（注入固定 dt）。
- 冻结语义**单点化**：S4§8-8（暂停零供料、恢复不早于剩余间隔+1 帧）与 S5§8-5（暂停 300s 恢复误差 ≤1 帧）的用例直接对 S1 编排层断言，无分散订阅方可漏。
- 两游戏语义差异（beads 选择性冻结 / breakout 全冻结+慢放）天然由各自游戏侧表达，core 保持"无玩法语义"的纯粹性。

**4.2 负面（已知成本，如实记录）**
- 每款新游戏都要**重新实现**一遍冻结纪律——这是判例复用而非代码复用，第三个游戏若再漏冻结，应升级为框架能力的信号。
- `game:paused` 事件"照发但不承担冻结"是**双重语义**：新成员可能误以为订阅了就等于冻结；须在控制清单与代码注释显式声明"事件仅通知，冻结看 S1 编排"。
- 表现层"不冻结"意味着 update 与渲染的推进来源不同（逻辑 dt 来自固定步、表现动画来自真实帧间隔），实现时需两条时间轴，调试心智略重。

**4.3 中性 / 待观察**
- 若矩阵第三款游戏出现"暂停期间继续表现层动画 + 计时部分恢复"类更复杂语义，届时复评是否把"时钟层"升入 core（见 §5）。

## 5. 复评触发条件（Review Triggers）

- 第三款小游戏出现与前两款都不同的冻结/缩放语义 → 复评方案 A（PauseClock 入 core）。
- 同类冻结 bug 在 QA 用例中重复出现（漏冻结）→ 视为判例复用失效，升级框架能力。
- 引入"挂机奖励/离线收益"类需要真实墙钟跨度的机制 → 墙钟与模拟钟分离需求出现，复评时钟层。
