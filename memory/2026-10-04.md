### WXG-T-237 v7.0：格面 mask 槽外透明（资产变更）

- **编码事实**（`tint-composite.ts`）：`out = base·d + (1−base)·l·shape`，**`alpha = shape = B 通道`**
  ⇒ 「槽外透明」= 把 mask 格外区域的 **B 置 0**（资产侧改，**不是代码侧裁剪**）。
- **⛔ 必守约束：槽底不得透明** —— 无孔档槽底是 `0.32` 深坑，透明化会抹平**判据 I-5** 钉的
  「有孔 0.70 / 无孔 0.32」分叉 ⇒ shape 只在**格外**置 0。**教训：改 mask 的透明性前，
  先查「哪些区域的色值承载了判据」。**
- **盘面视觉零变化（有数学解释 + 实测）**：原 mask 格外 = `base·0.70`，底色层 `drawTargetTile` 的
  `edge = mix(base,−0.30) = round(base×0.7)` ⇒ **同值（±1/255）** ⇒ 改透明后露出的底色与原值一致。
  **实测新旧截图盘面区差异 = 0px** ⇒ 这类「把平铺从 mask 移到���色层」的改动可以**零视觉风险**落地。
  ⇒ **方法沉淀：改 mask 前先算「原合成值 vs 底层值」是否同值** —— 同值则改动是纯结构优化，风险≈0。
- **仅托盘变**（16680px）：格外 `palette.slot×0.70`(#ADACB0 灰) → 面板白(#FFFFFF)，
  凹陷由保留下来的 3dp 斜面 + 槽底承担 ⇒ 观感「白板上一排排凹进去的小坑」。
- **封箱零追改**：封箱比**命令流**，mask 像素是**资产内容**、不进命令流（blit 只带 `fx.base`）
  ⇒ total/kinds/sha 全不变。**教训：改「资产」与改「命令」是两件事 —— 封箱只守后者；
  资产变更要另找门禁（本例是 `mask-diff` 对拍）。**
- ⚠ **探针假阴性坑（我自己的）**：临时探针用 `readPngRgba(...)[k]` 索引，而它返回
  `{width,height,data}` 对象 ⇒ `py[k]` 与 `ts[k]` **都是 undefined** ⇒ `undefined !== undefined` 为假
  ⇒ 报「0 字节不同」的**假绿**。**教训：写验证探针时，先确认索引对象是不是真的支持数字下标
  （或先断言一个已知非空值），否则「全绿」可能是「什么都没比」。**
- **两处实现坑（治根）**：① **PIL 与 TS 自实现 LANCZOS 对 0↔255 硬边振铃幅度不同**（1–9/255）
  ⇒ `SHAPE_RINGING_FLOOR` 地板清不掉对方残留 ⇒ 对拍门禁红（max 7）
  ⇒ **治根 = shape 在 128 空间直接判定不经缩放**（形状本就是二值语义，AA 由 R/G 斜面光照承担）；
  ② holeless 槽口 **22dp/角 7dp** ⛔ 不可硬编码有孔档的 12/8。
- **测试口径变更**：I-4「格面 B 满幅实底」前提被推翻 ⇒ 改写为「槽口内 255 / 格外 0 / 纯二值零振铃」。

## 二十九批 · 选型调研 + 甲″ 分层上界出数（2026-10-05 · WXG-T-249 · ADR-0030 §5.0.3）

**本批起源 = 两问一裁**（用户原话顺次）：「丙′ C　甲′ A 请调研，最佳实践推荐哪个？」→「甲」（= 我给的选项 A：开 甲″ 三层工程单）。

**1) 先答「两方案各自优势局限」（只算本仓实测账，不引外部）**：本质差别 = **成本落在哪一侧**。
丙′ 把命令重放搬到 Canvas2D ⇒ 换 GPU 侧几何/α 层（tris 182 vs 3354 vs 37k–55k），代价是**每脏帧一次满幅上传**；
甲′ 把珠子变成引擎原生节点 ⇒ **零每帧上传**，代价是层级/节点遍历回来。**门控改变了这笔账的形状**：静置期三臂都只剩 2–3 真脏帧，
而 beads 观感批几乎全是逐帧动画 ⇒ 动画期满载，**门控后换臂的增量收益需重算**（此句已写进 §5.0.2 末）。

**2) 外部最佳实践调研（4 组 WebSearch，逐条可源）**：离屏 canvas 每帧上传的行业读数全部是**负面**
（Babylon：`texSubImage2D` “same or worse”，解法是降到 32 ms 节流；Spine/Construct3：iPhone 每帧上传 ⇒ 60→30 fps；Android NDK：512² 上传 130–150 ms）；
微信官方虽推「单上屏 + 多离屏 canvas」，但同页写明「鸿蒙 OS 暂不支持外接纹理」与「避免过大宽高（安卓会 crash）」，
且**视频场景已改走 `wx.createVideoDecoder().getFrameData()` 直传**而非 canvas 上传 ⇒ 丙′ 押的是**两条未证平台能力**；
Cocos 侧三原则（图集统一 / 渲染序连续 / 统一材质）与「UI 单独一层做位置同步」= **正是甲″ 的形态**；
动态合图小游戏默认禁用需最外层 `macro.CLEANUP_IMAGE_CACHE=false`，入图条件 <512（我们 128 符合）。
⇒ **推荐：甲′（以甲″ 三层形态实施）为主选，丙′ 降为第二候选**（同源观感收益不变，变的是成本风险已拿到数）。

⇒ 本批只在**取证面**加一个 `layers=full,beads` 档测**上界**（非珠层整体停用），拿不到精确值但能回答「值不值得做」。
⚠ 实现陷阱（已沉淀 **K-104**）：必须**关组件**（`enabled=false` / `active=false`），不能「不喂命令」——
`CocosRenderModelRenderer.draw()` 内部才 `g.clear()` ⇒ 不喂 = 上一帧内容继续提交 = 读数成一份**冻住的矢量层**（会得出「什么都不省」的假结论）。

## 三十六批 · S5′-3 层序 = **视觉裁剪解**，不是「挪底板」（2026-10-05 · WXG-T-256 · ADR-0030 §5.6 第十六刀）

**用户原话（裁定与硬约束，三层分开记）**：① 提问「S5′-3 层序怎么切 解释下具体效果，我希望的是**盘面整体缩放，内容都不需要重新烘焙**；另外**背景框需要去掉**，整体游戏界面做一个统一背景即可」；② 选项题拍板 =「去板范围：**整块去掉（最彻底）**」「统一背景：**收成单层纯色背景**」；③ 路线拍板 =「**A 起步、B 作为收口替换**」（A = 渲染器自己画底色；B = 相机 `clearColor`）；④ 开工令三步 =「① 视觉裁剪（去板 + 背景单层 + 层归属标记 + 两块提交体 + 载体插序）→ 顺带重抓封箱基线 → ② 真机/harness 复读 dc 与截图 → ③ 若 +1 批有代价再切相机 clearColor（删 rect）」。

**上一轮那句「真解 = 把底板整块挪出 `Graphics`」被本批推翻（推翻的是诊断，不是事实）**：一块 `Graphics` 同装珠下底板与珠上遮罩确实是插入序死结；但去查板几何才是要害 ——`gridW = (gridCols−1)×snap.gridPitch + gridCell`**随 `camZoom` 每帧重算** ⇒ §5.2 裁② 那把尺「有没有动效」在板上直接判「有」⇒ 烘进 L0 就要按缩放档重烘 ⇒ **与用户硬约束「缩放不重烘」正面冲突**。用户裁去板后：**珠下零图元 ⇒ L0 不需要烘 ⇒ 冲突面消失**，层序改用**节点序**（Cocos UI 不需要 zIndex）⇒ ⛔ 框架 `render-model` 零改动，「层归属标记」这套新机制**一行都没写**（当初它出现在用户三步令的第 ① 条里，被更简的解替代 —— 记法：令里的构成项是可谈判的，目标不可谈判）。
