## 「到达序」判据清理：把不可测的「先到为准」统一换成帧内执行序（WXG-T-061）

- **关键发现：正确基准早已存在**。`pause-settings.md §6` 与 `timer-gameover.md §6` 在
  **WXG-T-031** 就确立过：帧内序 = **输入（段内序：状态指令 → 玩法事件）→ 连击窗 → 供料 → 计时**，
  理由是「单线程固定步长下『同帧到达序』不可定义（一帧内没有先后**事件**，只有代码**执行序**）」。
  ⇒ 本轮不是发明新基准，而是**把它推广到全域并归口**。
- **规范真源落到 §2.2**：`core-loop §2.2` 原先只有一个 5 步列表（供料→选珠→落子→判定→道具），
  被 Epic 文档误读成「update 顺序」。现拆为 **§2.2.1 玩法叙事序**（玩家感知的因果链，**非**执行序）
  与 **§2.2.2 帧内执行序（规范，唯一真源）**，并写明「其余 GDD 引用本节、不得各自复述」。
- **补齐玩法事件段内序**（backlog 的原话要求）：落子回执 `bead:placed` 恒先于 `level:cleared`
  （同一次落子调用栈）；`level:cleared`（输入段）恒先于 `level:failed`（计时段）。由此得到
  **「cleared 优先」的可观测机制**：输入段处理完若已离开 PLAYING，本帧**直接返回**，供料与计时都不执行。
- **换基准 14 处**（`tray-spawner` / `powerups` / `score-combo` / `bead-grid` / `input-control` §6 等），
  **outcome 一一对应**，只换基准不改判据；`pause-settings` / `timer-gameover` 的复述改为归口引用
  （复述漂移正是 WXG-T-031 的成因）。
- **顺带更正一处文档级错误**：`epics-beads.md` EP01-S2 写「固定步长 update 顺序（供料心跳 → 输入快照 → …）」——
  与实现（`_stepPlaying` = 输入 → 连击窗 → 供料 → 计时）相反，属把叙事序读成执行序。
- **新发现：若干「同帧」条款其实不可达** —— `score-combo §6`「`bead:placed` 与 `bead:rejected` 同帧」、
  `input-control §6`「同帧先选珠后点网格」、`tray-spawner §6`「落子回执与换选争同一槽」在
  「**每帧最多 1 条输入指令**」下不可能发生。已如实改为「不可能同帧」，不留假想分支。
- **可执行证明**：`tests/frame-order.test.ts` 4 条（beads 145 → **149**），用真·同帧注入
  （`beginFrame()` 后、`update()` 前推指针）钉住四条段序；含**对照组**（不注入时同帧确实供料）
  以免「假通过」。
- **两条标定纪律（踩了才知道）**：① 供料帧号必须**探针实测**——累计 `1/60` 有浮点漂移，
  `240×1/60` 略小于 4.0，实际落在**第 241 帧**；② **`giveTrayBead()` 自身就发 `tray:spawned`**，
  计数断言要用增量而不是绝对值，否则夹具动作会被算成供料段产出。
- **门禁**：`verify` 退出码 0；framework 234 / breakout 239 / beads 149。
- **归档腾余量 + 抓到归档器的一个结构缺陷**（同日追加）：按用户指示跑体积驱动归档
  `node tools/scripts/archive-tasks.mjs --until-under=7000 --write` —— 归档 **T-044…T-047 四行**，
  台账 7773 → **6821**（余量 1179），**头注未回退**（仍 T-061 / 下一可用 T-062 ⇒ T-053 的「只进不退」生效）。
  核对守恒时发现 `WXG-T-032` 在归档文件里**有两行**（残行自称「并入下方同号完整行」）：
  根因是**两个会话各自建了一行同号任务**，归档器**原样搬入、从不检查同号**。
  已手工合并为一行 + 补勘误注记，并把「归档器缺同号守卫」登记 backlog（建议保守做法：只警告，
  不自动合并——合并语义需人判）。**教训**：这类「搬运工不校验唯一性」的缺口不会报错，
  只会让下游「id → 行」映射型工具静默丢行。
