## 三十批 · `fx` 入指纹：blit 帧可判脏（2026-10-05 · WXG-T-250 · ADR-0030 §5.0.4）

**起源**：用户在二十九批汇报后再答「甲」= 开框架单把 T-249 撞到那条上限堆掉。本批**动生产**（框架 core），与上一批的「零生产改动」分界就在此。

**1) 先核后写（ponytail 阶梯 rung 2）**：T-248 当时写「`fx` 袋无固定可哈希口径」⇒ 但**值域定义就在同一文件里**：
`BlitFxValue = string | number | boolean | readonly number[]`，且类型文档规则 4 明文「键序由构造方固定（模块级常量）」。
⇒ 所谓「不可哈希」不成立 ⇒ 最短正解就是把字段遍历从「只认 number/string」改成**一个递归 `mixVal`**（数组走 `for...in` 即索引序，无需特例），
并**删掉**保守出口（`_frameSeq` 字段 + `begin()` 自增 + `if (hasBlit) mix(...)`）。**这一条是本批最值钱的教训：保守出口往往是「没查值域」。**

**2) 真风险不是哈希，是「同 id 换像素」**：判脏变严 ⇒ 若纹理内容能在 `textureId` 不变时变，就会漏画。逐条核了两条链：
tint = `cache.get(textureId, base)`（`base` 在 `fx` 里 ⇒ 入门）；bake = `bake:<styleId>:<colorIdx>` 且 `bakeSize = BAKE_CANONICAL_SIZE` 常量（不随 zoom/dpr）
⇒ 今日安全。⚠ 这成了**新的在册上限**（写进 `signature` 的 `ponytail:`）：指纹计**引用**不计像素，将来出现「就地重烘同 id」的生产者就必须补一个内容修订号。

**3) 读数（`[E]` Apple M4 · dpr2 · gate=on · zoom 1.0 · frames=150 warmup=40）**：静置 `drawn` —— C 丙′ **150 → 3**、A 甲′ **150 → 2**（full 与 beads 两档同）、V 对照组不变 3；
甲′ 整帧 tick **1.30 → 0.40 ms**（上界档 0.90 → 0.40）；**丙′ 每帧 6,031,680 B 上传 ⇒ 150 帧只 3 次**（≈ 18 MiB 而非 862 MiB）。
最坏档（`--disturb`）tick V 5.10 / C 1.40 / A 1.40 ⇒ **递归代价读不出**（每 blit 一个键）。
⚠ 两条诚实注：① 开档 `draw p50`/`gpu p50` 样本只剩 2–3 帧 ⇒ 无判别力，判收益只看 `tick p50` + `drawn`（K-101 原样适用）；
② V 本轮 disturb 5.10 vs §5.0.2 的 4.80 = 运行间漂移（V 不含 blit），⛔ 不得归因为本批。**画面正确性**：`drawn=2–3` 的静置截图目测仍是完整盘（128 珠 + HUD）。

**4) 单测换档（契约变了就必须改测）**：`render-model.test.ts` 那条「blit 掺帧序号 ⇒ 恒判脏」翻成四腿（同内容同指纹 / `fx` 值变 / 数组载荷变 / 有无 `fx`）；
`app.test.ts` 那条「blit 帧永不判干净」翻成「四 tick 只画 1 次，改 `fx` 必再画」（新增 `blitFx` 旋钮，⛔ 用 `size` 改会连带几何）。两批旧测都是「宁多画」时代的产物，⛔ 不得留着当绿。
