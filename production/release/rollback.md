# 回滚方案（Rollback Plan）· 《砖阵》Breakout

- 项目：微信小游戏矩阵 · 首款 demo `breakout`
- 版本：v1.0 · 2026-09-11
- 作者：路远行（发布与 Live Ops）
- 状态：**预案（待评审）** —— 本轮不上线，故本方案为"上线时可照做"的预案

---

## 0. 回滚的两种含义（先分清）

| 类型 | 含义 | 本项目适用性 |
|---|---|---|
| **A. 版本回滚** | 退回上一个已发布版本，让玩家重新拿到旧版 | 依赖平台能力，见 §2 |
| **B. 修复性热修** | 不回退版本，直接发布一个修复版 | 本项目**主路径**（无热更通道，见 `version-strategy.md §5`） |
| **C. 存档回滚** | 处理"新版本存档不被旧版本识别" | 见 §3，本项目核心风险点 |

> 本项目**无服务端、无资源热更通道** → 没有"在线临时开关/降级"这类手段。
> 我们能做的其实是：**上一个版本重新发布（A）** 或 **推一个修复版（B）**，并保证**存档不被搞坏（C）**。

## 1. 触发条件（什么情况回滚）

### 1.1 Blocker 级（立即升级决策）
| # | 条件 | 说明 |
|---|---|---|
| T1 | 全量玩家无法启动 / 白屏 / 卡在 loading | 致命可用性问题 |
| T2 | 高频崩溃（崩溃率显著高于基线） | 影响绝大多数用户 |
| T3 | 存档破坏：更新后玩家进度/最高分被清空 | 数据损害，玩家信任受损 |
| T4 | 审核/合规问题导致被下架 | 合规风险 |
| T5 | 严重数值/流程阻断（例：某关必然无法通关） | 阻断主流程 |

### 1.2 非 Blocker（评估是否值得回滚）
| # | 条件 | 处理倾向 |
|---|---|---|
| T6 | 局部体验问题（某机型适配异常） | 优先**修复版**，非回滚 |
| T7 | 文案/显示错误 | 修复版 |
| T8 | 低影响 bug（不影响通关与存档） | 排期修复，不回滚 |

> **判断原则**：回滚是**高影响、有代价**的动作（见 §2 限制）。**能用一个 PATCH 修复版解决，就不回滚**。只有当"修复版的到达速度赶不上损害速度"或"根因未知"时才回滚。

## 2. 微信小游戏的回滚手段与限制

> ⚠️ **本段为高不确定区，务必以 mp 后台与官方文档为准。** 平台对"版本回退/撤回"的能力会变动。

| 手段 | 说明 | 限制 |
|---|---|---|
| **版本回退（若平台支持）** | 把线上版本指回上一个已发布版本 | ⚠️ 待核实：是否支持、可回退几级、是否有次数/时限、是否需重新审核 |
| **撤回发布 / 停止当前版本** | 让当前版本不可访问或停止放量 | ⚠️ 待核实是否存在该操作 |
| **灰度回撤** | 灰度发布时把比例调回 0 | ⚠️ 待核实灰度粒度与回撤能力 |
| **下架** | 整款下架 | 影响所有用户，最重手段 |
| **紧急审核通道** | 加急审核修复版 | ⚠️ 待核实是否提供、SLA 如何 |

**结构性限制（本项目视角）**：
1. **无服务端 → 无"远程开关"**：不能像有后端的游戏那样"下发配置关掉某个功能"。一切都随包走。
2. **玩家侧已缓存的版本**：即便平台"回退版本"，已进入玩家设备的资源/缓存不会自动消失。⚠️ 待核实缓存清理行为。
3. **存档是本地且永久的**：回滚**不会**帮助"在玩家设备上撤销一次已经写入的升级存档"——这正是 §3 的核心风险。

→ **结论**：本项目**不具备"快速技术回滚"的能力**。因此策略是**"往前修（PATCH 修复版）优于往后退（版本回滚）"**，并且**把风险前置到发布门控**（见 `release-checklist.md`）。

## 3. 本地存档兼容性风险（本项目核心）

> 权威设计依据：`games/breakout/design/gdd/save-progress.md §6`。实现现状：`packages/framework/src/core/save/save-manager.ts` + `games/breakout/src/game/save-schema.ts`。

### 3.1 为什么这是最大风险
- 存档**仅存在玩家设备本地**，**无云端可还原**。一旦写坏，**无法从服务端恢复**。
- 回滚版本**不能**撤销玩家设备上已被写入的"新版存档"。

### 3.2 版本矩阵（设计承诺）
| 情形 | 设计处理（`save-progress.md §6`） |
|---|---|
| `version == 1`（当前支持） | 正常读取 |
| `version < 1`（更旧） | 迁移：补默认值，保留已知字段 |
| `version > 1`（来自更新版本） | **安全降级 → 重置为初始存档，进 L1**；不解析未知字段、不抛异常 |
| 无 `version` / 无法识别 | 同上，**重置为初始存档** |
| 字段越界 / 非法 | 静默修正并回写，**不崩溃** |

**策略总纲：降级优先于报错** —— 任何情况下不得因存档问题中断启动。

### 3.3 回滚场景下的存档推演（关键）
> 场景：线上是 `v0.2.0`（存档 `version=2`），因 Blocker 回滚到 `v0.1.0`（只认识 `version=1`）。

| 玩家状态 | 回滚后会发生什么 | 后果 |
|---|---|---|
| 未曾更新到 v0.2 的玩家 | 存档仍是 `version=1` → 正常 | ✅ 无损 |
| 已更新到 v0.2 并写入了 `version=2` 存档的玩家 | 旧版 v0.1.0 读到 `version > 1` → **按设计降级为"重置初始存档、进 L1"** | ⚠️ **玩家进度被清空** |

→ **这就是本项目回滚的"隐藏代价"**：回滚**在技术上可行**，但对已升级的玩家**表现为"进度重置"**。
→ **缓解**：只有在"**必须回滚**"时才回滚，且**必须提前公告**"本次更新可能重置部分玩家进度"，把预期讲清楚。**绝不能让玩家以为存档丢了是 bug。**

### 3.4 降低存档风险的发布纪律（前置防线）
1. **任何存档 schema 变更 → 必须提供从旧版本的正向迁移**（不要靠"重置"兜底）。
2. **schema 变更 → SemVer 提升 MAJOR**（`version-strategy.md §2.1`），并在 `changelog.md` 的「存档兼容性」段显式标注。
3. **发版前注入"高版本存档"做降级测试**（`release-checklist.md §3.1` 已列为门控项）。
4. **禁止**"新版本读旧档直接重置"这种偷懒实现。降级路径只应服务"未知/损坏"情形，不应用于正常的版本回退。

## 4. 回滚决策人与流程

### 4.1 角色
| 角色 | 职责 |
|---|---|
| **USER（你）** | **最终决策人**。回滚/下架等高影响动作**须你明确批准**，不可自动执行 |
| **OPS（路远行）** | 提出回滚建议、执行回滚动作、维护本预案、对外公告 |
| **ENG（程基岩）** | 判断根因、评估"修复版 vs 回滚"、准备修复包 |
| **QA（严守真）** | 复现与确认问题等级（是否 Blocker）、验证修复 |
| **LEAD（游承峰）** | 协调决策、在 USER 与团队间中转 |

### 4.2 流程（Blocker 触发为例）
```
1. 发现 Blocker  ──►  确认等级（QA 复现，ENG 判根因）
                        │
2. 决策会（OPS 召集 ENG+QA+LEAD）
     ├─ 结论：能 PATCH 修复  ──►  走"修复版发布"（简化流程，见 §5）
     └─ 结论：必须回滚      ──►  进入第 3 步
                        │
3. 回滚建议提交给 USER（附：根因、影响面、存档影响、替代方案）
                        │
4. USER 批准  ──►  OPS 执行平台回滚动作
                        │
5. 公告（如存档可能受影响，必须提前公告）
                        │
6. 观察验证（QA 抽样：能否启动、存档是否如预期）
                        │
7. 复盘 → 更新本预案
```

### 4.3 决策时效目标（建议）
- Blocker 确认 → 决策会：**尽快**（同日）。
- 决策 → 执行：**尽快**。
- ⚠️ 具体 SLA 由团队与 USER 商定，本表不写死数字。

## 5. 热修（Hotfix）简化流程

> 适用：能用一个 PATCH 修复版解决、无需回滚。**简化的是流程，不是审计。**

```
1. 从当前线上版本对应的代码状态切修复分支
2. 最小改动修复（不做无关重构）
3. QA 回归：走 release-checklist §3 的"核心循环 + 存档 + 真机"三项必过
4. 版本号 +PATCH（如 0.1.0 → 0.1.1），更新 changelog.md「修复」段
5. 包体复检（不超过 2000 KB 目标）
6. USER 批准 → 提审 → 发布
7. 完整留痕：修复内容、验证证据、发布时间、影响面
```

**审计要求（不可省）**：
- 每个热修**必须**有：根因说明、修复 diff、QA 验证记录、版本号变更、变更日志条目。
- 热修**必须**同步更新 `changelog.md`（即使是紧急发布）。
- "紧急"**不等于**"免测试"——至少跑完三项必过回归。
