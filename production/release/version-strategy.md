## 1. 三个"版本号"要分清

本项目同时存在**三种版本标识**，它们的目的不同，**不要混用**：

| 标识 | 例子 | 谁在用 | 目的 |
|---|---|---|---|
| **语义化版本（SemVer）** | `0.1.0` | 代码仓库、`package.json`、变更日志 | 表达"改了什么类型的变更" |
| **微信后台版本号** | `1.0.0` | mp 后台提审/发布 | 平台侧发布标识（⚠️ 格式与规则待核实） |
| **构建号（Build Number）** | `0.1.0+20260911.1` | 构建产物、归档 | 区分"同一版本号的多次构建" |

> 现状：仓库 `package.json` 版本为 `0.1.0`。
> ⚠️ **待核实**：微信小游戏后台对"版本号"的格式要求（是否必须 `x.y.z`、可否带后缀、是否与 SemVer 一致）——以 mp 后台当前校验规则为准。

## 2. 语义化版本（SemVer）规则

采用 `MAJOR.MINOR.PATCH`：

| 段位 | 递增条件 | 本项目示例 |
|---|---|---|
| `MAJOR` | **不兼容**的变更（存档 schema 破坏性变更、核心流程重写） | `1.0.0` → `2.0.0` |
| `MINOR` | **向后兼容**的新增（新关卡、新道具、新设置项） | `0.1.0` → `0.2.0` |
| `PATCH` | **向后兼容**的修复（bug 修复、数值微调、文案） | `0.1.0` → `0.1.1` |

### 2.1 0.x 阶段的特殊约定
- `0.x.y` = **未达正式对外稳定版**。本项目 demo 处于 `0.x` 阶段，`MINOR` 可含较自由的变更。
- 但**存档兼容性**的承诺**不因 0.x 而豁免**：任何破坏存档兼容的变更，**即使仍在 0.x，也必须提升 MAJOR 并在变更日志显式标注**（玩家不该因更新丢进度）。
- 达到 `1.0.0` 的条件（建议）：构建管线闭环 + 真机验收通过 + 完成一次正式提审发布。

### 2.2 预发布标识（可选）
- 需要区分迭代通道时用 `0.2.0-rc.1` / `0.2.0-beta.1`。
- ⚠️ **待核实**：微信后台是否接受带预发布后缀的版本号；如不接受，**SemVer 与平台版号解耦**（见 §1 表）。

## 3. 版本号与微信后台的关系

- **单一真源**：仓库 `package.json` 的 `version` 是**唯一真源**；平台后台版本号与构建产物版本号**由它派生**。
- **派生规则（建议）**：
  - 提审/发布的"平台版本号" = SemVer 主段（如 `0.1.0`）。
  - 同一 SemVer 多次提审时，若平台不允许重复版本号 → 由 `PATCH` 递增或加构建号区分。⚠️ 待核实平台是否禁止重复。
- **一致性检查**：进入提审前，必须校验 `package.json` / 构建产物 / 平台后台三处版本号一致（见 `release-checklist.md §1.1`、`§2`）。
- **不写死**：版本号只在 `package.json` 定义一处，构建脚本读取注入，禁止在源码里硬编码版本字符串。

## 4. 构建号（Build Number）规则

格式建议：`<SemVer>+<日期>.<序号>`

```
0.1.0+20260911.1
        │        └─ 当日第几次构建（同日递增，从 1 起）
        └─ 构建日期 YYYYMMDD（本地时区）
```

- **作用**：同版本号下区分构建产物，便于归档与"哪次构建出的问题"定位。
- **可见性**：构建号写入**内部归档与变更日志**；**不面向玩家展示**（玩家只看 SemVer）。
- **单调性**：构建号只增不减；回滚时**不回退构建号**（回滚=发布一个指向旧产物的新动作，构建号继续向前）。
- ⚠️ **待核实**：如平台版本号字段不接受 `+` 后缀，构建号仅存在于内部归档，不进入平台字段。

## 5. 热更新（资源热更）的边界与本项目取舍

### 5.1 什么是热更新（在本语境下）
指**不重新提审**、通过服务器下发方式更新游戏内容（如资源包、脚本）。微信小游戏支持一定形式的**资源热更**（下载到本地缓存）。⚠️ **待核实**：平台对"可热更内容"的边界（通常**禁止**热更核心代码/绕过审核逻辑）。

### 5.2 本项目是否需要热更？—— **结论：不需要**

| 判断维度 | 本项目现状 | 结论 |
|---|---|---|
| 是否有远程资源 | 无。**全程序化绘制，美术位图 0 KB，无音频**（`assets-spec.md §5`） | 没有"远程资源"可热更 |
| 是否有服务端 / CDN | **无服务器、无账号、无云存档**（`concept.md §7 Won't`） | 缺少热更的**下发通道** |
| 包体压力 | 主包目标 ≤2000 KB，远低于红线 | 无"包太大要拆出去"的压力 |
| 更新频率 | demo 阶段，迭代以重新提审为主 | 无需热更带宽 |
| 合规成本 | 热更需要域名备案、下发服务、合规审查 | **引入成本 > 收益** |

**因此**：
- 本 demo **不建设热更新通道**，更新一律走"**重新构建 → 提审 → 发布**"的正规路径。
- 存档**schema 升级**走 `SaveManager` 的迁移机制（框架已支持 `version → migration`，见 `save-manager.ts`），**这不是热更**，是本地数据兼容，可正常工作。

### 5.3 未来若需要热更的前置条件（备忘，非本轮任务）
1. 有 CDN / 下发服务 + 域名 ICP 备案（返回 `wechat-submission.md §3` 的备案问题）。
2. 确认平台允许的热更内容边界（**核心逻辑通常不允许热更**）。⚠️ 待核实。
3. 建立热更包的**版本清单与回滚**（与 `rollback.md` 联动）。
4. 资源改为分包/远程加载后，主包预算需重算。

> **一句话**：热更是"有远程资源 + 有下发通道"时的优化手段；本项目两个前提都不存在，**强行引入是负收益**。

## 6. 变更日志规范（Changelog Convention）

### 6.1 面向对象分层
| 文件 | 面向 | 语言 | 位置 |
|---|---|---|---|
| **变更日志（内部）** | 团队 | 技术语言，可含 PR/提交/文件 | `changelog.md` |
| **补丁说明（玩家）** | 玩家 | 玩家语言，有温度，无术语 | 本文 §6.3 模板 |

### 6.2 变更日志结构（Keep a Changelog 风格）
每个版本一个段落，分类固定为：

```
## [版本号] - YYYY-MM-DD
### 新增 Added
### 变更 Changed
### 修复 Fixed
### 移除 Removed
### 存档兼容性 Save Compatibility   ← 本项目强制段
### 已知问题 Known Issues
```

- **`存档兼容性` 段为强制**：注明"兼容 / 需迁移 / 破坏性（放弃旧档）"。
- 条目**可追溯到工作项**（任务号或文件），便于回溯。
- **未发布的变更**放在 `[Unreleased]` 段，发布时转为正式版本段。

### 6.3 补丁说明（玩家语言）模板
```
【本次更新 · v0.1.1】

■ 更好玩了
- 第 4 关的难度曲线更顺了，不再一上来就被卡住

■ 修好了
- 修了一个小问题：暂停后快速点"重玩本关"偶尔会卡住

■ 一个说明
- 你的最高分和关卡进度会完整保留，放心更新

感谢你玩《砖阵》！有问题欢迎反馈。
```
> 原则：**说"玩家能得到什么"，不说"我们改了什么代码"**。修复类条目要给"现象"而非"函数名"。

## 7. 版本发布节奏（建议，非强制）

| 类型 | 触发 | 版本位 | 是否提审 |
|---|---|---|---|
| 开发迭代 | 日常提交 | 内部构建号 | 否 |
| 里程碑版 | 一个功能批次完成 | MINOR | 是（体验版/提审） |
| 修复版 | 线上问题修复 | PATCH | 是 |
| 破坏性版 | 存档不兼容变更 | MAJOR | 是，且需玩家公告 |
