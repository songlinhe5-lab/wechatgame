## 2. 三案对比与推翻理由

| 案 | 结构 | 进关交互数 | 判定 | 理由（逐条，不含偏好） |
|---|---|---|---|---|
| **方案 1**（用户） | 首屏走马灯橱窗，每橱窗 = 类别 → 类别内关卡 | 2（选类别 → 选关） | ❌ **推翻** | ① **类别无数据**：`design/levels/manifest.json` 全部条目 `pack: "main"`，关卡 JSON **无 category/theme 字段**，9 关名为 `studio-{n}-{hash}`（随机入关）⇒ 类别只能靠人工打标或派生（§5）；② 走马灯需要横向滚动，而 9–12 格**一屏放得下**（现 `levelsLayout()` 4 列×3 行 = 12 格已实装）⇒ 滚动成本无收益；③ 主理人自设硬前提「类别数 3~5」在当前 9 关下**无法满足**（9 关分成 3 类 = 每类 3 格 = 空架，分成 5 类 = 每类 1.8 格 ⇒ 类别页比作品墙更空） |
| **方案 2**（用户） | 主菜单一个二级入口 → 橱窗页（类别） → 关卡 | 3（入口 → 类别 → 选关） | ❌ **推翻** | ① 交互数 3 ≥ 方案 1，且**把「作品吸引力」藏到二级页**——这恰是方案 1 想解决的留存问题，方案 2 反向放弃；② 多一屏 = 多一次返回手势 = 微信小游戏首屏流失面 |
| **方案 3**（本单） | 主菜单 = 招牌 + 木框橱窗作品墙（可点）+ 主钮；类别按关数阈值延迟生效 | **1**（点格 / 点主钮） | ✅ **采** | ① **零新增数据字段**：陈列序由难度分 `DI` 派生（`level-difficulty.md`，复用现有关卡数据）；② 交互数降到 **1**（下限）；③ 与 `screens.md` S0 的「招牌 + 木框橱窗 + 木主钮」**版面同构**，只把「橱窗纯装饰不可点」翻转为「可点」；④ 类别作为**阈值机制**而非**当前结构**，30/60 关时按 §4 公式自动长出，无需重做架构 |

> **对主理人倾向的回应（部分推翻，理由在此）**：主理人「首屏即内容 + 小铺橱窗语义在首屏成立」的判断**本单全盘采纳**（这是方案 3 的骨架）；但「类别数要少（3~5）」的硬前提**本单改判为「类别数应为 0」** —— 不是「少」，是**当前不存在**。少 ≠ 零：3 类 × 3 格的作品墙，其「展品感」弱于 1 屏 × 9 格。

## 3. 规模推演与阈值（9 / 30 / 60 / >60）

### 3.0 配置项结构（**第三轮核心：全部可配，不写死**）

> 住 `levels-spec.md §5.0.x`（设计真源）+ `tuning.ts`（落码副本）；**不进 `systems-index §3`**（判例同 `PAUSE_PANEL_H`）。
> ⛔ **作废（第二轮）**：~~`WALL_CAPACITY = 12` 固定~~ · ~~`CATEGORY_MAX = 5` 固定~~ · ~~每类关数 = `n / K` 均分~~。

```json5
// WallConfig —— 作品墙与类别的**唯一**配置入口
{
  wall_capacity:      12,          // ✅ 可配：一屏作品格数（= 现 levelsLayout() 4×3，实装值）
                                   //   改此值须同步复核 TOUCH_MIN 88 与格缩略可辨性
  wall_overflow_mode: 'tab',       // ✅ 可配：'tab' | 'carousel'（走马灯）—— 二选一，**不并存**（§3.5）
  category_dimension: 'di',        // ✅ 可配：'di'(Q1=丙) | 'size' | 'theme' | 'colors'
  category_max:       5,           // ✅ 可配：类别数上限（横向浏览成本上限）—— **用户 Q4 硬要求**
  category_min:       2,           // ✅ 可配：类别数下限（= 1 等价于不分栏）
  category_floor:     8,           // ✅ 可配：一类最少关数；不足则自动降 K，不产生「空架」
  category_split:     'quantile',  // ✅ 可配：'quantile' 按 DI 分位自适应（**每类关数由数据定**）
                                   //          | 'explicit' 按 category_sizes 显式切
  category_sizes:     null,        // ✅ 可配：number[]，仅 'explicit' 生效；
                                   //   sum 须 === n，否则**回落 'quantile' + 告警不中断**
}
```

**默认值策略（四条，逐条给理由）**：

| # | 默认值 | 为什么是它 |
|---|---|---|
| D-1 | `wall_capacity = 12` | **沿用实装值零新常量**（`levelsLayout()` `cols=4, cellSize=120, gap=22`，`meta-view.ts:152-154`）；非设计偏好，是现状 |
| D-2 | `category_max = 5` | 横向浏览成本上限：最坏 5 次切换。**可配** ⇒ 用户 Q4 的「随版本升级可改」已满足，不必现在重定 |
| D-3 | `category_split = 'quantile'` | **零配置、自适应**：关数变了不用改配置。且难度带 = 按 `DI` 切 ⇒ 每类落多少关**本就该由数据决定** |
| D-4 | `category_sizes = null` | 默认不显式切；需要「类别1=7 关、类别2=5 关」这类**人工编排**时才填 ⇒ 满足「每类数量不固定、根据配置来」 |

> **⚠ 重要口径修正**：启用 `category_split = 'quantile'` 后，**不再存在「每类关数 = n / K」这个等式**。每类关数是 `DI` 分位的**产出**，不是除法的结果 —— 这正是用户 Q4「每个分类里的关卡数量不固定」的落点。

### 3.1 派生公式（可落码，单一真源）

```
// 类别数 K —— 由配置 + 关数 n 派生，**不是常量**
K(n) = 0                                                     if n ≤ wall_capacity          // 无类别、无第二机制
     = clamp(ceil(n / wall_capacity), category_min, category_max)   // 'quantile' 模式
     = clamp(category_sizes.length,    category_min, category_max)  // 'explicit' 模式

// floor 修正（防「空架」）：每类平均关数 < category_floor ⇒ 降 K，不降则分栏无意义
while (K > 1 && floor(n / K) < category_floor)  K--

// 形态
形态(n) = 单层作品墙                              if K === 0
        = wall_overflow_mode + 类内滚动            if K ≥ 1 && 某类关数 > wall_capacity
        = wall_overflow_mode                      otherwise
```

> **与原第二轮公式的差异（诚实登记）**：第二轮写死「`n > 60` ⇒ `CATEGORY_MAX=5` + 类内滚动」—— 那是把 `wall_capacity=12` 与 `category_max=5` 乘出来的隐含常数（12×5=60）。配置化后 **60 不再是常数**，它由 `wall_capacity × category_max` **派生** ⇒ 改任一配置，阈值自动跟着动。

> ⚠ **本表是「默认配置下的推演」，不是常量表**。改配置 ⇒ 本表全部重算（如 `wall_capacity=16` ⇒ 60 变 80）。落码**只读配置**，不得抄本表数字。

**为什么「每类关数」列不再给数字（直接回答用户 Q4）**：
`split='quantile'` 下，分带边界 = `DI` 的分位点 ⇒ **每类落多少关由关卡数据的 DI 分布决定**。现池 `DI` 分布已证明**极度不均**（54.3 → 538.0，首末比 9.91，L9 独占 538）：若 30 关里有 1 关像 L9 这样的离群大盘，等频分位会把它单独甩进一类 ⇒ 该类可能只有 1–3 关，而中间带可能挤 10+ 关。**这是数据的事实，不是配置的缺陷**。要强行固定每类关数 ⇒ 用 `split='explicit'` + `category_sizes`。

### 3.3 9 关如何分配（直接回答）

**不分配。** 9 关按难度分 `DI` 升序**平铺一屏**（4 列 × 3 行 = 12 格，占 9 格、余 3 个虚线空槽）。

**硬证据（实测，非推定）**：现池 9 关的**入关序 ≠ 难度序** ——

| 关号 | L1 | L2 | L3 | L4 | L5 | L6 | L7 | L8 | L9 |
|---|---|---|---|---|---|---|---|---|---|
| `DI`（难度分） | 54.3 | 132.8 | 89.7 | 86.3 | 206.0 | 143.4 | 118.9 | 78.8 | **538.0** |

⇒ 按关号陈列 ⇒ 玩家第 1 格（L1，DI 54）与第 9 格（L9，DI 538）**难度差 9.9 倍**，而中间 L8（DI 78.8）比 L2（132.8）还简单。**按关号陈列 = 难度乱序**，这是「不能裸用关号」的实测判据，也是 §5 类别维度选「难度带」的直接依据。

**按 DI 升序的陈列序（= 本单建议的墙序）**：
`L1(54.3) → L8(78.8) → L4(86.3) → L3(89.7) → L7(118.9) → L2(132.8) → L6(143.4) → L5(206.0) → L9(538.0)`

### 3.5 走马灯口径澄清（**第三轮新增，回答 §3 的口径差**）

**判断：用户是 (b)——用「橱窗」指代陈列概念，不是 (a) 要走马灯机制。** 三条判据：

| # | 判据 | 说明 |
|---|---|---|
| J-1 | **语境** | 该句出现在**命名讨论**里（「slogan = 拼豆小橱…『拼豆小铺』这个名字是否合适」），焦点在**词义**（铺 vs 橱），不在交互机制 |
| J-2 | **回应面** | 用户本轮逐条回了 Q1/Q2/Q4/Q6/Q8，**无一条是对第三案的异议**；而 Q2 = 作品格可点**正是第三案的核心机制** ⇒ 用户是在第三案框架内回应 |
| J-3 | **语义** | 「橱窗」在中文里**本来就指陈列装置**（商店的玻璃窗），不是「会转的轮播」。用户第一轮原话是「首屏**走马灯**橱窗」——「走马灯」是独立修饰词；本轮**删掉了「走马灯」三字**只留「橱窗」⇒ 读法应为「陈列概念」 |

**但用户可能是 (a) 的情况也要能接住 ⇒ 给出无条件生效的口径（两种读法下都成立）**：

1. **「橱窗」模块名与视觉语义 —— 保留**（第三案 L1 层本来就画了木框橱窗，§5.2）。这不是让步，是本案原有内容。
2. **走马灯机制 —— 当前不实现**，理由是第二轮的实测判据（9 关一屏放得下 ⇒ 横向成本 0）。
3. **保留条件（可落码，写进配置）**：走马灯与 tab 是**同层互斥**的溢出模式，`wall_overflow_mode` 二选一，**不并存**（二者都解决「一屏放不下」，并存 = 两套导航语言）。

**切换判据 = 类别维度是否有序**：

| `category_dimension` | 有序？ | 溢出模式 | 理由 |
|---|---|---|---|
| `'di'`（Q1=丙，难度带） | ✅ **有序** | **`tab`** | 难度有先后 ⇒ tab 的「顺序感」是信息，走马灯的「循环感」会抹掉先后 |
| `'size'`（尺寸带） | ✅ 有序 | `tab` | 同上 |
| `'theme'`（题材） | ❌ **无序** | **`carousel`** | 题材并列无先后 ⇒ 走马灯的「并列循环」更贴切，tab 会伪造一个不存在的顺序 |
| `'colors'`（色数带） | ✅ 有序 | `tab` | 同 `'di'` |

⇒ **因 Q1 = 丙（难度带 = 有序）⇒ 默认 `tab`，走马灯不启用。**
4. **迁移路径（折中，两种读法都满足）**：`wall_overflow_mode` 是配置项 ⇒ 未来若 (i) 改 `category_dimension` 为题材，或 (ii) 把 `wall_capacity` 下调（格放大、一屏变 6 格）使得 `n=9` 也溢出 ⇒ **改一个配置即切走马灯，零架构重做**。这就是对用户 (a) 读法的兜底。
5. **⛔ 不做的**：不为「可能的走马灯」预留视觉资产 / 不现在写轮播动效时长（`tokens.md §6` 零新增毫秒红线不破）。真要切时，由林绘澄走 art 单补。

### 3.6 分带模式与「每类关数不固定」（**用户 Q4 的第二半**）

| 模式 | 边界怎么定 | 每类关数 | 何时用 |
|---|---|---|---|
| **`'quantile'`**（默认） | `DI` 的**等频分位点**（`K−1` 个切点，按 rank 均分） | **由数据定，不固定** | 默认；关数增长不用改配置 |
| `'explicit'` | 按 `DI` 升序**切前 `category_sizes[0]` 个、再 `[1]` 个…** | **= 配置数组**（可不均等） | 需要人工编排（如「入门 7 关、进阶 5 关」） |

- **降级红线**：`sum(category_sizes) !== n` ⇒ **回落 `'quantile'` + 告警**，**不报错、不中断启动**（沿 `ux-spec §6.3` 第三行「安全降级优先于报错」）。
- **tie-break**：分位点落在两关 `DI` 相等处 ⇒ **关号升序**（零 RNG，铁律 L4）。

| 选项 | 维度 | 数据来源 | 评价 |

### 5.3 logo 尺寸档位（可重算，不许只抄数）

- 招牌可用宽 `W_avail = DESIGN_W − 2 × space_screen_edge = 750 − 48 = **702**`（`space_screen_edge` 24，`tokens.md §4`）
- 字模 = **8×8 珠点阵**／字；4 字；字间 = 半字 = `4d` ⇒ **总宽 = 4×8d + 3×4d = 44d**
- 上界：`44d ≤ 702` ⇒ `d ≤ 15.95` ⇒ **d_max = 15**
- 下界：珠面 = `d − BEAD_GAP(2)` ≥ **8**（同 `BEAD_DRAW_INSET` 判例族的可辨地板）⇒ `d ≥ 10`

| 档 | 珠距 d | 招牌总宽 | 字高（8d） | 用途 |
|---|---|---|---|---|
| **大（默认）** | **15** | 660 | 120 | 主菜单招牌 |
| 中 | 13 | 572 | 104 | 高屏/窄屏回落档 |
| 小 | 11 | 484 | 88 | `E2 大字号` 或极端窄屏 |

- **与渲染的关系（硬）**：`d = 15` = `BEAD_PITCH(32) × 0.469` ⇒ **落在 `CAMERA_ZOOM_MIN` 0.2 之上** ⇒ 复用珠体绘制 + 缩放档即可，**零新绘制通道**（`screens.md` S0 接线约束 ①）。
- **图元成本（诚实，不预支）**：4 字 × 64 格位 = 256 格位；汉字点阵填充率约 30–45% ⇒ **≈ 77–115 颗珠/招牌** `[待实测]`。属 `risks.md` K-6 的「图元随珠数线性增长」面 ⇒ **落码须按 K-051 差分复算 + 封箱复评**，本轮不写实测值。

### 5.4 与「开始」主钮的关系（三条硬口径）

1. **主钮 = 唯一 1 次交互「继续」通道**：点 ⇒ 开**当前关**（`maxUnlockedLevel` 最远关）+ 扣 1 心（§3.14 `STAMINA_START_COST`）。**语义不变**（`ux-spec §6.3` v1.14 / `beads-shell.ts:14`）。
2. **作品墙格 = 1 次交互「选关」通道**：点**已解锁**格 ⇒ 进该关 + 扣 1 心。**未解锁格 = 虚线空槽、零热区、零响应、零事件**（沿用 `levelsLayout()`「shell 只接已解锁项」的现行实现）。
3. **二者并存不冲突**：主钮走「当前关」、墙走「指定关」；视觉上主钮 = 木（T3 主）、墙格 = 纸（T1）。**不存在第三入口**（§2 随屏单通道纪律：`open-levels` 钮退役，见 §7）。

## 10. 命名裁定（**回答用户提问**）

### 10.1 裁定（一句话）

> **游戏名 = 「拼豆小铺」（不动）｜主界面橱窗模块名 = 「拼豆小橱」（采纳用户拟议，但改任模块名）｜slogan = 「一颗一颗，拼出你的小铺」。**

### 10.2 为什么「拼豆小橱」不作 slogan（改判用户拟议，给理由）

| # | 理由 | 说明 |
|---|---|---|
| N-1 | **词性不对** | slogan 是**一句话**（承诺/邀请），「拼豆小橱」是**名词短语**。招牌下挂一个与游戏名只差一字的名词 ⇒ 读起来像**别名/副名**，不像 slogan |
| N-2 | **语义重复** | 「拼豆小铺」与「拼豆小橱」**4 字里 3 字相同** ⇒ 上下两行几乎同名，视觉上是「再说一遍」，信息增量为零 |
| N-3 | **slogan 位已被 §6 Q3 占住** | Q3=①「一颗一颗，拼出你的小铺」—— 这句**同时**完成两件事：讲玩法（一颗一颗）+ 呼应「铺」字。换成「小橱」两件事都没了 |

### 10.3 为什么不改游戏名为「拼豆小橱」（推翻用户提问的隐含选项）

| # | 理由 | 类型 |
|---|---|---|
| **N-4（最硬）** | **珠拼点阵可辨性**：招牌是 **8×8 珠点阵** `beadText`（§5.3）。「铺」12 画（钅5 + 甫7）；「橱」**16 画**（木4 + 厨12），且「厨」内部含「豆」「寸」多层嵌套 ⇒ 8×8 下**必然糊成一团**。这是**落码级硬约束，不是审美偏好** | 硬 |
| N-5 | **图元成本**：招牌填充率随笔画数上升 ⇒ 「橱」比「铺」多约 4 画 ⇒ 珠数上涨，正踩 `risks.md` K-6「图元随珠数线性增长」面 | 硬 |
| N-6 | **识读/搜词**：「铺」比「橱」常用（小铺/店铺 vs 衣橱/橱窗，前者词频显著更高）⇒ 微信搜索联想与口口相传更友好 | 中 |
| N-7 | **外延大小**：「铺」涵盖 买/卖/做/藏/陈列 **全链路**；「橱」只涵盖**陈列**一类 ⇒ `铺 ⊃ 橱`。未来加收藏册/图鉴/交易，「铺」仍成立 | 中 |
| N-8 | **既有裁定成本**：`app_name = 拼豆小铺` 是用户 **2026-10-07 已裁**且已写入 `tokens.md §7`（唯一出处），改它 = 推翻用户自己的当日裁定 + 同步一批文件 | 中 |

**⇒ 三者的层级关系（这是最干净的结法）**：**「小铺」是店，「小橱」是店里那只陈列柜** —— 上下位天然成立，零语义冲突。用户拟议的**词义完全保留**，只是落到了它本该在的层。
