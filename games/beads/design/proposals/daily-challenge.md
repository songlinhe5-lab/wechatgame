## 1. 定位与范围

**一句话定位**：每天用本地日期种子从 8 关图案库确定性派生一张"今日图案"，复用既有玩法与判定打一次带连胜记录的挑战——给成就型玩家一个每日回访理由，零服务器、零新玩法。

**范围分层**（对齐 concept §7）：

| 层 | 每日挑战相关内容 | 状态 |
|---|---|---|
| MVP（验收线） | —（**不含任何每日挑战内容**） | demo 当前冲刺**不做** |
| Should | — | 不涉及 |
| **Could** | **每日挑战**（本文全部内容） | 供后续立项评审，**未立项** |
| Won't | 排行/好友对抗、补签、每日奖励、联网校验（见 §7） | 永久砍（demo 阶段） |

**立项前置条件**（评审时核对）：MVP 8 关全量验收通过 + S6–S9 GDD 交付后有余量，方可进入排期讨论；届时本文升级为正式 GDD（八节）并随冻结常量回写 systems-index §3。

## 2. 机制草案

### 2.1 入口与入口条件

- **入口位置**：关卡选择界面（D10 沿用 breakout 判例方向的界面）新增一张「每日挑战」入口卡，视觉沿用 `art-bible.md` §6 语言：`panel_surface` 白卡 + 1px `panel_border` + 强调色图标（`accent_purple` 或 `accent_blue`，**只沿用已定色值，不定义新色**）+ 日期文案；今日已完成时叠加 `success` 绿对勾角标。
- **热区**：入口卡为 UI 控件，热区 ≥ `TOUCH_MIN`（§3.8）；命中与路由归 S2 扩展（见 §3）。
- **入口条件**：`[待确认]` 二选一——
  - (a) 无门槛：可进第 1 关即可进每日挑战（推荐：与"治愈、低门槛"支柱 1 一致，实现最少）；
  - (b) 通过第 1 关解锁（`unlockedLevel ≥ 2`，读 S8 进度）。
- **进入时机**：从关卡选择点击入口 → 派生今日关卡 → 进入 S1 `PLAYING`（复用六状态机，见 §3）。
- **当日重试**：当日不限挑战次数；失败走 `GAME_OVER` →「重试本关」（S5 §2.4 整关重置五项语义照旧）；星级取**当日最优**记录。

### 2.2 确定性派生（核心机制）

**种子**：`seed = hash(本地日期键)`。日期键取设备本地时区 `YYYYMMDD` 字符串 `[待确认]`（跨时区/夏令时不追求公平，本地玩家自洽即可）；hash 算法 `[待确认]`（提案：FNV-1a 32 位，纯整数运算、引擎无关、可单测，符合 AGENTS.md L4 确定性 RNG 纪律——落码走 `services.rng` / `createRng(seed)` 注入，**禁止 `Math.random`**）。

**选题规则**（从 8 关图案池中确定性选 1）：

1. 候选池 = `DEMO_LEVEL_COUNT` 关全部图案（ADR-0004 行字符串，`BEAD_CHARSET` 合法）；
2. 可选筛选档：按当日 seed 从「低色日（用色 ≤ 4）」「高色日（用色 > 4）」二选一，再在档内按 seed 取模选题 `[待确认]`——不通过"删色改图案"实现限定色数（改字符=改图案资产，禁止，见 §7）；
3. **防连日重复**：若 seed 直接取模与昨日图案相同 → 沿候选池顺序后移 1 位 `[待确认]`（仅依赖昨日记录，仍纯本地）。

**变体规则**（只允许**不改动图案字符数据**的变换 + 区间内参数覆写）：

| 变体维度 | 规则 | 约束与依据 |
|---|---|---|
| 图案镜像 | seed 决定四态之一：原样 / 水平镜像 / 垂直镜像 / 180° 旋转 `[待确认]` | 镜像与 180° 旋转 = 行字符串反转/行序反转，行列数不变、`x` 锁定格语义不变、仍过 `validateLevel()`；**90° 旋转默认不用**（13 列图案转置后 13 行 > `GRID_MAX_ROWS`，违反 §3.3） |
| 供料间隔覆写 | `SPAWN_INTERVAL = DAILY_SPAWN_INTERVAL`（附录 A） | 必须落在关卡覆盖合法区间 [2.0, 6.0]（§3.4）——覆写走**关卡数据覆盖通道**，不改常量本身 |
| 时长覆写 | `LEVEL_TIME = DAILY_LEVEL_TIME`（附录 A） | 必须落在合法区间 [180, 420]（§3.5） |
| 杂色数量覆写 | 当日 decoy 数量由 seed 在 [0, `DECOY_COLORS_MAX`] 内确定 `[待确认]` | 不超 §3.2 上限；杂色色值仍从 `BEAD_PALETTE` 取，不入图案 |

**派生出口**：以上产物组装为一个**虚拟关卡描述**（图案矩阵 + 覆写参数），走与普通关卡相同的 `validateLevel()` 校验（BOOT 流程，架构文档 §6）——校验失败属程序 bug，按 core-loop §2.1「不允许带病进入 PLAYING」处理。

**同日一致性**：同一日期键下，任意次进入派生结果（图案、镜像态、供料间隔、时长、杂色数）完全一致。

### 2.3 完成判定与星级（复用 S7）

- 派生关卡即普通关卡：可填格全满 → S3 完成判定 → S1 `LEVEL_CLEAR` → `level:cleared {levelId, remaining, ratio, stars}` 照常广播；
- 星级判定**原样复用** `STAR3_RATIO` / `STAR2_RATIO`（§3.7），不引入独立阈值；
- 结果去向分流：`level:cleared` 的 stars 写入**每日记录**（§4 的 `daily` 字段），**不覆盖**关卡模式的星级存档——两套进度互不污染 `[待确认]`；
- 归零失败照走 `level:failed`，无额外惩罚。

### 2.4 连续打卡激励（纯本地）

- **连胜计数**：按本地日期键比较——今日完成且昨日记录也为完成 → `streak + 1`；今日完成但昨日无完成记录 → `streak = 1`；断签**无补签、无惩罚**（只是归零重计）`[待确认]`；
- **表现**：入口卡显示连胜数（如「连胜 N 天」纯文本，样式沿用 `text_primary`/`text_secondary`）；结算面板一行文案；
- **不与任何云端/排行/奖励挂钩**（§7）；连胜只做**回访动机的展示层**，不接入经济系统（本作无货币，concept §4 不设分数膨胀）；
- **跨天边界**：挑战进行中跨越本地午夜 → 以**开始挑战时的日期键**结算 `[待确认]`（避免玩到一半日期变更导致记录错乱；实现为派生时快照日期键）。

## 4. 存档增量（沿用 S8 版本化迁移纪律）

> 键名与字段命名**归代码侧**（D9 + systems-index 刻意例外：`wxgame.beads.save.v1`，`save-schema.ts` 定义）；本节只提语义与结构提案，字段名以代码实现为准。

**提案**：在现有 v1 存档根上新增可选对象 `daily`（字段级全部 `[待确认]`）：

| 语义字段 | 类型（语义） | 说明 |
|---|---|---|
| `lastDate` | 日期键字符串 | 最近一次**完成**的日期键（`YYYYMMDD`），连胜与防连日重复的判定依据 |
| `streak` | 非负整数 | 当前连胜天数（§2.4 规则） |
| `bestStars` | 日期键 → 1–3 映射 或 仅当日记录 | 当日星级（取最优）；是否保留历史日期记录 `[待确认]`——demo 建议只存当日，历史不入档 |

**迁移纪律**（对齐 S8 / `core/save` 判例）：
- 旧存档无 `daily` 字段 → 视为 `streak=0、lastDate 空、今日未完成`，**安全降级不报错**（`core/save` 永不抛异常判例）；

- 每日记录不参与 BOOT 降级判据（`daily` 字段损坏只清 `daily` 子对象，不动关卡进度）`[待确认]`。

## 6. §8 验收标准草案（4–6 条，全部 `[待冻结]`）

> 正式冻结后归入未来每日挑战 GDD §8，QA 直接引用造用例；冻结前**不得**据此写测试。

1. **同日确定性**：同一本地日期键内任意次进入每日挑战，派生结果（图案、镜像态、`SPAWN_INTERVAL`、`LEVEL_TIME`、decoy 数）逐项一致；固定 seed 下派生函数输出可快照测试。
2. **跨日变更**：修改系统日期（或注入日期键）→ 派生结果随之改变；抽查连续 ≥14 个日期键，派生关卡与相邻两日均不相同（防连日重复规则生效）。
3. **主链路复用**：每日挑战全程走 S1 六状态与既有 13 事件——`bead:placed`→`level:cleared`（含 stars，按 `STAR3_RATIO`/`STAR2_RATIO`）、归零→`level:failed`，与普通关卡无事件差异；星级写入每日记录且**不改动**关卡模式星级存档。
4. **纯本地断言**：全程（入口→游玩→结算→连胜更新）不触发任何网络/广告 API（代码审计 + 事件计数断言 =0）；断网状态可完整游玩。
5. **连胜记账**：连续两天完成 → `streak=2`；隔一天完成 → `streak=1`；同日重复完成 → `streak` 与星级记录不变（仅当日最优星级可能刷新）。
6. **存档兼容**：无 `daily` 字段的旧存档进入每日挑战不崩溃、按"未完成今日/连胜 0"降级；`daily` 子对象损坏仅清除该子对象，关卡进度与设置不受影响。

## 9. 首期形态：Boss 关限时复挑（v0.2 · 用户 2026-10-26 定）

> **用户原话**：「在一组任务里随机产生，首期只有一个任务组，已通 3 星的 boss 关，随机挑选一个 boss 关设定比 3 星更高的挑战时间，提供 3 次机会，可以用各种道具等。奖励会比正常 3 星高出一个等级，比如 2 倍或者 3 倍首通，这个需要计算后定。挑战成功后，标识完成每日挑战。」
> 性质：`[提案·待拍板]`，零落码。

### 9.1 与 v0.1 的关系

| 维度 | v0.1（作废为主形态） | **v0.2 首期** |
|---|---|---|
| 关卡来源 | 本地日期种子**派生**虚拟关卡（镜像 + 参数覆写） | **直接复用**已通 3★ 的 Boss 关，零派生 |
| 难度手段 | 覆写供料间隔 / 时长 / 杂色数 | **更严时限**（比 3★ 更快）+ 3 次机会上限 |
| 货币关系 | 「本作无货币」，只做展示层 | **接入经济**：给豆子奖励（见 §9.5） |
| 实现成本 | 高（派生器 + 校验 + 同日一致性） | **低**（选题 + 覆写 `time` + 计数） |

⇒ v0.1 §2.2 派生机制**保留为后续扩展备选**（用户原话「挑战可以先简单做，后续可以做更多的挑战」）。

### 9.2 选题规则（首期：单一任务组）

- **候选池** = 玩家**已达 3★** 的 Boss 关（`levels` 里 `kind === 'boss'` 且该关最高星 = 3）。首期首期只有一组（Boss 组），不做多组。
- **选取** = 在候选池内按**本地日期种子**随机取 1（确定性：同一天多次进入选中同一关；跨天变化）。种子算法沿用 v0.1 §2.2 的 FNV-1a 提案，落码走 `createRng(seed)`，⛔ 禁止 `Math.random`。
- **候选池为空**（尚无任何 Boss 关 3★）⇒ 入口置灰 + 文案「先把 Boss 关打到 3★」。
- **不要求重新解锁**：已通 3★ 即永久可被抽中，池子随进度自然增长。

### 9.3 时限规则（关键：不能用统一比例）

```
挑战时限 = 该关 3★ 预算 × DAILY_CHALLENGE_TIME_K
硬下限  = 该关最省解步数 × SEC_PER_STEP × 1.02   ← ⛔ 低于此值即不可达
```

- **`DAILY_CHALLENGE_TIME_K` 建议 = 0.93**（`[待拍板]`）
- ⚠ **0.85 这类激进值是错的**：L9（Boss）3★ 预算 228 s，最省解 50 步 × 4.14 s/步 = **207 s**；228 × 0.85 = 194 s < 207 s ⇒ **数学上不可能完成**。所有 Boss 关必须逐关按最省解验算，判例同 v1.87 的 `TIME_A` 定标流程。
- L9 实算：228 × 0.93 = **212 s**（距最省解下限 207 s 留 5 s 余量）⇒ 难度从「留 5 步」提到「留 1 步」，已是显著提升。
- **结论**：因为 3★ 本身已是紧平衡（留 5 步），「更严时限」的可用空间只有 **5–9%**。难度提升主要来自「必须接近最优解」，⛔ 不要指望靠压缩时间做出大跨度难度差。

### 9.4 机会、体力与道具

| 项 | 规则 | 依据 |
|---|---|---|
| 每日机会 | **3 次/day**；3 次用尽即当日结束（失败计入次数） | 用户令 |
| 体力 | **不扣心**（挑战是额外内容，不占体力池） | 避免 3 次机会变成 3 心负担 |
| 道具 | **照常可用**：每型免费 1 次，超出用豆子/广告（双通道） | 用户令「可以用各种道具」 |
| 道具额度 | 与普通关共用同一套每关计数，⛔ 不单独放开 | 防止道具额度在挑战里被放大 |
| 失败处理 | 可立即重试（消耗 1 次机会），不走 `GAME_OVER` 引流 | — |

### 9.5 奖励计算（用户要「计算后定」）

基准：Boss 关 3★ 首通 = **180 豆**（`CLEAR_COIN_FIRST_BOSS` 三档累进 40 + 60 + 80）。

**期望值表**（日产现有 = 90.71 = 签到 45.71 + 复刷 45）：

| 奖励档 | 名义 | p=20% | p=30% | p=40% | p=50% |
|---|---|---|---|---|---|
| 1.5× | 270 | 54 | 81 | 108 | 135 |
| **2×（推荐）** | **360** | 72 | **108** | 144 | 180 |
| 3× | 540 | 108 | 162 | 216 | 270 |

**结论：取 2 倍 = 360 豆**，`[待拍板]`。理由：

1. 目标成功率 25–30%（3★ 留 5 步 → 挑战只能留 1 步，估成功率偏低）⇒ 期望 **90–108/天**，与现有日产 90.71 基本持平，**不破坏产出结构**；
2. 3 倍（540）在 p=30% 时期望 162/天 = 现有 1.8 倍 ⇒ 玩家会放弃正常玩法只刷挑战，⛔ 不建议；
3. 挑战要求「已通 3★ 的 Boss 关」⇒ 天然是**后期内容**，不冲击新玩家前期经济，所以可略高于日常而不通胀。

⚠ **经济净流入分析（v0.2 修订，用户 2026-10-26 指正）**：初稿只算奖励、没算**同场景消耗**，结论偏悲观。实际净流入取决于「道具使用率」——

| 道具使用情况 | 单次尝试付费 | 3.3 次尝试消耗 | 期望奖励（p=30%） | **净流入/天** |
|---|---|---|---|---|
| 只用免费（每型 1 次 × 3） | 0 | 0 | 108 | **+108** |
| 每次买 1 次（约 30 豆） | 30 | 99 | 108 | **+9** |
| 每次买满 2 次（约 75 豆） | 75 | 248 | 108 | **−140** |

**结论：中位净流入 ≈ 0（+9 豆/天），挑战是「自我对冲」的消耗场景** ⇒ 用户判断成立：
- 奖励豆子进来，被更严的时限逼着花回道具 ⇒ 净流入有限；
- 而道具/扩容的付费通道是「**广告 or 豆子**」⇒ 挑战同时是**激励视频渗透率的放大器**（不看广告就花豆子，两者都算变现）。

⇒ **§14.4 外观总价不必重算**（1270 不改成 2650），改为**上线后监控「挑战场景道具付费率」**这一个读数即可。

⚠ **但成立的前提是「挑战难度必须高到免费 3 次道具不够」**：

| 难度 | 后果 |
|---|---|
| 太简单（免费道具就够） | 净流入 → **+108/天**，日产翻倍，皮肤被提前买穿 ❌ |
| **刚好（免费不够、付费刚好）** | 净流入 ≈ 0，经济稳定 ✅ |
| 太难（用满也过不了） | 成功率崩 → 玩家放弃挑战，内容白做 ❌ |

⇒ **挑战难度是经济闸门，不是体验选项**。`DAILY_CHALLENGE_TIME_K = 0.93` 与「每局免费 3 次道具」共同决定净流入，两者任一改动都必须重跑本表。

### 9.7 与「托盘扩容」的关系（现状核对，防误设）

| 项 | 现状 | 对本设计的意义 |
|---|---|---|
| 托盘扩容通道 | **只有广告路**（`requestTrayExpand` → `rewardedAd`），**无豆子路** | 用户「要不广告要不豆子」的设想**尚未落码**；若要加豆子路，须另开变更单 |
| 扩容档位 | 12 → 24 → 48，**共 2 档，永久生效** | 最多买 2 次 ⇒ **一次性买断出口，不能当持续消耗点** |
| 若要用作持续消耗 | 需改为「每局租用」（季/次制） | 与「永久扩容」语义冲突，属新设计，⛔ 本批不做 |

⚠ **道具额度是「每局重置」不是「每关」**：`_resetPowerups()` 在**换关 / 重试 / 新局**都会调用（见 [`beads-game.ts:1945`](../../src/game/beads-game.ts)）⇒ 每次重试都会刷新「每型免费 1 次 + 每局可买 2 次」。所以 3 次挑战机会的**理论最大**豆子消耗 = 3 × 75 = **225 豆**，这是净流入表里「买满 2 次」那行的来源。

### 9.6 完成标识与记录

- 成功 ⇒ 写当日记录 `daily: { dateKey, levelId, timeMs, cleared: true }`，关卡选择入口卡叠 `success` 绿对勾角标（沿用 v0.1 §2.1 视觉语言）。
- **只记当日一次**：3 次机会内成功即算完成；同一天成功多次不重复发奖（`[待拍板]`：是否允许重复领取？建议**不允许**，避免刷豆）。
- 与关卡模式星级**互不污染**：挑战成绩不计入关卡 3★ 存档（沿用 v0.1 §2.3 分流原则）。
- 记录字段落 `MetaState`（新增 `dailyChallenge` 子结构），须随存档版本迁移。
