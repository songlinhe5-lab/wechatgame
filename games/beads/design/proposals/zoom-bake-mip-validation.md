## 0. 本档回答的核心问题与预测

**问题**：0.2–2.0 连续缩放全程，V / S1 / S2 / M / M+ 五条路径中，哪一条能同时满足画质、闪烁、性能三项要求。

**主理人记录在案的预测**（用户 2026-09-27 提出，本方案的作用是**证实或推翻**它，不是给它背书）：

- 只烘一套 2× 作为唯一烘焙源 **可以**；但**不能**只用这一张图直接缩小到底。
- 缩放跨度固定 10 倍（纹理缩小倍率 = `CAMERA_ZOOM_MAX / zoom`，缩到最小 = 2.0/0.2 = **10**，
  且**与机型无关** ⇒ 该结论在所有手机上一致）；2D canvas 默认缩小过滤在低倍率下会闪烁。
- 最可能的定案 = **一套 2× 烘焙 + 加载时对半派生 mip**（方案 M）。
- ⛔ 本档任何预测都不得被读作已验（K-035/K-040/K-051）。

## 2. 测试素材

- **风格**：`facet-4`（现役默认，大块刻面，最耐缩）／`lineart-18`（线条最多的现有风格）／
  **压力配方** = 1 px 边缘高光线 + 2 px 星光 + 孔内壁暗环（代表美术想往参考图方向加的效果）。
- **颜色** 4 种：黑（暗、对比最强）／奶白（与底色最接近）／高饱和红／中灰蓝。
- **盘面**：32×32 满盘（0.2 倍下整盘可见；1024 颗是最坏绘制数量）。
- 风格入池判据（双指标、C12 主体色不变式）仍按 `bead-visual-style-spec §12`，本方案不改写美术门禁。

## 3. 测试项与判据

### 测试 1 · 静态画质
- 档位：zoom = 0.2 / 0.25 / 0.33 / 0.5 / 0.7 / 1.0 / 1.4 / 2.0，另加 0.37、0.83 这类非整比例点；逐档截图与 R 比误差（逐像素 ΔE 或 SSIM）。
- 分区统计：整颗珠／孔边／高光区。
- **通过线（暂定）**：整颗珠平均 ΔE < 2；孔边与高光区 ΔE < 5。
- 预测：facet-4 在 S1 下 zoom ≥ 0.5 通过，zoom < 0.4 孔边与刻面对角线出锯齿（局部不通过）；
  压力配方在 S1 下 zoom < 0.7 不通过（1 px 线断续）；M / M+ 全程通过。

### 测试 2 · 缩放闪烁（最关键）
- 0.2 → 2.0 以每帧 ×1.01 缩放（约 230 帧），再反向缩回；逐帧记录每颗珠整体与高光区平均亮度，
  与 R 同帧值作差，差值随帧的标准差 = 闪烁指数。
- **通过线（暂定）**：整颗珠 < 1.5 % 亮度；高光区 < 4 %。
- 预测：S1 在缩小倍率 > 约 4（zoom < 0.5）后明显不通过（否掉「只用一张图」的主要依据）；
  S2 在 Chrome harness 多半通过（Chrome 高质量缩小接近 mip 过滤），真机是否支持 `'high'` 未知、必须实测；M 通过。

### 测试 3 · 亚像素平移
- 固定 zoom（0.3 / 0.6 / 1.0），盘面按 0.1 物理 px 步长平移 20 步，测同一闪烁指数
  （检查静止拖动时珠子落在小数像素位置是否跳动）。
- 预测：S1 在 0.3 档不通过，M 通过。若连 M 也不通过 → 增加变量：静止时把绘制位置对齐整数物理像素。

### 测试 4 · mip 切档跳变（只测 M / M+）
- 连续缩放中找出所有切档帧，测切档前后同一颗珠的亮度跳变；人眼录屏复核。
- **通过线**：跳变 < 2 %；放大/缩小方向各录一次，看不出切档点。
- 预测：M 约 1 % 通过；M+ 在压力配方上会在细节消失那一档出现可察觉跳变，需把消失点再往下推。

### 测试 5 · 性能（先判，见 §4 判定流程）
- 32×32 满盘，zoom 0.2 与 2.0 两端点 + 一次连续缩放；比较 V / S1 / M 的 p95 帧时间与纹理内存。
- 环境：harness Chrome（4×、6× CPU 降速）；低端安卓（千元机）微信真机；iPhone 微信真机。
- **通过线（暂定）**：低端机 p95 ≤ 16.7 ms；**烘焙路径至少比矢量快 1.5 倍**，否则烘焙不值得做
  （本项同时补 `bead-visual-style-spec §13.10` 未做的 **D2-E3**）。
- 预测（**v0.3 按双平面重写**；v0.2 的「命令数 −57%」仍为**单珠臂**下的算账 ⇒ 本档不提前改成 N2 假定值，K-051）：
  已填格 = 底图 1 + `blit` 1 + 孔底 1 = **3/格**；空格 = **1 或 2/格**（取决于底图是否合张）
  ⇒ 终局满盘仍 3,072 条，**开局空盘帧自此首次下降**（真数 [待落码实测]）；
  **倍率属待实测**（按测量单禁令 3，`~~快 2–4 倍~~` 不得当已得结论引用）。
  内存按基准 112 px 双张 = **35 色 ≈ 4.7 MB**（预算回到 [待定]，ADR-0027 DEC-7）
  （`~~1440p 下 1.4MB / 加 mip 1.9MB / 落在 2MB 预算内~~` = 整格前旧算、`~~35 色 ≈ 2.3 MB 落在 2.5 MB 预算内~~` = v0.6 单珠算，均作废）。
  ⚠ **v0.3 新增一栏**：预烘文件的**磁盘字节**不属本测试，归**测试 15（包体）**；两者必须分开报。

### 测试 6 · 平台能力探测（两台真机）
- `imageSmoothingQuality` 设置后读回是否生效；棋盘格纹理缩小 8×，看均匀灰（正确平均）还是摩尔纹（只采几点）。
- 预测：iOS / Android 结果可能不一致；**任一端不支持 ⇒ S2 不能作为方案**。

### 测试 7 · 人眼终审
- 低端机真机，三款候选各玩一局 32×32，做连续缩放与拖动，录屏后请美术盲评。
- **通过线**：美术在 M 与 V 之间分不出差别。

#### 测试 10 · 内存（T5）
- 8 / 16 / 35 色 × `BAKE_DPR_CAP` 1 / 1.5 / 2 实测 L1 缓存字节，真机监听 `wx.onMemoryWarning`。
- **通过线**：不触告警；估算对账列改标 **[待定]** —— `~~预期 35 色 ≈2.3MB，预算 [暂定 2.5MB]~~` ⇒

#### 测试 11 · 失效、兜底与烘焙耗时（T6）
- 提升 `bakeSchemaVersion`、清空 L1/L2、模拟缓存未命中，逐帧检查输出；另测关卡加载时烘齐全部纹理总耗时。
- **通过线**：未命中帧与轻量矢量配方逐字节一致，下一帧起命中；烘焙耗时低端机 ≤ 100 ms **[暂定]**。
- ⚠ 口径：一致性比对只对**同一层集真源**成立 ⇒ 先归位 T-215，否则「一致」是假一致（配方失真被烘进缓存）。

#### 测试 12 · 预烘与运行时烘**同源性**（v0.3 新增，ADR-0027 DEC-4）
- 同一 `(styleId, colorIdx, bakeSchemaVersion)`：分别取「构建期生成器产出的文件纹理」与「运行时 offscreen 烘」，
  逐像素对比（含边缘与孔径）；并故意改动层集不重出资产 ⇒ 验 `bake:check` 必红。
- **通过线**：两路输出**逐字节一致**（或差异 ≤ 1/255 且已归因到解码器舍入）；守卫红。不红 = 真源分叉，本 ADR 转 Suspended。

#### 测试 13 · 分包到达时序（v0.3 新增）
- 弱网 / 分包未下载完成时进关：逐帧检查是否先矢量出画、到达后切换是否无感（无闪白/无尺寸跳变）。
- **通过线**：⛔ 空帧；⛔ 同一关内两种形态长期共存（切换只发于整格首次，不逐帧抖）。

#### 测试 14 · 「一张图」机检重设（v0.3 新增，承 §13.8 N2 生效义务）

- **通过线**：三条均有新判据且入 QA 档（属**判据重设计**，⛔ 用基准重捕代替）。

## 4. 判定流程（顺序不可打乱）

1. 先跑测试 5。**烘焙路径没快 1.5 倍 ⇒ 停下重评要不要烘焙**，后续测试不做
   （= `§13.13` 首条；失败 ⇒ 回矢量并限美术层 ≤7，ADR-0025 转 Superseded）。
2. 性能过，且 S1 通过测试 1–3 全部 ⇒ 单张 2× 直接定案（预测：不会走到这里）。
3. S1 不过、S2 过，且测试 6 确认两端真机都支持 ⇒ 单张 2× + 高质量过滤（预测：多半卡在测试 6）。
4. M 通过测试 1–4 ⇒ 定案「只烘一套 2× + 加载时对半派生 mip」（预测的最终结果）。
5. 只有 M+ 能过 ⇒ 美术要的细线/星光在缩小时成灰斑，两条路：**收紧美术规则**（消失点表）后回第 4 步（建议优先），
   或接受每档重烘（那就不再是「一套烘焙」，须回 `§13` 重开规格与预算）。
6. **v0.6 新增两条分支**：测试 8（孔对齐）连续半径 + 0.5px 仍修不掉 ⇒ 退回「孔整枚 live（含内壁）」、

## 6. 与常量批的接口（本批已生效的事实）

- 缩放跨度 = `CAMERA_ZOOM_MAX / CAMERA_ZOOM_MIN` = **10 倍**，绝对档 ⇒ 与机型、与盘的 fit 均无关。
- 烘焙最大档挂 `BEAD_CELL × CAMERA_ZOOM_MAX`（**不再 × fit**）⇒ 烘焙基准倍率 = `CAMERA_ZOOM_MAX`，两者零漂移。
- `zoom < ZOOM_TAP_MIN`（0.7 `[待真机]`）时棋盘 tap 被低倍档吞掉、改焦点放大到 1.0
  ⇒ 真机 playtest 时**放珠手感只在 ≥0.7 段成立**，本方案测试 7 的局内操作需在 ≥0.7 段评估手感、
  低倍段只评估可读性与闪烁。
- ⚠ 已知未验面（本批如实登记，不粉饰）：
  ① 焦点放大的补偿量若越出新档平移悬挑量，会被 `clampCamera` 锁回边缘（板小于视口的盘尤其明显），
  被点格不严格跟手 —— 是否放宽平移锁归体验 playtest / 另案；
  ② 整帧封箱基线（`tests/bead-style-seal.test.ts` 腿 4a/4b）因初始 `zoomSliderT` 由 0 变 ≈0.375
  （滑轨「已选段」rect +1 条）而失效，**须由 QA 按官方复取器重抓**，本批不代改基准数值。
