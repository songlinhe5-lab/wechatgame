## 2. 四个决策点的定稿

### 2.1 D-A：32 挂哪个量（P1 / 草案 D2·D3）→ **`BEAD_PITCH = 32`**

**推荐（甲）**：冻 `PITCH=32` / `GAP=2` 不动 ⇒ `CELL` 降为派生 **30**。

理由（三条，按强度排序）：

1. **语义**。`dip` 的定义量（`ADR-0021 §3`）与物理 5mm **peg 中心距**都是**中心到中心**；源图里相邻豆无缝相邻，「一颗豆占 32 源图 px」量的天然是**含缝格边长**。把 32 挂 pitch，才有「源图 1 px ↔ 渲染 1 设计 px @zoom=1」这条**逐格 1:1**；挂 CELL 则 pitch=34，"统一到同一尺"只统一了一半，剩下 2px 缝是一条新的任意量。
2. **抗漂移**。`CELL` 是**质感量**（美术会为了"露底色/珠形"反复调它），`PITCH` 是**映射量**。冻 pitch、让 cell 派生 ⇒ 质感调参永远推不动 5mm↔32 这条映射；反过来（冻 cell=32）一旦美术动 gap 或 inset，同尺关系立刻破。这正好对上 `ADR-0021 §1` 批评的形状：**别让某个特例读数当恒定量写死**。
3. **零残余继承**。`GRID_MAX=32` 与「1024 源图 = 32×32 最大单图 / 2048 → 2×2 均分四宫零残余」（`tuning.ts:138`、`§3.3` v1.45 注）在旧尺下是**巧合式论证**；采 pitch 锚后升级为**结构性对齐**，studio `PER_BEAD_PX = brand.dip`（`index.html:399`）与游戏 `BEAD_PITCH` 第一次真正同源同值（⇒ §4 加锁断言）。

**备选（如实列出，均已否决）**：

- **乙 `CELL=32 / GAP=2 / PITCH=34`**（我此前草案 §0.4 的默认建议）：珠体比甲大 6.7%，代价是 pitch 落在 34 这条非映射数上，1:1 同尺不成立。⇒ 若真机判「30px 珠面实在太小」，乙是**唯一值得回退的方案**（只搬冻结量、不改规则），但那是**新变更单**，不是本单的附带选项。
- **丙 `GAP=1 → CELL=31`**：多 1px 珠体，换来一条新的任意 gap。否决。
- **丁 `GAP=0 → CELL=32`**：源图格与珠体完全等径、`natW = cols×PITCH` 最干净。否决理由 = gap 是**露底色通道**（L11 目标色垫 = 全格底，靠 gap + inset 才看得见；`BEAD_DRAW_INSET` 6 的真机裁定正是买这条可见性），gap=0 会让邻珠的边光/暗边直接相接、垫色语义消失。
- **`TRAY_SLOT` 是否搬家**：**不搬**（理由与反转登记见 §1.2）。

### 2.2 D-B：顶格 / 占屏（P3）→ **推荐 (a) 接受 + 保留 `fit ≤ 1`，但改写其理由；预案不预登记**

关键复算（**这条决定了 (a) 比 52 基下强得多**；`fit = min(1, 702/natW, 592/natH)`，**竖向窗 592 才是现关表全部盘的绑定轴**）：

| 盘（关表**实测** L00001–L00008） | 52 基 `fit`（绑定轴） | 52 基屏上珠径 | 32 基 `fit` | 32 基屏上珠径 | 变化 |
|---|---|---|---|---|---|
| 14×12（L00003） | 0.952（H） | 47.6 | **1.0** | 30.0 | **−37%** ← 损失最大 |
| 14×13（L00001/2/5） | 0.878（H） | 43.9 | 1.0 | 30.0 | −32% |
| 14×14（L00004，最大盘） | 0.815（H） | 40.8 | 1.0 | 30.0 | −26% |
| 8×15（L00008） | 0.761（H） | 38.0 | 1.0 | 30.0 | −21% |
| 12×16（L00006） | 0.713（H） | 35.7 | 1.0 | 30.0 | **−16%** ← 损失最小 |
| 顶格容纳档 | 13×11 | — | **22×18** | — | 大盘不再靠缩放 |

⇒ 同一复算的两个副产品（均为公式推导，**非实测**）：**① 现 8 关在旧尺下已全部 `fit<1`** ⇒ 旧尺本来就在靠缩放顶着手，本单不是"从不缩到要缩"而是反向；**② 新尺下 8 关全部 `fit=1`** ⇒ 屏上值就是 §2.3 表的 `zoom=1` 值（旧尺不是，两尺对比时最容易错比）。

- **关表内不存在"被 fit 除回去"的盘**：现 8 关均 ≤22×18 ⇒ 新尺 `fit=1`，缩不掉的那一截（屏上珠径 47.6/40.8/38.0/35.7 → **统一 30**）才是真实代价，幅度 **−16% ～ −37%**。`IMPACT-0020a 摘要2`「fit 会把变小的尺子除回去（14×18 屏上 pitch 32.96 vs 33.00，差 0.12%）」**只对超出顶格档的大盘成立**（其 14×18 是示例盘、非关表实盘），不适用于本单关表；且它的算式是 34 基（其 33.00 = 34×0.97）。
- **代价集中在小盘与新手第一屏**：真小盘（如 `GRID_MIN 6×5`，两尺下均 `fit=1`）从屏上 50px 直接跌到 **30px（−40%）**，且这类盘落在 **L1 首屏留存位**；现关表内最接珠原样的 14×12（fit 0.952）也跌 37%。这是本单的真实风险面，不许用"平均下来差不多"糊过去。
- **(b) 放开 `Math.min(1,·)`**：能一步消掉小盘损失，但 = **二次推翻 `ADR-0018 §3.4.1②`**，且带来三条副作用：① 30px 珠放大到 50 屏径 = 用 0.6 逻辑分辨率画满屏，边缘与质感线会糊（`minStroke=2` 钳位后再放大）；② 屏上 pitch 可能越过 `GRID_HIT_SIZE` 一侧的既有核算与 `CAMERA_ZOOM_MAX_SPAN` 语义（上限变成"fit×span"而 fit 本身>1）；③ 语义倒退成"屏幕就是尺子"，与本单立单理由（同尺源图域）直接对冲。**⇒ 本批不采。**
- **(c) 重算 fit 规则**：`fit ≤ 1` 的**理由**（不放大超过实物比例）确实随 ① 一起被推翻，但**规则本身**仍有独立价值（防无脑放大填满屏幕、防上列 ①②）。⇒ 处置 = **规则保留、理由改写**，写进 `ADR-0018 §3.4.4` 拟修订注（§3）。这不是骑墙：规则与理由分离登记，落码零改动，语义不欠账。
- **预案（钉死路径，不预登记数值）**：真机若判「小盘珠体过小 / 首屏观感不可接受」，**另立 §3 变更单**放开为 `fit ≤ SMALL_BOARD_FIT_CAP`（数量级参考 = 50/30 ≈ 1.67，使 **顶格档 ≤22×18** 复原屏上 ~50px），届时才二次推翻 §3.4.1②。**本单不写入该值**（数值先行 = 造第二条未冻结常量）。

### 2.3 D-C：质感系数 → **只给机械缩放起始值，全部挂起**（本单不定稿、不得判绿）

另登一条 **art 必须同批裁的未结案项**：`inset` 不随 zoom 缩（`bead-render.ts:409–410` 实装如此：`size = (outer − inset×2) × scale…`，inset 在缩放前扣；`ADR-0015 §3.3-5` 已挂为未裁项→ C-5）⇒ 同一颗珠在 fit<1 时珠面占格会**额外恶化**（旧尺 14×12@0.952 = 71.9%、12×16@0.713 = **63.9%**）。⇒ 本单推荐 art 在定 `inset` 值时**一并裁定"inset 随不随 zoom 缩放"**；只看下表 `zoom=1` 一列会低估大盘的观感差异。

先给一条**必看的算术**（珠面占格 = `(BEAD_CELL − 2×inset)/BEAD_PITCH`，**一律在 `zoom=1` 比**，以免两尺各自的 `fit` 差混进来；与 `IMPACT` 的 73.1% 同源同值）：

| 组合（均 @`zoom=1`） | 珠面占格 | 露底 | 中心孔半径（设计px） |
|---|---|---|---|
| 旧 52 基，inset 6 | (50−12)/52 = **73.1%** | 26.9% | 38×0.36/2 = **6.84** |
| 新 32 基，**inset 保 6** | (30−12)/32 = **56.3%** | 43.7% | 18×0.36/2 = **3.24** |
| 新 32 基，**inset 缩 4 + holeRatio 0.44** | (30−8)/32 = **68.8%** | 31.3% | 22×0.44/2 = **4.84** |

逐项起始值：

1. **`BEAD_DRAW_INSET` 6 → 起始值 4（= `round(6×0.6)`）**。⚠ 这是本单**唯一一处对既有真机裁定值做机械缩放**，必须交代动因与代价：`6` 来自 WXG-T-162（旧 2 在真机 scale 0.5 下 ≈1 CSS px 看不见）。基尺缩到 30 后，**不缩 inset 反而让露底由 26.9% 涨到 43.7%**（远超 art 侧记录的竞品 31% 区间，网格感变碎、豆变小），同时把珠面压到 18px——18px 面要装 L2 高光 + L3 暗边 + L1c 中心孔（⚠ **L5 符号层已随 `bead-visual-style-spec` v1.5-r8（2026-09-23 用户拍板）整层删除**，本条按删除后的层集算），**这才是真风险**。故 4 与 6 的取舍不是比例问题，是"珠面还剩多少可画"问题 ⇒ **`[待林绘澄/真机]`**。备选路径：保 `inset=6` 并把 `holeRatio` 抬到 0.44（孔半径 18×0.44/2 = **3.96**，仍大于 3.24，但珠面只有 18px 可画）。 **两条给 art 的算术（比占比好用）**：① 露底环单边宽 = `inset + GAP×zoom/2`（`inset` 不随 zoom 缩，见本节首条）⇒ **`zoom=1` 时新旧两尺同为 7px**（`GAP` 不动）——本单不改这道底色分隔带的**绝对宽度**，改的是它的**占比**（26.9%→43.7%）与珠面可画面；② 若把 `inset` 缩到 4，环带绝对宽度**同步削到 5px**，而 v1.5-r8 后 L11/B0 目标色底图按 `BEAD_PITCH` **满铺方角、格间无缝** ⇒ 这条环带是「连续目标色版图」的**唯一分隔**，32 基已把版图从 52 格距压到 32 格距，削 `inset` 是**叠加代价**（`[待林绘澄]`）。
2. **`minStroke = 2` → 不缩**（canvas 可见地板，缩到 1.2 只会更糊）。**必须如实登记的风险算式**：`bevelWidthDark 5/64 → 30×5/64 = 2.34 ✓ 存活`；`bevelWidthLight 4/64 → 1.875 ✗ 钳平`；`rimWidth 3/64 → 1.406 ✗ 钳平`。而 `bead-render` 里 `rimWidth` 由 2/64→3/64 的加粗理由原文就是「50px 珠上 2/64 被 `minStroke=2` 钳成 2、无变化，3/64→2.34 才真变粗」（`bead-visual-style-spec §1.9.7` 落码记录，2026-09-23）⇒ **该前提随本单作废，3/64 也被钳 ⇒ 三档倒角在 30px 珠上全部同宽 2px，质感层次被抹平**。两条出路都归 art + 真机：(i) 比例分母 64→32（线宽比例翻倍）；(ii) `minStroke`→1（放弃地板，真机极可能重演"看不见"）。**本单二选一都不替 art 裁。** ⇒ `[待林绘澄/真机]`
3. **`BEAD_LOD_CELL` 45 → 派生 27（`0.9×CELL`）**、**`BEAD_LOD_HYST` 2.5 → 派生 1.5（`CELL/20`）**。⇒ **`IMPACT-0020a 摘要③`「LOD 档结构性失效，32 基需 zoom 1.406 才触发、默认视角恒降档」不成立**：那个结论的前提是把 45 当**绝对像素地板**；它的真实出身是**比例**（`tuning.ts:852` 原文「取 ADR-0017 建议档起点 zoom 0.9（= 珠 45 设计px）」）。公式化后降档触发点仍是 `zoom < 0.9`，行为与旧尺**完全同构**，入口屏（fit=1，珠 30 > 27）**不降档**、中心孔质感不缺席。这是本单对 IMPACT 的实质修正（§7）。挂起项：降档阈值 27 是**格径（`layout.cell`）而非珠面径** ⇒ 降档时珠面只剩 27 − 2×inset ≈ 15px，那么「降档省掉的层」是否还剩可省的东西 ⇒ 归 art（收益变小的 LOD 是否还值得两态）+ `ADR-0017` 状态仍 Proposed，**真机 FPS 依旧未验**（`[待真机]`）。红线不变：**L11 目标色垫与中心孔 L1c（`bead-render.ts:521`）任何档不砍**。⚠ **连带核销（既存漂移，非本单引入）**：`tuning.ts:829`「保留集 = L0b+L1+L2+L3+L4c+**L5**」、`:842` `WAVE_LOD_LAYERS = 7`（含 L5）、`:854`「红线 = L11 垫与 **L5 符号**」三处的对象（珠面符号层）已随 v1.5-r8 整层删除 ⇒ 本单落码批（207-A ④ 注释清理）须一并核销；降档层集是否重数归 art/QA 另案，**本单不代裁**。
4. **中心孔可辨（`ADR-0017` 红线）**：新尺下孔半径起始 **3.24–4.84 设计px** ⇒ 真机 scale ≈0.5 下 **直径约 3.2–4.8 CSS px**。这与当初判 `inset=2` "看不见"的量级只差一档 ⇒ **禁止以"比例没变应仍可辨"判绿**（K-035/K-040/K-051）。必须真机截图 + 色盲模拟（⚠ **现行口径 = 二重：色相 + 明度**，符号层已随 v1.5-r8 删除；`accessibility.md A3 ②` 早已量化「明度单独不足以分开 10 色」⇒ 32 基把珠面压到 18–22px 后辨色负担**比旧尺更重**，中心孔不承担辨色职责）。⇒ `[待林绘澄/真机 + 色盲模拟]`
5. **`SOCKET_CARD`（坑四层）**：`pitInset 0.06` 是比例 ⇒ 自动随尺 ✓ 无需改；三条线宽（3/64、2.5/64、2.5/64）与 `minStroke` 同题（分母 64 的标定基准 = 50px 珠/坑边）⇒ `[待林绘澄]`。
6. **`BEAD_CARD.radius 0.30`（K1，用户 2026-09-23 从 0.22 拍板）**：**比例制 ⇒ 不改值**。登记「0.30 的裁定前提是 50px 珠，18–22px 珠面上同比例圆角是否仍读作'豆形'待 art 看截图」。旧注释里的 `50×0.22−6=5` 随本单一并作废。

### 2.4 D-D：包体 / 图元

- **`bead-visual-style-spec §11.2` 图元基线 1587 不变**：条数 = 层数 × 格数（13×12 夹具分解式），**与尺子无关**。若有人按"珠变小 ⇒ 图元会涨/跌"做性能或包体预算，属无依据推论。⚠ **不背书具体值**：1587 是否已含 v1.5-r8 符号层删除后的重算**未核**（符号层删除会砍图元条数，那是与基尺无关的另一件事）⇒ 交程基岩在重 bless 夹具快照时一并复测。
- **须重跑的是**：① `bead-render.test.ts` 逐字段几何断言（size / radius / 孔半径 / 线宽全变，含 `TRAY_BEAD_SIZE === TRAY_SLOT−4` 那条）；② 夹具快照重 bless；③ fill-rate 与真机 FPS（像素填充率理论下降，但**无实测不算数**）。
- **`check:size`：本环境无 AppID ⇒ 不可测**，标 `[待真机/待上传]`，不得填数。

## 4. 关卡是否需重烤：**不需要**（已核实，附证据与两处例外）

**证据**：`design/levels/singles/L00001.json` 顶层键 = `id / name / cols / rows / time / pricing / cycleProfile / decoys / pattern / swaps / misplaced / palette / paletteCodes` —— **无任何 px / cell / pitch / size 字段**（脚本扫全关表，零命中）；`pattern` 是每格一字符的行串（§3.2）。盘面几何全部经 `gridLayoutFor(cols, rows)` 由常量派生 ⇒ **换基尺 = 自动等比缩，关表与 `manifest.json` 零改动，无需重烤**。

**两处必须区分的例外（"不重烤"≠"不重跑"）**：

1. **`time` 不需改，但 bot 回归要重跑一次**：v1.41 的时长按**真引擎实测 taps** 定价（`T = clamp(taps × SEC_PER_TAP, 120, 420)`），taps 是**点击次数**、与 px 无关 ⇒ 数值不动。但 `beads-bot.ts` 与 `beads-game` 的命中路径读的是 `gridLayoutFor`/`colCenterX`，且 `BOARD_TAP_MOVE_THRESHOLD=8` 这类**绝对像素阈值**在 32 基下相对语义变大（8 / pitch32 = 25% vs 8/52 = 15%）⇒ 要求程基岩跑一次 bot 全关回归**确认 taps 不漂**（若漂，动的是阈值不是关表）。
2. **studio 镜像必须同批改**（否则"文档一致、代码一致、预览不一致"三态并存）：`apps/beads-studio/public/board-render.js:38` `CELL_OF_PITCH = 50/52` 是**第三条硬编比例副本**（K-053 反转批须镜像下游），须随尺改；`:20` 注释同批。`index.html` 的 `PER_BEAD_PX = brand.dip` 已是查表 ⇒ 不动。**⚠ 同文件既存漂移（非本单引入，改镜像时一并核）**：`board-render.js:38` `RADIUS = 0.22`，而游戏侧 `BEAD_CARD.radius` 已由用户 2026-09-23 拍为 **0.30**（`bead-render.ts:68`）⇒ 预览与真机圆角本就两套值；本单不动 §3 的 0.30，但镜像同步须把它对齐（否则「同步同批」名义下仍留旧值）。

**建议新增的一致性守卫**（交程基岩裁定可行性）：`BEAD_PITCH` 与 `dip(5mm)` 现同值 ⇒ 值得锁死。⚠ 诚实限制：`dip(mm)` **只存在于生成期**（`ADR-0021 §4.2-1` 明文"运行时代码里没有 dip 函数"）⇒ 游戏侧无法 import 断言；可选落点只有 ① `palettes:check` 侧比对 `brands.json` 的 5mm 档 `dip === 32 === §3.3` 冻结值，或 ② 跨包读不到时退化为**文档级双注释互指**。两种都能防"静默漂移"，都防不了"同时改错"。
