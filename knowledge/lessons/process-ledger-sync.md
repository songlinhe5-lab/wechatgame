## 流程台账协作

- **[流程台账协作][K-045] 同一台账文件被并发会话同时写时，`git add <整文件>` 会把别人的 WIP 捎进本单提交**（来源 WXG-T-097/BD-10，2026-09-15）
  现象：另一条会话在同一仓库活跃，两份台账（主表 + 详情分片）里它的新节与新行都还没提交，和本单的回写落在同一批未暂存改动里。
  根因：暂存的原子单位是**整个文件**，不是「我这个任务的段落」；只要对共享文件做文件级 `add`，两条线的编辑历史就被绑成一笔。
  规避：① 共享台账文件**禁止** `git add <file>`，改走 `git diff -U3 <file>` → 按 hunk/按行过滤（丢不属于本单的 hunk；混在同一 hunk 内的相邻行须按行剔除并**重算 `@@` 计数**）→ `git apply --cached`（只改索引，不动工作区）；② 提交前用 `git diff --cached` 对被剔对象做**计数断言**（如「索引内 `+## <他人任务号>` 必须为 0」），别靠肉眼看 patch；③ 若过滤后仍有交叉，宁可把本单笔次排到对方之后，也不合并两单。
  判例引用：本轮 `production/TASKS.md` / `TASKS-DETAIL.md` 局部暂存（另一会话 = WXG-T-104）；同族「镜像目录 add 须逐次复核暂存列表」（误扫 stray `.ts.meta`）。
  追记（2026-09-19，WXG-T-128 收口提交 · **以「重放」替代「过滤」的更稳做法**）：本轮同样遇到 `TASKS.md` / `TASKS-DETAIL.md` 混入并发会话（T-167 轨）的未提交改动，但**没有走 §① 的按 hunk 过滤 + 重算 `@@` 计数** —— 那一步的失败面（行号漂移 / 相邻他单行同 hunk / 计数算错后 `git apply` 静默丢块）恰是本条最初想规避的风险，手工 patch 编辑本身又引入新的手误面。改用**「以 HEAD 为基底重放本单改动」**：① `git show HEAD:<file>` 取出干净版；② 脚本重放本任务的那几处改动（`String.replace` + **锚点命中校验，不命中即 throw**，绝不静默跳过的替换）；③ `git hash-object -w` 写入对象库；④ `git update-index --cacheinfo 100644,<sha>,<path>` 只换索引条目 —— **工作树一行不动、并发改动原样留存、无需触碰任何 patch 计数**。校验改用双向断言（「目标文本含本单字样 = 1」且「含对方字样 = 0」），比肉眼审 patch 直接。**适用前提**：本单改动**可被脚本重放**（纯新增节、锚点式整行替换都满足；纯手工微调不满足 ⇒ 退回 `git apply --cached`）。判例：本轮 `TASKS.md`（主表 T-128 行）+ `TASKS-DETAIL.md`（收尾节）两文件精确入 index，落于提交 `61d2911`（该笔含 9 files，另 3 为钩子自动重建的 ctx 产物）。
  追记（2026-09-26，WXG-T-169 收口提交 · **新形态：共享的是「源码 + Cocos 镜像」两份**）：同一个 `src/view/*.ts` 被两条线同时改，且它在 `games/<game>/cocos/assets/scripts/**` 还有一份 `framework:sync` 产出的拷贝 ⇒ 按 hunk 暂存**必须对两个路径各做一遍**（同一 patch 只换路径前缀），否则 HEAD 里 src↔镜像漂移（BD-20 族）。另：镜像门 `sync --check` 校的是**工作树全局**，对方有 src 比镜像新就会拦下本单（哪怕那几个文件不属本笔）⇒ 先 `framework:sync`（只改工作树、**一个对方文件也不暂存**）。自证沿用本条②的双向计数：`git show :<path> | grep -c <对方特征>` = 0 且 `<本单特征>` = 1（只校一向会漏「自己那几行被对方整文件写档冲掉」）。落于提交 `c7d157d`。

- **[流程台账协作][K-158] 跨会话「只披露不代填」是双向通道：对方会话会读头注并照做，判归属要用 mtime 而不是 git status**（来源 WXG-T-346 / commit b453498，2026-10-22）
  现象：本会话按用户裁定对他轨的两个批（另一会话的音乐音效批、主菜单签到批）**不代登台账**，只在 `production/TASKS.md` 头注写「请原会话自行补登」并在相关节末以二级条披露。随后对方会话读到该披露 ⇒ 自己补登了它那一批的主表行与详情节、保留了本会话写的同号双用订正、并把「下一真可用号」顶到再下一个；本会话领号时同样以**工作树**头注为准让号。双方零互踩，但过程中三次遇到「工作树在我读→写之间被人改过」。
  根因：头注与详情节是多会话之间**唯一的共享通信面**（无锁、无消息中间件），所以「写进头注」等价于「给对方发工单」；反之只在自己的提交信息或会话回复里说明 = 对方读不到 = 缺口永久留存（K-137 即此反例）。
  规避/做法：① **归属判定用 mtime 与本会话最后一次写入时刻比较**——`git status` 只能说「脏」，`ls -lT` / `stat` 给出的秒级时间才能说「谁在写」；晚于自己最后一次编辑的新增 M ⇒ 判为在制品、不碰不提交；② 他轨产物一律**不代填、不代改、不代抓基准**（K-045 / K-076 / K-137 同谱），把裁决权交回原会话；③ 披露必须落在**共享文件**（头注 / 详情节）并写明「谁来补、补什么、为何不代填」，⛔ 只写在提交信息里；④ 让号优于抢号，号递增不回收（K-046④）。
  判例引用：`production/TASKS.md` 头注同日三段披露、`production/TASKS-DETAIL.md §WXG-T-346 §6`；同族 K-045 / K-046 / K-087 / K-137。
