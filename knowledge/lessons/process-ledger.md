- **[流程台账][K-046] 领号必须读「工作树全文」的全局最大号，只读已提交的头注必撞号**（来源 WXG-T-106 / WXG-T-111，2026-09-15；**2026-09-18 追加「反向面」WXG-T-168**）
  现象：本会话按 `production/TASKS.md` 头注领号，但 HEAD 里的头注长期停在「已分配至 WXG-T-106／下一可用 107」，而并发会话当时已在工作树里写下 104–110、113–114 的节与行（均未提交）。若照 HEAD 头注领号，两条线必然拿到同一个号；本会话改按**工作树**全文领 111/112，对方随后领 113/114 时看到的正是我写在树里的 111/112 ⇒ 双方零冲突。
  根因：头注记录的是**已提交快照**的属性，号池的真实状态是**工作树 ∪ HEAD ∪ 归档**的全局最大号；台账被多会话共享写时，两者可以差好几个号，而「领号认本注」的旧口径把真源指错了地方。
  代价：撞号后果不是报错而是**静默合并**——两单共用一个 `## WXG-T-0NN` 节，`check:tasks` 只校「主表行 ↔ 详情节」配对数，同编号反而配得上；事后只能靠人工辨认哪几段属于谁（判例 K-008 当年即为此）。
  规避：① 领号前查**工作树**：`grep -o 'WXG-T-[0-9]\{3\}' production/TASKS.md production/TASKS-DETAIL.md | sed 's/.*WXG-T-//' | sort -n | tail -1`，取最大值 +1（禁止只 `git show HEAD:` 读头注）；② 领到号立刻落主表行 + 详情节，让并发方尽早可见；③ 头注「已分配至」按**本次暂存快照**自洽来写（blob 暂存时不可把别人未提交的号写进自己那笔），事后可用 `pnpm run tasks:archive` 校准；④ 号递增不回收，跳空合规——让号优于抢号。
  追记（2026-09-18，**反向面**：只 grep 两张任务表仍然撞号，WXG-T-168）：本会话严格按上条规避① 执行——`grep -o 'WXG-T-[0-9]\{3\}' production/TASKS.md production/TASKS-DETAIL.md` 得最大号 166、头注亦明示「下一可用 167」⇒ 领 167 并落码；随后才发现 **`games/beads/design/gdd/input-control.md` 头注早已写着「版本 v2.5 · 任务号 WXG-T-167」**（并发会话的 ADR-0015 C-3 翻转单），该号**只存在于 GDD/ADR 头注，从未进任务表** ⇒ 全量 sed 改号 168 收场。
  根因（补充）：号池真源不止两张表 —— **任务号会被随手登记在 `games/*/design/gdd/*.md` 的版本头注、`docs/architecture/adr/*.md`、以及各文 §9 变更记录里**，这些位置既不在 `check:tasks` 的扫描面内，也不在 grep 两张表的命令里；规避① 的命令只覆盖「表」，覆盖不到「文」。
  规避（补充 ⑤⑥）：⑤ 领号前除两张表，还须 `grep -rn 'WXG-T-1[0-9][0-9]' games/*/design/gdd/*.md docs/architecture/adr/*.md production/qa/**`（**工作树**）查头注与变更记录里的占用；⑥ 撞号后的改号成本远高于事前多查一次 —— 本例需对 src/tests/文档共 8 个文件做 sed，且已写进 changelog 的号要逐处对齐（`sed` 只改字面，不保证语义一致，改完必须重跑 `check:tasks` + `ctx:check`）。
  判例引用：本轮 106（让 105）与 111/112（并发方占 113/114）；**2026-09-18 反向面**（167 由 `input-control.md` v2.5 头注占用、`ADR-0015` §4 佐证，本会话改领 168）；`production/TASKS.md` 头注勘误条（WXG-T-040 校准口径）；同族 K-008（跨 IDE 撞号）、K-045（共享台账的暂存原子性）。

- **[流程台账][K-050] 缺陷号（`BD-NN`）与任务号同规：领号须读工作树全文，且「已登记 BD-xx」的声明必须回查台账是否真有正本行**（来源 WXG-T-119 / 主理人复核，2026-09-16）
  现象：`WXG-T-119` 报告与并发会话新开的 `WXG-T-122` 任务书都把「宿主双驱动（仿真/墙钟 ≈2×）」登记为 **BD-40**，而 `BD-40` 早在 `WXG-T-112` **已入库**为「`ctx:check` 未挂 verify」⇒ 同号两义；且 backlog 表里始终只有我那一行 ⇒ 这条 P1 级发现**根本没有正本行**，只有报告与任务书里的引用。
  根因（与 K-046 同一形状，只是换了命名空间）：号池真源是「工作树 ∪ HEAD ∪ 归档」的全局最大号，但成员在**自己视野内**就地造号，台账写入又发生在另一会话/另一时刻；`check:tasks` 的 A–H 门只校**任务行 ↔ 详情节**配对与 backlog 行长度，**不校 BD 号唯一性** ⇒ 无机械拦截。
  规避：① 落笔「登记 BD-xx」前先 `grep -o "BD-[0-9]\+" production/TASKS.md`（**工作树**，不是 `git show HEAD:`）取最大号 +1；② 主理人收口时对成员声明的每个缺陷号做**双向对账**（号 → 台账有行 / 行 → 报告表述一致），缺一即补登或改号；③ 消歧信息要写进**表内那一行**（「原记 BD-40 系撞号，正本以本号为准」），不要只留在报告里——后人检索号时读的是台账；④ 补登走 blob 法，且同一变换要 `--worktree` + `--stage` **双施加**：blob 只决定「暂存什么」，若 `git commit` 仍带 **pathspec**，它取的是**工作树**内容 ⇒ 照样把并发会话未提交的行捎进本笔（本单上一笔即如此）；工作树那份则保证对方后续整文件 `add` 不冲掉本行（K-045）。
  代价（真实后果不是报错，是**跨会话误读**）：`WXG-T-122` 任务书已写下「`WXG-T-121` 已把 BD-40 挂进门禁 ⇒ 该线只解决检测」，而 T-121 挂的是装置门 `ctx:check`（与双驱动无关）⇒ **修复单的前提描述失真**，必须在动工前订正，否则会去找一条不存在的「检测已覆盖」结论。
  追记（同日约半小时后，本条代价坐实了一半）：对方会话已把该修复单施工完（自证比值回到 1.00），而任务书里的失真句与探针判据行里的旧号**原样留着** ⇒ 只在 backlog 补一行正本号**不够**，消歧须回写**每个调用点**（任务书背景段 + 探针/报告的「登记 BD-xx」字样）；否则后续会话仍按旧号叙述，正本行沦为孤行。
  判例引用：K-046（任务号领号认工作树）、K-045（共享台账暂存原子性）、K-008（跨 IDE 撞号）。

- **[流程台账][K-169] `check:tasks` 按裸竖线切主表行：行内写管道或命令即被判「列数 N ≠ 5」**（来源 WXG-T-378 / commit d7243cb，2026-10-25）
  现象：新任务行正文里写了取节命令（`jq` 的 `.files[]` + `select(...)` + `.sections` 三段管道），`pnpm run check:tasks` 立刻红：`A: WXG-T-378 列数 7 ≠ 5（表头为 id/名称/负责/状态/产出）`；同一批 `selftest:fast` 里 `verify:selftest` 第 4 步「去掉注入项 ⇒ 必须绿」也跟着报 `check:tasks 单步不绿`，看着像聚合器坏了。
  根因：A 项的列切分是最朴素的 `split('|')`，不识别 markdown 转义；行内任何**裸**竖线（命令管道、或表格单元格里未转义的竖线）都算列分隔符 ⇒ 列数溢出。门只报「列数不对」，不指出是哪段文字导致，容易被误判成撞号或格式漂移。
  规避/做法：① **主表行是索引不是正文** —— 带竖线的命令、多行脚本、成对表格一律写进详情节 `## WXG-T-0NN`，主表只留结论与读数；② 详情节表格单元格内若必须写竖线，用转义形式 `\|`；③ 见到「列数 N ≠ 5」先用 `node -e` 或 `sed -n 'Np'` 打印整行原文数一遍竖线，**先怀疑自己写的行，再怀疑撞号**。
  **追记（WXG-T-381，2026-10-25）**：列数不对有两种**方向相反**的成因——行内有**全角竖线「｜」**（不是分隔符 ⇒ 两格并一格，列数变**少**）与行内**未转义的半角竖线**（多切一刀，列数变**多**）；只报「列数 4 ≠ 5」会让人去翻表头。`check:tasks` A 项已点名字符并给改法（`cellCountHint`）。另：这类「只加提示、不动判定」的改动，回归风险 = **提示变成假话**（上游规则放宽后提示仍在）⇒ 提示旁须写明「规则放宽就删我」。

- **[流程台账][K-170] 单文件上限是硬顶：往详情节追加前先估 tok，撞顶后再挤会白跑一轮 pre-commit**（来源 WXG-T-378 / commit d7243cb，2026-10-25）
  现象：`production/TASKS-DETAIL.md` 追加一节（约 1.5k tok）后 pre-commit 直接拦下：`B: production/TASKS-DETAIL.md 205381 tokens > 所属类别上限 205000（tasksDetail）`；首次压缩只降到 204,897（余量 103 tok）⇒ 下一笔任务必重撞同一道门。
  根因：WXG-T-377 把台账类上限分档（`TASKS.md` 80000 / `TASKS-DETAIL.md` 205000），意图是「由 `archive-tasks.mjs` 治理」，但归档**不挂** pre-commit / CI ⇒ 详情节只增不减，上限迟早被顶穿；而门只在**提交时**报，写作阶段没有提示。
  规避/做法：① 写详情节前先用 `tools/scripts/lib/context-tokens.mjs` 的 `estimateTokens` 读整个文件算余量（与门禁同一口径），篇幅按余量定；② 余量不足约 3k 时先跑 `node tools/scripts/archive-tasks.mjs --detail-until-under=<目标> --write` 归档最老 ✅ 行（行与节成对搬运、带守恒校验），再写；③ ⛔ 用调阈值或加豁免绕（WXG-T-377 明确判据与台账类不放松）；④ 归档后 `check:tasks` 会同时校「主表 ↔ 详情 ↔ 两个归档」，跑一遍再提交。

- **[流程台账][K-172] `TASKS-DETAIL` 节标题必须裸写 `## WXG-T-NNN`：带副标题会被 `parseDetail` 漏认，门却报「没有此小节」**（来源 WXG-T-381 / commit c1a48df，2026-10-25）
  现象：详情节标题写成 `## WXG-T-380 · ctx · 填充预留`，`check:tasks` 报 `C: 主表有 WXG-T-380，但 … 没有 ## WXG-T-380 小节` —— 小节明明在第 13 行；该节也拿不到配对搬运（归档只看 `parseDetail` 的识别结果）。
  根因：`tools/scripts/lib/tasks-detail.mjs::parseDetail` 的标题正则只认 `^##\s+(WXG-T-\d+)\s*$`（纯号、无任何后缀）；门此前只报「没有」，与「真没写」不可区分。WXG-T-381 起失配时回报形似标题的行号与原文。
  规避/做法：① 节标题只写号，副标题另起一行加粗（照 T-379 / T-380 的写法）；② 见「主表有、详情无」先 `grep -n "^## WXG-T-NNN" production/TASKS-DETAIL.md`，命中行带后缀即本坑；③ 号别塞进 `### ` 子节当节用（解析器只认 `## `）；④ 若日后放宽标题规则（允许副标题），须同批删掉 `strayHeadingHint` 与门里两句提示，否则提示会变成假话。
