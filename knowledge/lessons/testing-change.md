## 测试变更
- **[测试变更][K-125] 语义从「取大」换到「优先」时，`≥` 型不变式没有判别力，必须补一条相等式**（来源 安全区接口优先批 / WXG-T-265 · commit 5703654，2026-10-13）
  现象：改写 `safeEdgeInset` 后既有测试「结果 ≥ 胶囊底换算值 + 余量」全绿——但**旧 `max` 写法同样满足它**；只留这条，旧语义回潮不会有任何一条红。
  根因：不变式只刻画「不低于」方向，而本批改的恰恰是「常量不得参与」这一侧；换算单一真源化之后，测试若再从同一份常量取期望值就等于用被测逻辑测被测逻辑（同 K-042）。
  规避/做法：① 换语义批必须新增**成对断言**——正向严格相等 `toBe(112 + MARGIN)` ∧ 反向排除 `not.toBe(SAFE_TOP_H + MARGIN)`，把「宏不得参与」钉成可失败判据；② 逐机档用**字面量**钉死（116/137/164/176/161、72/63/104），不许复写成被测同款公式；③ 单位换算方向另配单调性断言（同 dp 下屏越窄 ⇒ 设计 px 越大），防分子分母写反后数值仍「看着合理」。
  判例引用：K-042（真源化后判据失去自证，须另配不依赖该真源的守卫）、K-060（变异自检断言方向选错留伪绿）、K-089（守卫硬编码与真源脱钩 ⇒ 断言永不触发）。

- **[测试变更][K-129] 往皮肤调色板加一枚字段在本仓是「三处联动」的改动，逐道修会逐道漏；台账那一道的修法只有一条**（来源 L4 门楣牌第十一批 / 无单，2026-10-13）
  现象：`BeadsPalette` 新增 3 枚令牌后，先只跑相关两套测试 ⇒ 红的是 K-6 图元族台账两条（菜单帧 total/sha 漂）；重跑捕获脚本顶版后再跑**全量**又冒出两道独立红：`skin-system.test.ts` 两肤字段键集恒等（`expected 29 to be 32`）与 `bead-render.test.ts` ④ 色表锁（条数 + sha1 前 12）。三道锁彼此不知道对方存在，所以「修到绿」得跳三次。
  根因：同一份调色板被三个不同侧面消费（绘制命令图元计数 / 两份肤的键集一致性 / 色表指纹），而没有任何一处能预告「你还要改另两个」；最危险的是台账那道的**诱因形状**长得像「改个期望值就绿」，手改 fixture JSON = 伪造证据（与 K-111 同一脉）。
  规避：① 开工前先列三处清单并**同批改完再跑全量**（逐道修逐道跑会把一次改动敲成三轮）；② 图元台账只允许走**捕获脚本**重取，然后逐键对预期（本例 playing 四键必须仍 MATCH，否则是渗漏不是漂移）；③ 新增字段必须**同批**给每份肤一个值，别名只能指向在册值（⛔ 为编译过而临时编一个新色相）；④ 色表锁的顶版数值用与测试同款的去注释实算给出，但要同时明白**它只防漂移不防错色**，数值对不对得靠另一条不依赖该表的判据（本例 = 对比度实算腿）。该锁的期望值是手钉字面量，⇒ 属 K-089 描述的「与真源脱钩」形状，顶版时把来源（哪个批次、哪三枚）写进注释行，否则下一个人无从判断这是真改动还是误改。
  判例引用：K-111（「顺手重建产物」覆盖基线）、K-089（守卫硬编码与真源脱钩）、K-042（判据与被测面同源）。

- **[测试变更][K-151] 关卡「扩池」是破坏性存档变更：关表长度即 `DEMO_LEVEL_COUNT`，降级矩阵按「长度不符 → 重置全 0」静默清历史星**（来源 WXG-T-341，2026-10-21）
  现象：把一张已验证的照片 boss 经 beads-studio 正常入成**第二大关**（第一章 9 关一字未动），`levels:check` 全闸绿、游端 `validateBeadsLevel` 0 错、包体在预算内；直到 `pnpm run verify` 才由单测报出「历史星不被清零：expected +0 to be 3」——那一例本身只是**夹具写了 9 位星级**而池已变 10 位。真行为 = 旧档 `starsByLevel` 长度与新包不符 ⇒ 整组归零，**不报错、不部分保留**。
  根因：`DEMO_LEVEL_COUNT` 随 `manifest.entries` 生成（`tuning.ts:884`），而 `normalizeStars(raw, levelCount)`（`src/game/save-schema.ts:251-253`）按 S8 §2.4 明文「长度不符 → 重置全 0」（是重置、不是钳长）⇒ **投放新关 = 改池长 = 触发降级矩阵**；内容管线的现有门禁（章容量 / 规模 / 步数 / pack）只问「本版结构合不合法」，没有任何一道问「这次变更对**旧档**是否无损」。
  规避：① 把「关表变长」当**跨版本兼容事件**：上架后扩池须先有迁移腿（旧数组前缀搬运 + 新位补 0），镜像用例 = 喂 9 位旧档入 10 关池期望**前 9 位无损**（现行期望是全 0 ⇒ 属 S8 裁定变更，要开单拍板）——**该条已于 WXG-T-342 落地**：`normalizeStars` 改为前缀搬运（短补 0 / 长截断 / 非数组才全 0），判据 = `save-progress §8-14` 四臂（前 N 位无损 / 末位 0 / 首次 `changed` / 二次幂等）；② 未上架期可接受，但必须**写明代价落在哪**（内部测试档 / 真机扫码档可重建），⛔ 不说「无影响」；③ 连带回落面一并查：本例 = 总星数（§3.7 主题解锁货币 = Σ 历史最高）+ 橱窗三态（cleared → pushing/locked）+ `nextTierFor` 档位掉回 1★；④ 测试夹具与断言里的**长度型 magic number**（9 位星级、“翻一次到末页”）一律改成真源派生（`LEVELS.map(…)` / `ARC_OPEN_MAX`），否则下次扩池还会以「假 bug」重演；⑤ **迁移腿只买「末尾追加」的安全**：任何按数组下标对位的迁移，一旦在中间插入 / 删除 / 重排条目就会静默错位且不报错（第 6 关删掉后，原第 7–10 关的星落进第 6–9 位）——那类变更必须另开迁移单按稳定 uid 对位，并且不要在「结构没变」上自我安慰：管线门禁通常只校结构合法，不校「这次变更对旧档是否无损」。
  判例引用：`games/beads/src/game/save-schema.ts::normalizeStars`、`games/beads/design/gdd/save-progress.md §2.4` + `§8-14`、`games/beads/tests/save-schema.test.ts`（迁移腿三臂 + 9→10 无损）、`games/beads/design/levels/levels-spec.md §11.7`；同族 K-036（跑过 ≠ 检了）、K-106（门禁跑过 ≠ 新文件被看到）。

- **[测试变更][K-152] 把「本版快照」当不变式硬写的测试，会在内容投放变更时批量假红并淹没真信号**（来源 WXG-T-341，2026-10-21）
  现象：投放第二大关后 beads 9 例齐红；定性拆开 = **8 例假红 / 1 例真信号**（上条）。假红写法全同形：`expect(ARC_OPEN_MAX).toBe(1)`、`WALL_CAPACITY === LEVELS.length`、扫 `singles/*.json` 当 §5 九关池、“点一次 next = 末页”、9 位星级夹具。
  根因：这些断言描述的是**某一版的内容事实**（只有一章 / 全池 = 第一章 / 页数 2），而非系统规则；写成与代码同形的常量后，版本演进必红，且红得跟真 bug 一模一样。
  规避：① 版本快照类断言改**数据驱动表达式**（页数 = `ARC_OPEN_MAX + 1`；池 = `ARCS[i].levelRefs` 派生；夹具长度 = `LEVELS.length`）；② 改完做反事实：若真回到 1 章版，数据驱动写法仍给出正确结论而不是永真；③ 标题与注释同步改口径并明写「旧文只对单大关版成立」（如“越界槽本版不可达”→ “第一章不可达；第二章清单 1 关 ⇒ 8 槽锁格，本版**可达**”），⛔ 留着过期描述让后人当不变式；④ 与真信号混在一起时**先按机制分组再判红**，否则会把「测试要改」误读成「产品不能投放」，或反过来为了赶绿去改 §5 冻结表。
  判例引用：`games/beads/tests/{difficulty,meta-menu-wall,arc-carousel,arc-level-select,main-menu-presenter}.test.ts`；同族 K-089（守卫硬编码与真源脱钩，须先证能红）、K-144（同结论两机制 ⇒ 逐机制配例）。

- **[测试变更][K-157] 夹具手工拼出的「最小形状」若与生产装配形状不同，对数据形状敏感的边界分支就永远走不到，变异也不会红**（来源 WXG-T-345，2026-10-22）
  现象：存档「身份指不回时落到哪一根指针」的降级锚用例，首版夹具手搓「只含被点名关卡」的稀疏星账；而生产读档会把星账补成「每关都有键（缺者记 0）」的稠密形态。于是一个「取装配序最靠后那一关」的错误实现（设计正文明令禁止的「落表末位」）在稀疏夹具下每次都仍指向同一关，五条用例全绿；改用生产装配函数喂「全 3★ 稠密账」后，同一实现立刻变红。
  根因：被测逻辑判定的对象不是「某几个键」，而是「键集是稠密还是稀疏」这一形状本身；夹具绕开生产装配入口 ⇒ 形状差异被夹具抹平 ⇒ 边界分支在测试里不可达（这是 K-152 的镜像：那里误把「本版快照」当不变式，这里误把「手搓形状」当生产形状）。
  规避/做法：① 夹具一律走生产装配入口（建档 / 读档 / 归一化函数），⛔ 手搓「最小可用形状」；② 确实必须手搓时，先单独写一例断言「夹具形状 ≡ 生产形状」（键集、长度、默认值逐项），让它成为可失败判据；③ 变异选点必须打在**形状敏感的边界**（末位 / 首项 / 空集 / 缺键），能红才证明夹具没把该分支压平；④ 新判据落地时同批回查既有夹具：它们描述的是生产形状，还是上一版手工形状。
  关联：K-152（本版快照当不变式 ⇒ 批量假红）、K-144（同结论两条机制 ⇒ 只配一例时变异不红）、K-060（存在性断言无判别力）。
