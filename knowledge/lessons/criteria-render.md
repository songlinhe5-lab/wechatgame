## 判据渲染

- **[判据渲染][K-052] 动效时长常量一旦决定「事件发生在哪一帧」，它就是玩法时序而非表现层参数，判据与守卫都得换档**（来源 WXG-T-150，2026-09-17）
  现象：解环器相 A 的 200ms 在美术卡里是「高亮闪一下」。采「先预警 → 后动手」裁定后，这 200ms 同时决定了 `bead:placed` 发射帧、过关判定帧、托盘可取状态帧 ⇒ 它**不能**再挂在表现层槽（`_update` 尾部那串「不被 PAUSED 冻结」的动画步进）上，必须走 `playing` 相位守卫，且 `paused` 只能**冻结不作废**（道具已扣次）。
  根因：GDD/美术卡的分类轴是「谁看得到」，工程的分类轴是「谁改状态」；一个时长跨两轴时，纸面归属会把它误导成可随意调的观感参数。
  规避：① 建**判据三层**：包络（纯函数）／**时序（真链 + 事件计数 + 门两端各一例）**／观感（命令层几何与 α），三层各一条 describe，别用观感例代判时序；② 该时长在**三处同时钉注**（常量头注、持有字段的注释、规格落码注），写明「改它 = 改玩法」；③ 既有的其他单重启门（本例 `FILL_POP_RESTART_GATE_MS`）**优先旁通而非软化**：另开独立逐颗队列让每颗拿到完整包络，原门常量一字不动；④ 相位作废口径要逐条写死：`paused` 冻结 / 其他非 `playing` 作废 / 重装配（换关·重试·崩溃恢复）作废、过关判定排到序列末。
  判例引用：`games/beads/src/config/tuning.ts` G2′ 常量块头注、`games/beads/src/game/beads-game.ts::SolverFxQueue/_stepSolverFx`、`games/beads/tests/solver-vfx.test.ts` ②组 8 例（199ms/201ms 门两端 + 暂停/换关守卫）；同族 K-044（不可判定子句只能产 PASS\*）、K-040（判据变更归因）。
- **[判据渲染][K-055] 「连通块」API 的返回序是行主序、不是距锚序：「就近/最近」语义取前 N 前必须显式重排**（来源 WXG-T-168，2026-09-18）
  现象：落实用户裁定「空槽不足 ⇒ 收离点击位置最近的 N 颗」时，直接取 `collectMisplacedGroup` 返回 `cells` 的前 N 颗 ⇒ 单测当场暴露收进去的是**最远**的那颗（锚点在组中段时，行主序把它上方的同组珠排在最前）。该 API 末尾有一句 `out.sort(行主序)`，BFS 天然携带的**距锚层级**在出口被抹平。
  根因：「连通块」与「距锚远近」是**两种不同的序**：前者由 flood-fill 的 `out` 数组天然携带，后者需要显式度量；末尾 `sort` 的初衷只是让结果稳定可测（行主序确定性），却把序的语义偷换成「坐标序」，而调用方按函数名（`…Group`）自然会读成「距离序」。
  规避：① 凡「就近 / 优先 / 最近」语义，取前 N 前**必须显式重排**（本例按到锚珠的欧氏距离平方升序，平局回退行主序），并在被调函数头注写明「**本函数返回行主序，非距锚序**」；② 判据必须能**区分两种序**——构造锚在**组中段**的用例（锚珠上方仍有同组珠）；若只测「锚在角落」，两种序恰好一致 ⇒ 伪绿；③ 排序键用**距离平方**（整数、免开方），平局回退既定稳定序，避免浮点误差与顺序不确定（L4 确定性）；④ 部分收纳类语义还要同步定义**余量归属**（本例余珠留格、锚改指剩余首颗且不发事件），否则「就近」只对首批次成立，续点就漂。
  判例引用：`games/beads/src/entities/grid.ts::collectMisplacedGroup` 末尾 `sort`、`games/beads/src/game/beads-game.ts::_nearestFirst` / `retrieveSelectedGroup`、`games/beads/tests/retrieve-landing.test.ts`（就近续点 3 例）；同族 K-035（「规格已写」≠「代码已实现」）、K-054（未登记 ≠ 已证伪）。
- **[判据渲染][K-056] 渲染里「未解锁/扩展」的视觉语言必须随容量语义常量派生：裸行号判定会把已开放行画成未开放，并反噬成「假容量」缺陷报告**（来源 WXG-T-168，2026-09-18）
  现象：托盘第二行显示成淡色虚线、看不出是可用的开放槽；用户据此报「容量只有 12，珠子却跑进第二行」。真因既不在容量也不在配色：`drawTray` 里 `dashed = row > 0` —— 虚线语言本应**只属扩展行**，但基础容量 24（2 行）时，**基础第二行也被判成虚线**。
  根因：视觉语言绑定的对象是「相对行号」这种**随数据变化的位置**，而不是「是否属于扩展容量」这一**语义**；容量常量一改（24→12）同一行号的归属就翻转，旧判定立刻失真。更隐蔽的是它会**反向污染需求判断**：玩家/测试看到的「未开放」是渲染产物，却被当成容量事实上报，排查方向被引到数值侧（本例先排查容量、再回头才发现是渲染）。
  规避：① 渲染中的状态语言一律由**语义常量派生**（`row >= ceil(TRAY_BASE_SLOTS / TRAY_COLS)`），禁止用裸行号/下标表达「第几行之后算扩展」；② 容量常量变更时，**渲染判定与容量判定必须同批复核**（本例改 12 后虚线判定自动正确）；③ 收到「容量/数量不对」类反馈，先分清**模型事实**（`tray.capacity` / `freeCount`，用一条 Node 断言钉死）还是**呈现事实**（描边/配色/可见行数），再决定改哪一侧；④ 与 K-051 同族 —— 纸面归类的值/口径会随并行单失效，落码时必须差分复算一次。
  判例引用：`games/beads/src/view/view-model.ts::drawTray`、`games/beads/src/config/tuning.ts::TRAY_BASE_SLOTS`（§3.4 v1.30，24→12）；同族 K-051（增量值须差分复算）、K-030（产物新鲜度假绿）。
  追记（2026-09-20，WXG-T-179 · **同族的「上游加约束、下游仍用全量池」形态**）：给生成器加 `--colors N`（限制用色数），实现里把超限色重映射到保留色集，但**下游的平衡环节仍以「全调色板」为候选池** ⇒ 它会把刚被禁掉的色**复活**：`--colors 4` 实测产出 **5 色**、`--colors 3` 产出 **4 色**，限制形同虚设。同轮另有一处**同型**：脚本把色板大小硬编码成 8（`new Array(9)` / `for (c <= 8)`），加 `--palette N` 后这些位置全成**维度泄漏**（越界/漏色），须逐处改为单一常量；更隐蔽的是**跨执行上下文**——`page.evaluate` 内的代码**看不到 Node 侧常量**，写成 `PAL_N` 会在浏览器里 `ReferenceError`，只能走**传入参数**（`pal.length`）。**规避**：① 上游一旦引入「允许集合」（白名单 / 子集），**所有下游选择点必须收到同一集合**（本例 = 给 `balance` 传 `allow: Set`），无可用目标时**如实返回 note 而不越界**；② 把「维度 / 上限」抽成**单一常量**并全量替换硬编码（`8` → `N`），改完用一次**边界用例**（本例 `--palette 2`）逼出越界；③ 跨上下文（Node ↔ 浏览器）传值只能走**参数**，不得引用外层常量；④ 判据 = 「产出 ⊆ 允许集合」且「产出 ⊆ 板长」——一行断言即可抓住，比肉眼看产物可靠。
- **[判据渲染][K-063] 会「静默转移」的锚不能当距离排序基准：消费序基准与展示坐标必须分离**（来源 WXG-T-183，2026-09-20）
  现象：board 锚组批量直填（WXG-T-180）后锚珠被填 ⇒ 锚静默转移到剩余组首，此后所有「就近」排序继续读锚坐标 ⇒ 基准随每次消费漂移；且转移复用「头珠改指」同一写入点——展示坐标与排序基准共用一个字段，改展示即动排序（展示头珠跟随转移本身合理，错在排序也跟着走）。
  根因：「锚」身兼两职——消费序基准（应恒定可复现）与展示头珠（应跟随剩余组）；凡锚会静默转移的实现，距离序都隐式依赖「已消费到哪一步」，同一盘面同一点击的行为随消费历史变化、无法离线推演。
  规避：① 选中那一下固化拾取坐标（`anchorRow/anchorCol`，此后任何路径不改），`row/col` 降级为纯展示头珠；② 所有消费序（批量填、部分收纳）统一以固定锚为基准——度量（切比雪夫/欧氏）可换，**基准不可换**；③ 批量填用同序配对：目标序（BFS 由近及远）× 组员序（距锚升序）按索引配对，逐目标就近取珠的 O(n²) 扫描与基准漂移一起消失；④ 判据必须能区分新旧序——构造「目标离拾取点远、离某组员近」的几何，使旧序选 A、新序选 B；只测「目标就在拾取点旁」两种序一致 ⇒ 伪绿。
  判例引用：`games/beads/src/game/beads-game.ts::_boardSelected/selectBoardBead/retrieveSelectedGroup/_tryDirectFillFromBoard`（src 与 cocos 镜像）、`games/beads/tests/misplaced-direct-fill.test.ts` 选豆点基准例；同族 K-055（连通块返回序 ≠ 距锚序——本条是其下游：显式重排之后，**重排的基准点**还必须恒定）。
- **[判据渲染][K-067] 「就近」排序的度量必须与集合的连通定义同度量，且多消费口共用一份序**（来源 WXG-T-186，2026-09-22）
  现象：错位珠组按 8 向**连通**生长（`collectMisplacedGroup`），两个消费口却各按**几何**距离排序（直填 = 距选豆点切比雪夫、取回落槽 = 欧氏²）⇒ 组一拐弯或中间有缺口就「跳过缺口先吃对岸珠」（玩家读到隔空取物）；同圈层由行主序裁决 ⇒ 最左上的珠最先被吃（与玩家「从手边一片揭起、最远的留到最后」相反）。两路口径在 2 万随机组形上有 **89.4%** 给出不同序。
  根因：成员集合由**图连通性**定义、「最近」却用**平面坐标**距离 —— 两者在带洞/拐弯的形状上必然分歧；且两处各写一份排序代码，改一不会通知另一。
  规避：① 集合按连通性定义时，「最近」取**该连通图上的距离**（从锚 BFS 层号），几何距只在集合本身按几何定义时才对；② 序**只在拾取时算一次**（不设颗数截断），各消费口取同一份产出的前缀 —— 口径一致由「共用一份」构造保证，不靠两处写成一样；③ 「不跳空洞」与「不吃散（不吃割点）」**数学上互斥**（往外揭迟早要吃桥珠），必须显式定让步方向并写进规格，别指望调权重能两者归零；④ 判据要能区分新旧序（带缺口形状 + 「全程不跳」与「任意 k 剩余仍连通」两条不变式）——直链/小坨上两种序重合，拿它当基准例 = 伪绿。
  判例引用：`games/beads/src/systems/consume-order.ts::planConsumeOrder`、`games/beads/tests/consume-order.test.ts`；同族 K-063（基准点须恒定 —— 本条是**度量形态**须与集合定义同构）、K-055（连通块返回序 ≠ 距锚序）。
- **[判据渲染][K-091] 满铺底图的相邻 rect 会因 AA 边缘覆盖不足而漏出底层：外扩同色可根治，度量必须用「相对局部底色的亮度跳变」而不是纯白阈值**（来源 WXG-T-235，2026-10-03）
  现象：盘面格边界出现一条 **1 设备px** 的亮线，肉眼读作「格与格之间的白线」，且**随缩放变强变弱**（改 zoom / dpr / 窗口宽就换一副样子）。实测像素剖面：底色 `(150,71,99) lum 97.8`，格边界 x=286 / x=329 各 `(172,112,133) lum 132.3`；三通道解混合一致（R 需 0.18 / G 0.22 / B 0.22）⇒ **约 20% 的浅色底板从接缝漏上来**。
  根因：满铺底图按「边缘恰好重合」给边长（`边长 = 格距`），而格距在设备像素上多非整数 ⇒ 两个 rect 的 AA 边缘各只覆盖一部分、**合计不足 100%** ⇒ 缝里透出底下那层浅色面；强弱是 `zoom × dpr × 窗口宽` 的**相位函数**。⛔ 不是取整误差、不是颜色算错、也不是某一臂独有的 bug（本例 tint 臂与矢量臂同位置 p99 几乎相同 ⇒ 该线由两臂**共用**的底图层产生）。**追记（2026-10-03 实测修正，前一版写的「低倍率格距变小 ⇒ 1px 缝占比最大 ⇒ 最显眼」是错的）**：定点缝探针（zoom ∈ {0.2, 0.5, 0.8, 1.0} × dpr ∈ {1, 2}，修前/修后各一张）实测 —— 修前**只在 `zoom = 1.0` 两个 dpr 上检出缝**（各 8 条缝列、Δlum 46 / 41），`zoom < 1.0` 四点**均未检出**；修后 8 点全为 0。⇒ 「低倍率最显眼」不成立，**不要把它当规律**。⚠ 该探针在低倍率**灵敏度偏低**（珠子会打断整列，缝列判据失效）⇒「低倍率无缝」是**弱证据**，而「zoom 1.0 有缝、修后归零」是**强证据**。教训：**『相位函数』这类机理解释不能替代逐档实测** —— 机理说得通不等于方向对（本条即为机理推断方向错的实例）。
  规避：① **同色外扩**：满铺底图类矩形每边外扩 `⌈1 设备px⌉ / dpr` 设计px（本仓取 `0.5`/边 ⇒ 相邻重叠 1 设计px ⇒ `dpr ≥ 1` 时恒 ≥ 1 设备px，足以盖住实测的 1px 缝；再大只会让相邻异色格的色界多偏 0.5px，无收益）。⚠️ **只放大绘制边长**，⛔ 不动布局格距 / 命中判定 / 快照字段；且**改前先确认层级**——「珠与珠之间的缝」与「底图与底图之间的缝」是两层，改错层的常量既无效又破冻结值。② **先判「是不是这一层」再改**：出亮线时先做**两态/两臂对照截图**（本例 `?tint=off` 对照）⇒ 若两态一致即可立刻排除「刚做完的那个功能引入的回归」。这一步不做，很容易把既有现象记到新功能头上，**并污染封箱归因**、误导后续复评。③ **度量用亮度跳变，不用纯白阈值**：判「有没有白线」若按「纯白 ≥ 248」筛，会把混色后的亮线（本例只有 lum 132）判成「不是白」⇒ 伪绿（本例第一轮就误判成「格间没有白线」）。正确做法 = 取局部底色中位 `m`，按**列/行方向**扫 `max(lum) − m` 定位线段，再对候选列打 RGB 剖面并**解混合**求漏出比例（**三通道一致性**是判据自洽的关键）。④ **普查用「缝列」计数而非「亮线像素数」**：后者会把底板本身算进去（本例曾把整片白底板计成「漏白 1.1 万 px」，数字完全无意义）；用「该列超阈行占比 > 60%」筛出**缝列**再分组，本例修前 **7 条** → 修后 **0 条**，一眼可验。⑤ 与判据变更相邻的连带面要一次清点：外扩会让所有「按字面量宽度筛该矩形」的过滤器**静默退化为空断言**（筛出 0 条时「逐字段相等」永真），并让「相邻零重叠」这类旧不变量翻面 ⇒ 逐处留决策出处，别当数字微调改掉。
  **追记（2026-10-03 守卫落码，K-089「先证守卫能红」）**：已建 `tools/scripts/check-board-seam.mjs`，**静态口径门进 `verify`**（无浏览器依赖 ⇒ CI 可跑）四条断言 —— ① `TILE_BLEED > 0` ② `drawTargetTile` 真按外扩绘制 ③ 相邻重叠 ≥ 1 设计px ④ 测试口径无「字面量格距硬判」；**四种改法逐条实测能红**（改 0 / 去掉外扩 / 外扩减半 / 口径回退）。⛔ **像素复验（`--pixels`）不挂 verify**（本仓 CI 无浏览器 ⇒ 必假红），只作本地测具。⚠ **落码时守卫误报过一次**：正则只匹配 `2 * TILE_BLEED`，而真实现写的是 `TILE_BLEED * 2` ⇒ **真实现被判红**。教训：**口径门要匹配语义，不能匹配写法**（乘法顺序、变量名、助记符都不该成为红线）；这类 brittleness 会让人把守卫当噪声关掉。同族 K-030（产物新鲜度）、K-043（脚本自证）。
  **追记（2026-10-03 收口，接缝是「窄窗口现象」）**：修后共测 **12 个档位**（dpr 1/2 × zoom {0.2, 0.5, 0.8, 1.0} + **dpr 3**），接缝**一律为 0**；而修前**只在 `zoom = 1.0`（dpr 1 与 2）**检出。两条要点：
  ① ⛔ **「重叠 ≥ 1 设备px 才盖得住」不可当机理** —— 低 zoom 处重叠**更小**（`zoom 0.2 × dpr 1` = 0.2 设备px）却**未检出** ⇒ 接缝是否出现与 `zoom × dpr` **不是单调关系，尚未建立**。外扩量的依据是「**已实测有效**」，不是「算得出来」。
  ② ⚠ **dpr 越高不等于越明显**（与直觉相反）：dpr 3 未检出，dpr 1/2 的 `zoom 1.0` 反而检出 ⇒ 白线是**窄窗口现象**。⚠ 顺带纠一处**我自己写错的推论**：外扩量在**设计域**，重叠的**设备**像素 = `zoom × dpr`（不是「dpr ≥ 1 ⇒ 恒 ≥ 1 设备px」）。
  ⛔ 残留边界：以上若为 harness/Chromium 口径，则 **iOS Safari 的 AA 规则一致性未证**（Canvas2D 光栅化跨引擎无强规范）。

- **[判据渲染][K-102] 给渲染链加「跳帧」类优化时，落点选在回调时机而不是返回值形状；形状一变就击穿整帧封箱基线，而跳帧带来的宿主契约变化必须同批登记**（来源 WXG-T-248 / ADR-0030 §5.0.2，2026-10-05）
  现象：要做「内容没变就不重画」。候选落点有三：① 游戏侧声明 revision；② 把指纹塞进 `RenderModel` 返回对象；③ 在 `App._render` 跳过 `onRender`。其二是陷阱：
  `RenderModel` 多一个字段 ⇒ `wxg-t-211-s3-seal.json` 这类以 `JSON.stringify` 为口径的**整帧封箱基线当场漂移**，必须走 QA 复评才能接着跑。
  根因：封箱基线钉的是「输出形状」，而门控真正需要的是「是否递送」——两者本可正交；把判据塞进数据面是把零成本改动变成了基线换代。
  规避：① 跳帧只做在**调用/回调层**（适配器不持跨帧状态，失效口集中一处）；② 跳帧 = **宿主契约变化**（`onRender` 不再是逐帧钩子 ⇒ 不得在里推状态、不得依赖 `alpha` 每帧变），
  必须同批登进控制清单正本并把警示写进接口 jsdoc，⛔ 不得当「内部优化」静默上；③ 失效面要逐项列举而不是只靠指纹：初始化 / 回前台（`onShow`）/ `resize()`（设计尺寸不变但表面已换）/
  开关由关翻开——用 `NaN` 哨兵（永不自等 ⇒ 必重画）一处表达「强制脏」，比较路径零分支；④ **不可靠哈希的帧宁多画不漏画**：本例 `blit` 的 `fx` 袋无固定可哈希口径
  ⇒ 掺一个每帧自增的 `_frameSeq` 使含 blit 帧恒判脏，并用 `ponytail:` 注释登记上限与升级路径；⑤ 内容指纹要按**插入序**混字段而非按键名 switch（新增字段自动纳入，无维护欠账），
  但**顶点/缓冲类旁路数据必须另走**（命令里只有 `offset/count`，不混旁路就是伪绿判据）；量化粒度（1/64 设计px）要写成**契约**而非精度注脚。
  追记（2026-10-05 WXG-T-249・**本条 ④ 的「损失小」理由已被实测推翻**）：当时给含 blit 帧判脏写的上限理由是「它们的每帧成本在上传不在命令重放 ⇒ 损失小」；
  分层上界实测证明：非珠层每帧仍付 **13 dc + ≈0.9 ms CPU + 1.3–1.8 ms GPU**，而取证面两档 `drawn` 全部 **150/150**（`chg` 只 3–4）⇒ **含 blit 的载体完全吃不到跳帧收益**。
  ⇒ 做法升级：`ponytail:` 上限必须同时写清「损失小」的**可验前提**；一旦实测拿到相反数，**先改注释理由再回写 ADR**，并把该项从「延后」升格为**采纳门禁的硬前置**（⛔ 不得只加一条新注释而不修正旧理由）。
  追记二（同日 WXG-T-250・**上限已换档**）：`fx` 本就属 JSON 安全的封闭联合（`string | number | boolean | readonly number[]`）且构造方钉住键序
  ⇒ 「无固定可哈希口径」不成立，字段遍历改成**一个递归 mixVal** 即可（⛔ 不需要键名白名单），`_frameSeq` 整体删除。
  ⇒ 可复用的判据：**保守出口（恒判脏）往往是「没查值域」而非「查了做不到」**；动手前先读值域定义与它的键序约定。
  新上限随之换位置：指纹计纹理**引用**（`textureId`）不计像素 ⇒ 就地重烘同 id 纹理对门控隐形；登记时必同时列出**为何今日安全**（内容入 key）与**何时失效**（出现就地重烘的生产者）。
  判例引用：`packages/framework/src/core/render/render-model.ts::signature`、`packages/framework/src/compose/app.ts::_render`/`dirtyGate`、
  `docs/architecture/control-manifest.md §8`、`production/qa/beads/evidence/carrier-bench/gate-ab*/`；同族 K-082（封箱基线只归因不代改）、K-084（冻结量换源需同批登记复评）、K-100（先量脏帧再比载体）。

- **[判据渲染][K-117] tint mask 的透明度不在 A 通道：像素审计必须逐通道，「哪张是权威资产」用重跑生成器比 md5 判定**（来源 WXG-T-257 / WXG-T-258，2026-10-05）
  现象：用户问「这张 mask 是透明底吗」。PIL 采样 8 个点全部 `(178,0,255,255)` ⇒ 我据此答「整张均匀不透明」；
  而真正的结构（斜面环 / 格底 / 格外）与「用户看到的那张红底图」的差别**全在 B 通道**，A 恒 255。
  根因：本仓 tint mask 编码 = `R=d`（暗系数）/ `G=l`（高光）/ **`B=shape`（真透在此）** / `A=255 满幅免疫 Cocos Trim`
  ⇒ **任何按 A 通道的检查（alpha 统计、`getbbox`、红底预览肉眼判）都会得出错误结论**；shader 与 CPU 合成两侧都是
  `alpha = shape`（`out = fx.base·d + (1−fx.base)·l`；【WXG-T-259】旧 CPU 式多乘一次 `shape`，已按 GPU 口径去掉）。
  另一层根因：harness 经 `/mask-assets/` 只读映射吃
  `tools/mask-preview/cocos-assets/`（定稿正本），Cocos 吃 `cocos/assets/textures/`（手抄件）⇒ **两端不同源**，
  于是「harness 效果 ok、真机/另一档缺底色」这类分裂可以长期存在而不被任何测试抓到。
  规避/做法：① 审计 mask **一律逐通道列「唯一值 + 计数」**，不看合成色、不采样几点下结论；
  ② 判权威资产 ⛔ 不比 mtime、不比 git 状态，而是**把生成器拷到 temp 重跑**（jsfxr 式确定性）比 md5 ——
  与定稿目录逐字节相等者即正本，不等者即漂移；③ 「两端同源」要**进门禁**（等值腿，无产物也跑），
  否则修完这次下次还会漂；④ 透明度这类**像素级属性**的语义变更，必须同时写**像素断言**（真函数直调 + 统计），
  静态口径门不算证据。
  判例引用：`tools/mask-preview/export-cocos-textures.py` 头注、`tools/scripts/check-cocos-mask.mjs`（定稿等值腿）、
  `packages/framework/src/core/bake/{tint-composite,mask-tile}.ts`；同族 K-047（写方读方不同源 ⇒ 假绿与自毁并存）、K-089（守卫能不能红）。
