## 判据渲染

- **[判据渲染][K-052] 动效时长常量一旦决定「事件发生在哪一帧」，它就是玩法时序而非表现层参数，判据与守卫都得换档**（来源 WXG-T-150，2026-09-17）
  现象：解环器相 A 的 200ms 在美术卡里是「高亮闪一下」。采「先预警 → 后动手」裁定后，这 200ms 同时决定了 `bead:placed` 发射帧、过关判定帧、托盘可取状态帧 ⇒ 它**不能**再挂在表现层槽（`_update` 尾部那串「不被 PAUSED 冻结」的动画步进）上，必须走 `playing` 相位守卫，且 `paused` 只能**冻结不作废**（道具已扣次）。
  根因：GDD/美术卡的分类轴是「谁看得到」，工程的分类轴是「谁改状态」；一个时长跨两轴时，纸面归属会把它误导成可随意调的观感参数。
  规避：① 建**判据三层**：包络（纯函数）／**时序（真链 + 事件计数 + 门两端各一例）**／观感（命令层几何与 α），三层各一条 describe，别用观感例代判时序；② 该时长在**三处同时钉注**（常量头注、持有字段的注释、规格落码注），写明「改它 = 改玩法」；③ 既有的其他单重启门（本例 `FILL_POP_RESTART_GATE_MS`）**优先旁通而非软化**：另开独立逐颗队列让每颗拿到完整包络，原门常量一字不动；④ 相位作废口径要逐条写死：`paused` 冻结 / 其他非 `playing` 作废 / 重装配（换关·重试·崩溃恢复）作废、过关判定排到序列末。
  判例引用：`games/beads/src/config/tuning.ts` G2′ 常量块头注、`games/beads/src/game/beads-game.ts::SolverFxQueue/_stepSolverFx`、`games/beads/tests/solver-vfx.test.ts` ②组 8 例（199ms/201ms 门两端 + 暂停/换关守卫）；同族 K-044（不可判定子句只能产 PASS\*）、K-040（判据变更归因）。
- **[判据渲染][K-055] 「连通块」API 的返回序是行主序、不是距锚序：「就近/最近」语义取前 N 前必须显式重排**（来源 WXG-T-168，2026-09-18）
  现象：落实用户裁定「空槽不足 ⇒ 收离点击位置最近的 N 颗」时，直接取 `collectMisplacedGroup` 返回 `cells` 的前 N 颗 ⇒ 单测当场暴露收进去的是**最远**的那颗（锚点在组中段时，行主序把它上方的同组珠排在最前）。该 API 末尾有一句 `out.sort(行主序)`，BFS 天然携带的**距锚层级**在出口被抹平。
  根因：「连通块」与「距锚远近」是**两种不同的序**：前者由 flood-fill 的 `out` 数组天然携带，后者需要显式度量；末尾 `sort` 的初衷只是让结果稳定可测（行主序确定性），却把序的语义偷换成「坐标序」，而调用方按函数名（`…Group`）自然会读成「距离序」。
  规避：① 凡「就近 / 优先 / 最近」语义，取前 N 前**必须显式重排**（本例按到锚珠的欧氏距离平方升序，平局回退行主序），并在被调函数头注写明「**本函数返回行主序，非距锚序**」；② 判据必须能**区分两种序**——构造锚在**组中段**的用例（锚珠上方仍有同组珠）；若只测「锚在角落」，两种序恰好一致 ⇒ 伪绿；③ 排序键用**距离平方**（整数、免开方），平局回退既定稳定序，避免浮点误差与顺序不确定（L4 确定性）；④ 部分收纳类语义还要同步定义**余量归属**（本例余珠留格、锚改指剩余首颗且不发事件），否则「就近」只对首批次成立，续点就漂。
  判例引用：`games/beads/src/entities/grid.ts::collectMisplacedGroup` 末尾 `sort`、`games/beads/src/game/beads-game.ts::_nearestFirst` / `retrieveSelectedGroup`、`games/beads/tests/retrieve-landing.test.ts`（就近续点 3 例）；同族 K-035（「规格已写」≠「代码已实现」）、K-054（未登记 ≠ 已证伪）。
- **[判据渲染][K-056] 渲染里「未解锁/扩展」的视觉语言必须随容量语义常量派生：裸行号判定会把已开放行画成未开放，并反噬成「假容量」缺陷报告**（来源 WXG-T-168，2026-09-18）
  现象：托盘第二行显示成淡色虚线、看不出是可用的开放槽；用户据此报「容量只有 12，珠子却跑进第二行」。真因既不在容量也不在配色：`drawTray` 里 `dashed = row > 0` —— 虚线语言本应**只属扩展行**，但基础容量 24（2 行）时，**基础第二行也被判成虚线**。
  根因：视觉语言绑定的对象是「相对行号」这种**随数据变化的位置**，而不是「是否属于扩展容量」这一**语义**；容量常量一改（24→12）同一行号的归属就翻转，旧判定立刻失真。更隐蔽的是它会**反向污染需求判断**：玩家/测试看到的「未开放」是渲染产物，却被当成容量事实上报，排查方向被引到数值侧（本例先排查容量、再回头才发现是渲染）。
  规避：① 渲染中的状态语言一律由**语义常量派生**（`row >= ceil(TRAY_BASE_SLOTS / TRAY_COLS)`），禁止用裸行号/下标表达「第几行之后算扩展」；② 容量常量变更时，**渲染判定与容量判定必须同批复核**（本例改 12 后虚线判定自动正确）；③ 收到「容量/数量不对」类反馈，先分清**模型事实**（`tray.capacity` / `freeCount`，用一条 Node 断言钉死）还是**呈现事实**（描边/配色/可见行数），再决定改哪一侧；④ 与 K-051 同族 —— 纸面归类的值/口径会随并行单失效，落码时必须差分复算一次。
  判例引用：`games/beads/src/view/view-model.ts::drawTray`、`games/beads/src/config/tuning.ts::TRAY_BASE_SLOTS`（§3.4 v1.30，24→12）；同族 K-051（增量值须差分复算）、K-030（产物新鲜度假绿）。
  追记（2026-09-20，WXG-T-179 · **同族的「上游加约束、下游仍用全量池」形态**）：给生成器加 `--colors N`（限制用色数），实现里把超限色重映射到保留色集，但**下游的平衡环节仍以「全调色板」为候选池** ⇒ 它会把刚被禁掉的色**复活**：`--colors 4` 实测产出 **5 色**、`--colors 3` 产出 **4 色**，限制形同虚设。同轮另有一处**同型**：脚本把色板大小硬编码成 8（`new Array(9)` / `for (c <= 8)`），加 `--palette N` 后这些位置全成**维度泄漏**（越界/漏色），须逐处改为单一常量；更隐蔽的是**跨执行上下文**——`page.evaluate` 内的代码**看不到 Node 侧常量**，写成 `PAL_N` 会在浏览器里 `ReferenceError`，只能走**传入参数**（`pal.length`）。**规避**：① 上游一旦引入「允许集合」（白名单 / 子集），**所有下游选择点必须收到同一集合**（本例 = 给 `balance` 传 `allow: Set`），无可用目标时**如实返回 note 而不越界**；② 把「维度 / 上限」抽成**单一常量**并全量替换硬编码（`8` → `N`），改完用一次**边界用例**（本例 `--palette 2`）逼出越界；③ 跨上下文（Node ↔ 浏览器）传值只能走**参数**，不得引用外层常量；④ 判据 = 「产出 ⊆ 允许集合」且「产出 ⊆ 板长」——一行断言即可抓住，比肉眼看产物可靠。
- **[判据渲染][K-063] 会「静默转移」的锚不能当距离排序基准：消费序基准与展示坐标必须分离**（来源 WXG-T-183，2026-09-20）
  现象：board 锚组批量直填（WXG-T-180）后锚珠被填 ⇒ 锚静默转移到剩余组首，此后所有「就近」排序继续读锚坐标 ⇒ 基准随每次消费漂移；且转移复用「头珠改指」同一写入点——展示坐标与排序基准共用一个字段，改展示即动排序（展示头珠跟随转移本身合理，错在排序也跟着走）。
  根因：「锚」身兼两职——消费序基准（应恒定可复现）与展示头珠（应跟随剩余组）；凡锚会静默转移的实现，距离序都隐式依赖「已消费到哪一步」，同一盘面同一点击的行为随消费历史变化、无法离线推演。
  规避：① 选中那一下固化拾取坐标（`anchorRow/anchorCol`，此后任何路径不改），`row/col` 降级为纯展示头珠；② 所有消费序（批量填、部分收纳）统一以固定锚为基准——度量（切比雪夫/欧氏）可换，**基准不可换**；③ 批量填用同序配对：目标序（BFS 由近及远）× 组员序（距锚升序）按索引配对，逐目标就近取珠的 O(n²) 扫描与基准漂移一起消失；④ 判据必须能区分新旧序——构造「目标离拾取点远、离某组员近」的几何，使旧序选 A、新序选 B；只测「目标就在拾取点旁」两种序一致 ⇒ 伪绿。
  判例引用：`games/beads/src/game/beads-game.ts::_boardSelected/selectBoardBead/retrieveSelectedGroup/_tryDirectFillFromBoard`（src 与 cocos 镜像）、`games/beads/tests/misplaced-direct-fill.test.ts` 选豆点基准例；同族 K-055（连通块返回序 ≠ 距锚序——本条是其下游：显式重排之后，**重排的基准点**还必须恒定）。
- **[判据渲染][K-067] 「就近」排序的度量必须与集合的连通定义同度量，且多消费口共用一份序**（来源 WXG-T-186，2026-09-22）
  现象：错位珠组按 8 向**连通**生长（`collectMisplacedGroup`），两个消费口却各按**几何**距离排序（直填 = 距选豆点切比雪夫、取回落槽 = 欧氏²）⇒ 组一拐弯或中间有缺口就「跳过缺口先吃对岸珠」（玩家读到隔空取物）；同圈层由行主序裁决 ⇒ 最左上的珠最先被吃（与玩家「从手边一片揭起、最远的留到最后」相反）。两路口径在 2 万随机组形上有 **89.4%** 给出不同序。
  根因：成员集合由**图连通性**定义、「最近」却用**平面坐标**距离 —— 两者在带洞/拐弯的形状上必然分歧；且两处各写一份排序代码，改一不会通知另一。
  规避：① 集合按连通性定义时，「最近」取**该连通图上的距离**（从锚 BFS 层号），几何距只在集合本身按几何定义时才对；② 序**只在拾取时算一次**（不设颗数截断），各消费口取同一份产出的前缀 —— 口径一致由「共用一份」构造保证，不靠两处写成一样；③ 「不跳空洞」与「不吃散（不吃割点）」**数学上互斥**（往外揭迟早要吃桥珠），必须显式定让步方向并写进规格，别指望调权重能两者归零；④ 判据要能区分新旧序（带缺口形状 + 「全程不跳」与「任意 k 剩余仍连通」两条不变式）——直链/小坨上两种序重合，拿它当基准例 = 伪绿。
  判例引用：`games/beads/src/systems/consume-order.ts::planConsumeOrder`、`games/beads/tests/consume-order.test.ts`；同族 K-063（基准点须恒定 —— 本条是**度量形态**须与集合定义同构）、K-055（连通块返回序 ≠ 距锚序）。
