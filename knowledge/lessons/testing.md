## 测试

- **[测试][K-061] `noAssemble` 下手工铺盘 ≠ 装配：子系统内部索引未建，表现为「点名了但不动手」，极易误判为业务缺陷**（来源 WXG-T-128 / commit 61d2911，2026-09-19）
  现象：为构造「solver 归位致过关」局面，用 `createBeadsHarness({ noAssemble: true })` + 手工 `grid.fill()` 铺满盘、再把一格染色 ⇒ `misplacedCount === 1`（**读面正确**），`usePowerup('solver')` 返回 `true`、`solverProgress` 从 0 走到 1 再归零 —— 但**棋盘纹丝不动**（`misplaced` 恒 1）、`phase` 恒 `playing`、`level:cleared` 计数 0。第一反应是「solver 有业务缺陷」。
  根因：`noAssemble` 只跳过关卡**装配**，而装配期同时建立了子系统（解环器点名队列等）依赖的**内部索引 / 缓存**；手工 `fill` 只改格子读面（`cell.state` / `isMisplaced`），不重建那些派生结构 ⇒ 点名清单为空、相 A 空转、相 B 无到点。**读面正确 ≠ 内部结构正确**。
  规避/做法：① 造局面优先「**默认装配 + 官方构造器**」（先装配出就位盘，再用异色对调 / `setBead` 造受控错位），不要为省事用 `noAssemble` + 手铺；② 断言「**行为已发生**」而非「状态读面正确」——本例若只断言 `misplacedCount` 与 `usePowerup` 返回值，会得到一个**自洽但完全空转**的绿；③ 排查「点名了但不动手」先怀疑装配面、再怀疑业务面（临时打印点名清单长度即可分辨）；④ 定位这类**静默空转**最快的办法 = 临时探针用例逐帧打印 `phase` / 进度标量 / 棋盘计数（用完即删，勿留在测试面）。
  判例引用：`games/beads/tests/scene-vfx.test.ts` 恒播满例（首版失败记录）；同族 K-038（测试入口 ≠ 真实入口）、K-042（测试失去自证能力）。

- **[测试][K-062] 事件驱动宿主的输入位移必须进单测：prev 在帧首结算会把帧间到达的位移吞成 0**（来源 WXG-T-178 / 真机反馈「能缩放不能拖动」，2026-09-19）
  现象：Cocos/微信真机上双指捏合正常缩放，但单指拖拽**完全不平移**；同一份代码在 Node 单测（501 例）与浏览器 harness 里全绿。插桩读数：拖拽分支每帧都跑（`panFrames=69`），但喂进去的位移 `panDxSum=0`，而指针坐标确实在变。
  根因：`InputManager.beginFrame()` 里做 `_prevX = _x`，而事件驱动宿主（Cocos）的原生 `touch-move` 到达在**两个固定步之间**（上一次 `endFrame` 之后、下一次 `beginFrame` 之前）⇒ 拷贝时 `_x` 已是新值，`dx = _x - _prevX` 恒 0。位移判定用的是「当前位置 − 按下位置」，所以「进了拖动态」看起来一切正常，只有真正要增量的地方拿到零 —— **症状与被吞的量正好错开一层**。
  规避：① 采样器的 prev 推进放在**帧末**（`endFrame`，一固定步 = 一输入帧），使事件驱动宿主与同步宿主同一语义；② 单测必须有一条**按宿主真实顺序**写的用例：`endFrame → push(事件) → beginFrame → 读 snapshot`，断言位移非零、且无新事件的下一帧位移归零；只在 `beginFrame` 之后 push 的同步形**永远测不出这类缺陷**；③ 通用形态：**「坐标对但行为不跟随」先查增量型量（dx/dy/dt/count delta）是否被采样时序吞掉**，别去查几何或语义；④ 修法要覆盖**所有走该通道的游戏**（本次两游戏共用 core，需同时验证另一游戏不读该量 → `grep .dx` 全仓确认影响面）。
  判例引用：K-037（指令流可证 ≠ 宿主可证）、K-036（全绿不构成证据）、K-042（断言不得与真源共用同一个错）、K-054（未登记 ≠ 已证伪）。

- **[测试][K-076] 脏工作树里「这条测试红是不是我引入的」必须用 stash 隔离实测判定，不得凭直觉归因**（来源 WXG-T-169 / commit c7d157d，2026-09-26）
  现象：本单改动落码后全量测试剩 1 条红（`bead-style-seal` 腿 4 整帧命令数对不上已登记基线），而它与本单同族（都是「渲染」），极易被误读为本单引入 ⇒ 下一步就是去「更新基准让它绿」（封箱类基准的红正好是被禁止那样做的）。
  根因：门禁红是**时点性**证据，工作树上同时存在他人未提交改动时，「红的集合归属」不可从「我改了什么」反推；本次真因是并发会话在 `view-model.ts` 新增缩放控件，使整帧 +3 rect / +3 text / +1 circle。
  规避：① **只 stash 自己的文件集**做对照：`git stash push -- <本单文件>` → 复跑该测 → 仍红即证与本单无关 → `git stash pop`（整树 stash 会吞掉并发会话的工作，禁用）；② 结论写进提交信息（「唯一红 = …，经 stash 隔离证明非本批引入」），否则下一个读者得重做同一实验；③ 封箱/基准类判据被他人红时，**不得为绿改基准**（K-051/K-053 口径），交回改动的那一单重封；④ 并发改动还在实时流入时（看 mtime / `git status` 新增脏文件），红灯集合本身会变，本判定只在**当时有效**，提交前重做一次；⑤ 尾报可能遮真因（本例 ctx 拦截报「索引不一致」，实为另一道预算门）——拦截后先看完整输出再下结论。
  判例引用：同族 K-040（读数变脸须逐条归因）、K-036（全绿不构成证据）、K-037（指令流可证 ≠ 宿主可证）、K-045（并发工作树的暂存原子性）、K-010（假阴性输出不得当证据）。

- **[测试][K-082] 珠体族视觉改动 ⇒ 封箱对照腿必然红是预期行为，唯一合法通道 = 复评归因（禁自更新基准）**（来源 WXG-T-214，2026-09-26；原 [判据]，因 criteria 分片越 B 阈按 §4 移册）
  现象：beads 珠体视觉改动（`BEAD_DRAW_INSET` 4→2、孔径取整）落码后，`bead-style-seal.test.ts` 腿 1（十层对照臂 96 例 ≡ HEAD）与腿 3（孔层 hash ≡ 登记值）红——**没有任何人改封箱代码**，基准却「自己变了」。
  根因：对照臂**故意吃活常量**（`legacy-ten.ts` 头注明写「保持绝对 `BEAD_DRAW_INSET`（= HEAD 封箱口径）」）⇒ 改常量 = 改对照臂的**输入**，输出必变；腿 3 的孔层 hash 同理。这是设计使然：对照臂钉的就是「什么都没变」，而珠体族三键（legacyFlow / facetNonHoleLayers / facetHoleLayer）**永不走基准修订的例外通道**——改了就该红，就该回炉。
  规避：① 改珠体系数/几何**之前**先预期哪几条腿会红、把复评归因排进交付清单，不要收口时被红吓回改基准；② 唯一合法通道 = `§K.5.1` 复评归因（先例 WXG-T-212：比较基改指 `s3.*` + provenance 流级差分 + 反例判红自证），⛔ 禁自更新、禁 env 后门、禁删断言；③ 非珠体族改动（HUD/底图/带尺）才走「例外通道」三条件；④ 改常量前 `grep` 该常量在封箱臂/钉值测试里的消费者，把判据同步清单列进交付（本例同批同步了 4 个文件的孔径取整期望 + C12 钉值）。
  判例引用：`games/beads/tests/bead-style-seal.test.ts` 头注「珠体族三键永不走此通道」、T-212 先例；同族 K-051（纸面推论须实测复算）、K-053（不静默删除）。

- **[测试][K-083] 「面积占比 ≥X%」是代理指标不是感知标准；感知判据 = 对比度（3:1）+ 样本视角（≥1°），且面积账必须含圆角修正**（来源 WXG-T-214，2026-09-26）
  现象：给 beads 格内「错豆可辨」立判据时，直觉写了「目标色可见面积 ≥30% 格」；自查发现被指的元素**面积达标但线性尺寸远不够**：环宽 1.5 CSS px（0.05° 视角）、孔 ⌀5.7 CSS px（0.17°）——远低于小视野辨色可靠区（≥0.5°，稳定 ≥1°）⇒ 面积够 ≠ 能辨。
  根因：感知上可引用的只有两类门槛——**对比度**（WCAG 1.4.11 图形对象 ≥3:1，判「是不是同一色」）与**样本视角尺寸**（判「这是什么色」；30cm 观看 1° ≈ 5.2mm ≈ 33 CSS px，<0.5° 后辨色阈值显著变差）；面积占比与两者都不同构。另：面积账若用**方角近似**会多算 ~5% 珠色（圆角方面积 = `面² − (4−π)·r²`），本例 56:44 的估算在圆角修正后实为 **49.6:50.4**——差值恰好改变「均衡度」结论。
  规避：① 面积判据一律**标注「代理指标」**，不得写进验收条当感知标准；② 「是不是同一色」走对比度门（逐色对 ≥3:1，等亮度对会当场判红=好事）；③ 「这是什么色」的样本要求 = **同色连片 ≥3×3 格**（1.46°）——写进生成侧约束而非渲染参数；④ 任何格内面积账先声明形状口径（方角/圆角、内缩基准是格径还是格），口径不一致的两组数不可直接比。
  判例引用：`games/beads/art/cell-standard.md`（§3 J2 代理指标标注、§5 视角结论引用）、`tests/bead-cell-standard.test.ts`；同族 K-035（不写无依据的「已达标」）。

- **[测试][K-085] 缩放/焦点几何的实现与测试一律从布局真源取数，手推「屏幕位置式」必漂**（来源 WXG-T-217，2026-09-27）
  现象：beads 低倍点击「以点击处为焦点放大」连错三版（常量平移项 / 带心锚屏幕插值 / 板半宽符号），每版都是**代数自洽、实算不符**；测试侧同样手推屏幕式，造成「实现红、判据也跟着错」的假归因，单轮排障耗掉大量步数。
  根因：格心的真源式是 `gridLayoutFor` 里的 `left + BEAD_CELL·z/2 + j·BEAD_PITCH·z`（gap 缩放规则不成比例、`BEAD_CELL ≠ BEAD_PITCH`），任何「我以为同构」的屏幕式都会在这些微差上偏离；而不变式测试若用同一份错式，就永远验不到偏离。
  规避：① 需要「缩放后某点落在哪」时，**直接调真源函数**（`gridLayoutFor(cols,rows,{zoom,offset:0})` 取新档零偏移格心，再解 `offset = 焦点屏幕位 − 新档格心`），不写第二套公式——冷路径一次点击一次分配可接受，热路径仍禁 alloc；② 判据与被测面**必须同源**，另配一条不依赖该真源的不变量守卫（同 K-042），防「同源一起错」；③ 焦点补偿会撞上「板小于视口 ⇒ offset 锁 0」的既有平移界，先算清悬挑量再选测试盘（本仓 32×32 @1.0 悬挑 X 503 / Y 210 才可验跟手分支）。
  判例引用：`games/beads/src/systems/board-camera.ts::zoomAtPoint` 注、`games/beads/tests/board-camera.test.ts`「zoomAtPoint」三例；同族 K-042（真源化后须另配守卫）、K-077（缩放改造须整路径盘点绝对量）。

- **[测试][K-086] α 有两个合法计数式（显式 alpha ∨ rgba 色串），不注明就得到同一盘面两套数**（来源 WXG-T-218，2026-09-27）
  现象：数 beads 现役逐格 α 时，同一颗锁定格按门禁 `isRealAlphaLayer`（`alpha<1` **∨** `fill` 以 `rgba` 开头）= **2 α**，
  按「命令级 alpha 字段」读法 = **0 α**；提案正文写的却是「按命令级口径」⇒ 对照表里锁定格、参考图风格估算、
  测量单 `alphaCmds` 埋点三处互相不自洽（没有任何测试会变红）。
  根因：本仓有两条半透明表达路径共存 —— builder 的 `alpha` 字段与 `withAlpha()` 产生的 rgba 色串；
  风格层集惯用前者，`drawLockedBead`/`drawSweep`/debug 路径惯用后者，而计数式只卡前者时**后者被静默放行**
  （反例臂 `fixture-5cmd-3alpha` 就是为此存在：故意只写 rgba 不填 alpha，漏计第二支必红）。
  规避：① 报 α 数时**同批注明计数式**（两支式 / 单支式），⛔ 靠上下文猜；② 跨文档/跨臂对比一律固定用
  **可机检的那支**（门禁两支式），其余只作换算注明；③ 逐处列出「哪层吃 `withAlpha`」的现役事实（本例 = 锁定格两条斜线），
  否则换人重数必得另一套数；④ ⛔ 把命令级 0 α 写宽成「0 次半透明混合」——Canvas2D `drawImage` 仍走 source-over，
  GPU 是否真关混合只能由帧时间实测判（同 K-037：指令流可证 ≠ 宿主可证）。
  判例引用：`games/beads/src/view/bead-styles/contract.ts::isRealAlphaLayer`、`tools/scripts/check-bead-style-pool.mjs`（反例臂 `fixture-5cmd-3alpha`）、`games/beads/src/view/bead-render.ts::drawLockedBead`；同族 K-037（全绿不等于宿主可证）、K-035（不写无依据的已达标）。

- **[测试][K-088] 渲染形态换轨（图元 → 位图）会让「以图元为统计域」的机检判据当场不可执行 ⇒ 换轨批必须先重设判据，⛔ 沿用旧式当已验**（来源 WXG-T-219，2026-09-27）
  现象：beads 珠面改为「预烘位图皮肤资产」后，C12 主体色不变式的判据「珠面 pixel 数占比最大的端点色，统计域 = **珠面族图元**」
  失去输入 —— 一个已填格在命令流里只剩一条 `blit`，没有任何「图元」可枚举；同理 P7「有豆/无豆 = 同一张图」原本由
  「同一个 B0 rect 恒画」**结构保证**，底图与珠体分属两张纹理后退化为**工艺保证**（缝宽/色档一致性无人守）。
  根因：机检判据的**统计域**是与渲染形态耦合的隐含前提，文档里只写了判据本体、没写「本判据仅在逐格矢量下成立」；
  换轨时改的是渲染，红的是判据的适用面，而它**不会报错、只会静默空转**（枚举到零图元 ⇒ 「占比最大」无从谈起）。
  规避：① 任何「换渲染形态」的裁定批，交付清单里必须有一条**判据重设计**项（新统计域 + 新可机械化的表达式），
  ⛔ 用「基准重抓」代替判据重设计；② 降级要写成语义变化而不是消失 —— 本例把双指标门禁（命令 ≤7 / 真 α ≤2）
  显式降级为**配方复杂度上限**并写明它不再约束运行时开销、风险换维到烘焙耗时与纹理张数；③ 换轨批必须同时登记
  「因旧门禁被移出、自此具备翻案资格」的历史记录，并注明翻案的前置验证（细线 2.0× 降采样实机质量），
  ⛔ 把「门禁不再约束」直接读成「当年被拒的风格现在可以进池」。
  判例引用：`docs/architecture/adr/ADR-0027-beads-prebaked-bitmap-skin-assets.md` DEC-2 / §4.2、
  `docs/architecture/control-manifest.md` §19 第 2 条、`games/beads/design/proposals/zoom-bake-mip-validation.md` 测试 14；
  同族 K-035（不写无依据的已达标）、K-082（封箱基准禁自更新）。

- **[测试][K-094] dev 调试注入不得绕过玩法命令层直写权威状态（守恒类玩法会被造成死盘）**（WXG-T-244 二十一）

- **[测试][K-103] 截图差分非零不直接计缺陷：先拿「与被测改动无关的两个历史运行」做控制对照，把运行间状态漂移与真缺陷分开**（来源 WXG-T-248 / ADR-0030 §5.0.2，2026-10-05）
  现象：脏帧门控 A/B 的两档截图差分 0.25–0.34% 非零像素。门控的本意就是「干净帧不重画」⇒ 第一反应是「旧帧残留 = 真缺陷」。
  根因：本仓盘面带**逐运行变化**的状态（`createRng(Date.now())` 抽珠 + HUD 计时文本），所以**任何**两次运行的截图都不逐像素相同；
  把「两档互差」单独拿出来看，等于把一个对所有运行对都成立的现象记到被测改动头上（K-095 同型的「归因错层」）。
  规避（三步，缺一不可）：① **定位到带**：先打行/列直方图（本例 8×10 带），看差异集中在哪——本例全部落在 HUD 计时与托盘三小簇，
  **盘面中段逐像素为 0**（⇒ 「陈旧帧」若为真应当先出现在盘面上）；② **做控制对照**：拿改动**前**的历史截图分别与今日两档比，
  若差异**同带且同量级**（本例 4823 px / 3361 px）⇒ 归因为运行间漂移；没这一层就不能下「非缺陷」的结论；
  ③ **结论措辞诚实**：⛔ 不得写「两档逐像素相同」，要写「差异已归因为 X，证据 = 对照 Y」；并且当状态不确定时，
  把可控制变量钉住才是根本解决（固定种子 / 冻结计时器），本例作为取证 spike 可接受，但**正式对拍腿（S3）不得沿用这个口径**。
  判例引用：`production/qa/beads/evidence/carrier-bench/gate-ab*/` 与同目录 `vector-z*.png`（历史对照）、`docs/architecture/adr/ADR-0030-*.md §5.0.2` 结论 5；同族 K-095（先定性再选层）、K-092（定点参数是定位前提）、K-040（判据变更归因）。

- **[测试][K-118] 修像素级缺陷前先看「门是什么类型的门」；目标文件未入库（无 HEAD 基线）时 A/B 对照臂 = 摘掉新增那一笔调用重建**（来源 WXG-T-257 / WXG-T-258，2026-10-05）
  现象：`check:board-seam`（C1–C4）与 `check:cocos-mask` 双双绿，但合成出的 L0 底 tile 实测 **50.7% 像素 alpha=0**
  （格底外圈 3dp + 出血圈全透）⇒ 盘面珠格四周露背景、「−0.3 色档底色」消失。两条门一条只证「外扩系数存在」，
  一条只证「文件在包里」，**都不证像素属性** ⇒ 门绿与缺陷并存。
  根因：门禁的**类型**与被修属性的**类型**不匹配（静态文本门 vs 像素级不变式）；此外被改文件在 git 里是
  `??`（untracked，上一批新增未提交）⇒ `git checkout HEAD -- <file>` / `git stash` 这类常规对照手段直接失败，
  没有基线就没有「改之前长什么样」的自动证据。
  规避/做法：① 开工前先给缺陷**归类**：口径类（可静态断言）/ 像素类（必须像素断言）/ 时序类（必须多次采样）；
  像素类修复的判据一律写成「真函数直调 + 计数」，⛔ 不要指望既有静态门顺带拦住；② 无 HEAD 基线时的对照臂：
  **用脚本把新增的那一笔调用摘掉 → 重建 → 同参数截图 → 复原**（⛔ 别用 `sed '\s'`，BSD sed 不支持 ⇒ 静默 no-op
  会得到「差异 0.00%」的假结论；改完必须断言目标串计数已归零）；③ 修的位置优先选**所有 caller 汇聚的那一处**
  （本例两条出口共用一个 `SHAPE()`），比在每个 caller 加守卫更小且不漏兄弟路径；④ 对照臂若因未使用变量而
  `noUnusedLocals` 报错，只要 tsc 仍 emit 就有效，但要在在册里写明该改法，避免下次被当成真失败。
  判例引用：`packages/framework/src/core/bake/mask-tile.ts`、`packages/framework/tests/core/mask-tile.test.ts`（腿 ④）、
  `docs/architecture/adr/ADR-0030-*.md §5.8/§5.9`；同族 K-089（假绿守卫）、K-103（截图差分先做控制对照）、K-037（指令流层可证 ≠ 屏幕层可证）。
