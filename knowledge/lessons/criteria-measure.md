## 判据实测

- **[判据实测][K-126] 同一张美术在不同像素网格下量出的「设计 px」并不相同 ⇒ 跨批复用实测值前先对齐网格**（来源 原型 v2 第十批 / 无单，2026-10-13）
  同一主菜单美术存成两档：`v1-mainmenu-final.png` 1520×2736（`sx 2.027 / sy 2.051`）与
  `menu-750x1334-at2x.webp` 1500×2668（`sx=sy=2.000`）。按设计 px 量同一批元素得到**两套数字**
  （门楣梁面 246–308 vs 247–306、招牌 65–205 vs 88–212、顶栏三颗自顶 46–104 vs 31–95）——
  不是矛盾，是**多出的那 20/72 px 留白把整幅画往下推了**。前一批据此定的落位（牌位 255–293）
  恰好仍在梁面内属运气，不是校验过。口径：① 量数必须注明来自哪张图；② 非整数倍网格（`sy≠2`）的图
  **降级为构图参照**，不当事实数字来源；③ 交付规格由用户明令时（本批：UI 原型一律 750×1334@2x），
  整屏件按该尺寸出，**裁切/拼图件须在清单里标「非规格件」**，否则下一个人拿 3000 px 宽的拼图当基准。
  同族 K-123（登记违例前先确认判据对象存在）、K-122（两端同源要进门禁）。
  代码锚：`temp/l4-proto2.py`（一次性，不入库）、`design/proposals/ui-style-redesign/menu-architecture.md §5.1b-2` 第九/十批。

- **[判据实测][K-128] 在暖色浅底上抠「亮白但自带渐变」的实体：判据要用**中性度**，亮度阈值会吃掉下半个实体**（来源 原型 v2 第十批 / 无单，2026-10-13）
  白盘圆钮（(255,254,255) 顶 / (252,255,252) 底，渐变到下部才暗）坐在奶油底 (253,246,235) 上：
  亮度门 `min(r,g,b) > 244` 只圈到上半亮核，实测 Ø51 vs 真盘 Ø59（**小 8 px**），抠出来贴过去缺一块；
  换 `r − b < 9`（白盘 0–2 / 奶油底 18–22 / 暖色柔投影 18）**一条判据同时分开「底」与「投影」**，
  量得 Ø54×54 正圆。配套三条：① 归一尺寸时切圆取**短边半径 −1**（齿轮那颗自带白晕，长边会把晕吃进来 →
  缩放后一圈白边）；② 擦原位掩码必须**膨胀 ~14 px**，只擦实体像素会留下投影 ghost 环；
  ③ 搬走的钮要**合成一枚柔投影**再贴（原投影被擦掉了，不补会有贴图感）。
  代码锚：`temp/l4-proto2.py::disc_mask/disc_cut/with_shadow`；同族 K-126。

- **[判据实测][K-130] 量「某件的底缘在第几行」必须把「本体描边」与「柔投影」分成两个读数，占比型判据会系统性把投影算进本体**（来源 定稿底图换代·走③压矮 / 无单，2026-10-14）
  现象：同一颗 CTA 胶囊，用「x 窗口内非背景占比 <99%」量得底缘 y-up **68**，用「中心列仍为高饱和本体色（`r−g > 40`）」量得 **72**，差 4 px；而安全带正好是 68 ⇒ 前者报「余量 0（贴边）」、后者报「余量 +4」，同一张图两种结论。
  根因：交互件的烘焙光影是**连续衰减**的（本例描边末行 (168,98,95) → 投影四行 (235,209,197)/(226,212,201)/(233,221,209)/(241,230,218) → 背景 (248,237,225)），任何「非背景」阈值都切不出这条尾巴的终点，切点完全由阈值决定。
  规避：① 判据里写清量的是**本体**还是**含投影包络**，两个数都给，别只给一个；② 本体腿用**饱和度**（本例 `r−g`）而不是「是否等于背景」，投影腿才用背景占比；③ 安全带/碰撞类门一律按**本体**判（投影入带不判违例，但必须显式登记投影末行，否则下一个人会以为已含投影）。
  代码锚：`temp/l5-deliver.py::rim_end / shadow_end`；同族 K-126（网格口径）、K-128（中性度 vs 亮度阈值）。

- **[判据实测][K-131] 当作「后续测量基准」交付的位图必须无损编码，有损重编码会让「未改动区域逐字节相同」这条自证直接失效**（来源 定稿底图换代·走③压矮 / 无单，2026-10-14）
  现象：同一条压矮术式，无损中间件对基准实测「切口以上 maxΔ = 0 / Δ>0 像素 = 0」；落成 q82 WebP 后变 **maxΔ = 23 / 988,947 像素漂移**（1500×2668 全页，噪声集中在硬边）。
  根因：WebP/PNG 之分类比的不是「看起来一样」而是「解码后逐通道一样」；有损编码在每次交付都重采样一遍整张图，于是「我只动了下面一条带」这句话在交付件上无法自证，且代际损失会沿「底图 → 叠放 mock → 再叠放」累加。
  规避：① 区分两类产物 ——**基准件**（后续要被量、要被再叠放）走 `lossless=True`，**取证/评审拼图**（只给人眼看过一遍）继续有损，别一刀切；② 选了无损就把体积代价写进文档（本例 1052 KB vs 145 KB，且 design references 不进包体预算），免得下一个人当失误删掉；③ 若历史上已经用了有损件，**所有读数必须声明取自交付件本身**，否则文档坐标与被量的像素不是同一份。
  代码锚：`temp/l5-deliver.py`（`OUT` 无损 / `EV` q82 同文件并存，即两条通道各写一次的样板）。

- **[判据实测][K-140] 逐对象输出的工具，取数必须按对象名锚定；`tail` 取末行会把最后一个对象的读数当成第一个**（来源 BD-61 收尾批 / 无单，2026-10-18）
  现象：`check:size` 对 `games/*` 逐个报「主包 X KB / N 文件」，我用 `tail -5` 取尾行 ⇒ 把 **breakout 的 1886.1 KB / 24 文件当成 beads**，据此往两份 ADR 里写了「beads 主包 1886.1 KB」与「重建后包体不变」，还把 beads 今日 3422.2 KB 与 10-12 在册 2979.0 KB 的差误判成「约 1.1 MB 成因未查」。真值：**beads 3422.2 KB / 108 文件**（距 4096 红线余量 673.8 KB）、breakout 1886.1 KB / 24 文件；所谓 1.1 MB 差异纯属读数错配，真实差 **+443.2 KB** 与 `cocos/assets/textures/` 24 件投放件合计 **419.1 KB** 吻合（= 10-15/16 主菜单位图集入库）。
  根因：**多对象聚合输出 + 人取“最后一行”的习惯**。输出里每个数字都归属某个对象，但尾行只留下顺序上最后一个，**对象名在更早的行上**——与 **K-047**（写方与读方不同源）同族，只是这次“不同源”发生在**读取端**。⚠ 本仓 2026-10-05 已为完全同型的错误做过在册自纠（`production/archive/TASKS-DETAIL-archive.md:4091`：「上一批我把两游戏读数**对调**了」）⇒ **同一条坑两个月踩两次，说明只写进日记不够，得改工具输出形状**。
  规避/做法：① 取多对象工具的数字一律 **`grep '<对象名>'` 或读整段**，⛔ 用 `tail`/`head` 取“看起来像结果”的那一行；② **改输出形状而不是改人**：`check-bundle-size.mjs` 已加「单行摘要」块（逐游戏一行、行首 = 游戏名、带判定与距红线余量），让 tail / grep 都能读对；③ 引用这类数字时**连对象名与分母一起抄**（“beads 3422.2 KB / 108 文件”），名字与数字绑成一个不可分单元，缺名即不引用；④ 拿数字做历史差集前先确认两次记录的**口径同一**（同 release 档 / 同判定源 / 同对象），否则差异没有意义（同 **K-135**：先对量纲再取靶值）。
  关联：K-047（写读不同源）、K-036（缺对象仍报绿）、K-096（环境与数字都是快照不是现状）、K-135（复用旧尺子先对量纲）。

- **[判据实测][K-149] 组合图（plate）满密度宫进不了「普通关」：规格要的「≤60% 整区域就位」档工具没实现（已补），补完实测又拓出两件事——规格那句「reg60 = 90–96 taps 达标」绑的是旧尺＋合成大色块盘（真实照片同构造现尺要 229–257 步），而门禁⑦ 对 boss 只设下限 ⇒ 出口在 boss 档不在普通关档**（来源 WXG-T-341 / 无单，2026-10-21；**同日六版订正**：初版写「判据堵死大图、物理上进不来」属误判；二版「补上 ≤60% 档即可入关」亦未成立；三版「满盘照片无路可走」不对——越的只是普通关档；四版把 5 倍差归给「旧尺不可平移」也不对——尺子只占 2 倍，剩下是**素材连通度**；五版把「出口在 boss 档」从真闸函数探测升级为端到端冒烟（真入一关、bot 打完、全闸绿）；六版该章已真入表不还原，并拓出「封面图没进包」这条素材腿缺口（→ K-108 ⑥））
  现象：把 64×64 大图用管理页批量导入切成 4 格，连拒三次：① `门禁⑥ DI 非严格递增（L5=360.7 → L6=360.7）`（四格内容相同）② `门禁⑦ 普通关 steps=134 越出 [18, 90]`（小图被重复边缘撑满 32×32）③ `steps=12`（图太稀）。第四次用四张 14×10~14×14 的真实稀疏图（每格 81/96/129/150 颗珠）通过，实测 37/50/68/72 步。当时据此向上报的是「满密度照片类大图物理上进不了关」。
  根因：这件事规格在 2026-09-22 就定案了（`games/beads/design/levels/levels-spec.md` §3.1① 第 159–166 行 / §10 第 83 行 / `tuning.ts:490` 注）：**组合图每一宫的错位密度必须 ≤60%，且要按「整区域就位」（大色块整体搬移）构造**；E1 两轮 bot 实测复现「32×32 全错位宫 176–178 taps 结构性超 420 秒预算 ⇒ 不可入关」，并点名「逐格随机散点式部分错位是反模式」。而构造器 `tools/scripts/level-derange.mjs` 的四档是：甲 = 每一颗全部错位（100%）、甲max = 守恒极值（≈100%）、乙 = 最多 8 对互换（≈0%）、丙 = 无法错位（直接拒）——**规格唯一允许的 ≤60% 那一档根本没实现**。我当时拿甲档拼 32×32 满珠板，撞的正是规格早已判死的那种构造，却把报错读成了“判据不合理”。
  规避/做法：① 造 plate 数据**先读 levels-spec §3.1① 的构造约束**，别从门禁报错反推「判据该改」（本条就是这份代价）；② 缺的那档**已落地**：`buildRegionDerange`（按 8×8 块粒度选子集、块内整体循环移位、超预算整块不搬、无一可搬则落回甲链），plate 每宫默认走它（`server.mjs::planShape` 传 `{region:true}`）。**坑：未被选中的块必须逐格保持原色，⛔ 留 0** —— 0 会被 `solvedToRowstrings` 编成 `.`，等于把整块珠子从盘上抹掉（首轮实测即此病，靠守恒断言拓出）；③ 量纲已实测：**`taps = 2 × steps`**（2002/1001、457/229、513/257，`tuning.ts:677` 注早写了「同一个盘两个数差≈2 倍」），旧尺的 116 taps 上限 = `SEC_PER_TAP 3.6 × 420s`，§3.5 v1.50 已改名重锚为 `SEC_PER_STEP 1.69` + 上限 2500s ⇒ 尺子只能解释 **2 倍** 的差。我据此把「现测比 E1 高 5 倍」也归给尺子，**又错一层**：拿 E1 同口径的 **bs8 合成大色块盘**在现尺重跑 = 99 steps / 197 taps（与 E1 量级吻合），真实照片盘同尺寸同构造 = 1001 steps ⇒ **剩下的 5–10 倍全是素材的色块连通度**。⇒ **对比两个读数前，先确认被测对象是同一个东西**；只对「量纲」不对「对象」，同样会得出一个看着完整、实则归错因的结论（这是 K-135 的第二种破法）。附带实测两条：把照片按众数压块 229→143 步（省 38%），但**压到 4×4/8×8 起 bot `no-move` 死锁**（托盘被整块同色填满、无处落子 ⇒ `cleared=false`）⇒ 压块有天花板；⇒ **≤60% 是构造上限，不是门禁⑦（steps ∈ [18,90]）的达标充分条件**；实测 32×32 满盘宫 reg60 = 229–257 步、reg20 = 168–183 步，只有≈**一个 8×8 整块错位（64/1024 ≈ 6%）= 56–57 步** 才落闸内。⚠ 但越的是「普通关」这一档：门禁⑦ 对 boss **只设下限**（`BOSS_STEPS_MIN=120`，无上限），1256–1692s 也仍在规模闸 2500s 内 ⇒ 满盘照片的现存出口 = 单图当大关首关 boss（读真闸函数 `checkStepsGate` 直接探测证实，不是口头推）。**五版补：这条出口已端到端冒烟证实**——真跑 `POST /api/manage/chapter` 把库里唯一一张满格 32×32 真实照片入成新章首关 boss ⇒ bot `cleared=true` / 1001 步 / 2002 taps / 1692s、`levels:check` 全闸绿、游端 `validateBeadsLevel` 0 错、盘面恰在 `GRID_MAX` 32 上限；同盘改以 `single`/`plate` 身份入普通关档即被门禁⑦ 拒 ⇒ 由推论变实测。两个新坑：结果自带 `thumb` 是 JPEG 而接口只收 PNG（须转码）；新建章默认 `open:false`，不开放玩家看不到。真机/浏览器通关与包体重建复测仍未做。【六版补：两点已补做】浏览器真页面 `goToLevel(9)` ⇒ 32×32/1024 格/playing/0 error（5 帧 47338 draw calls ≈ 9.5k/帧，格数 6.6× 而 draw 9.6× ⇒ 超线性，低端机另测）；`build:cocos` 重跑 ⇒ 3224.9 → 3312.7 KB / 111 件（仍达标，余量 783 KB）；章已开放常驻（`ARC_OPEN_MAX 1 → 2`）。⚠ 过程中拓出一件比判据更要命的事：**新章封面图其实不在真机包里**（studio 只写 design 目录、无腿搬进 `cocos/assets/themes/` bundle），而 harness 的 dev 路由会让它在浏览器里 200 可见 ⇒ 详见 **K-108 ⑥**。复测已登记进 `levels-spec §3.1①`，取值待裁定（脚本 `temp/wxg-t-341-reg60-measure.mjs`）；④ 仍然有效的两条实测经验：四格珠数各差 ≥20 才躲得过门禁⑥（难度分不许并列）；小图拼进 32 格画布时空白留 `.`、⛔ 重复边缘像素（否则珠数被拉到上限）。
  关联：K-036（门禁的 ✅ 要靠清单自证）、K-135（复用旧尺子先对量纲）、K-140（逐对象读数按对象名锚定）。

- **[判据实测][K-150] 带快照回滚的写事务，「本次改动叫什么名字」这类诊断信息必须赶在回滚之前采集——回滚一跑，落盘痕迹就不存在了**（来源 WXG-T-341 / commit ce2eec9，2026-10-21）
  现象：beads-studio 的大关管理写端点失败时，只把生成期断言的红字原样转回页面，而红字里的 `L5` 是按装配顺序重编号后的关号。用户在管理页上既找不到「L5」是哪张图，也不知道四格里究竟哪一格被拦，只能一张张重猜。
  根因：事务顺序固定是「快照 → 写盘 → 重编号 → 跑门禁 → 失败就恢复快照」。**重编号后的关号只在写盘到回滚这几秒内有对应的真实文件**；一旦先执行回滚，关卡文件恢复原状，「L5 = 某张大图的左上那一格（它的落盘名里带着来源图的 id 尾号）」这条线索永久消失，响应里只剩一个对不上任何图的空数字。
  规避/做法：① 失败分支里先用回滚前的关卡文件建好「关号 → 落盘名」映射，再回滚，最后组装响应（`apps/beads-studio/server.mjs` 的 `applyManage` + `gateNameOf`）；② 转译只覆盖**已经用真实数据撞过**的判据（步数越界、难度并列两类），其余照抄原文——把没验证过的红字润色成通顺中文，等于让报错替门禁说话，与 K-036 反对的是同一件事：门禁的可信度不能被加工；③ 人话放 `error`、门禁原文整段另放 `detail`，前端两段都显示（`httpErr()`），使用者既能照着改图，也留了回查判据正本的路。
  关联：K-036（失败即短路的门禁，其 ✅ 不构成证据）、K-119（工具尾部那句通用报错会掩盖真因）。

- **[判据实测][K-156] 度量「已有构建产物」的读数（包体、快照、生成物校验）必须先核对产物时间戳，否则读到的是上一批的数**（来源 WXG-T-345，2026-10-22）
  现象：本批收尾跑包体检查读到 3319.0 KB 并准备入账；核对时间戳发现构建产物 12:16、本批源码 12:34 ⇒ 该读数是上一批产物。按本批源码重建后的真实读数是 3318.7 KB。若直接入账，台账会记下一个从未存在过的数值。
  根因：这类检查只做「读文件 + 求和」，既不触发重建、也不校验 mtime；门禁绿只说明「产物本身合法」，不说明「产物由本版源码生成」。它与 K-111（用 `--debug` 产物当基线）是同一类错的另一个维度：一个错在构建档位，一个错在构建时间。
  规避/做法：① 任何读产物的度量，先断言产物 mtime ≥ 源码 mtime（或同批显式重建再测）；② 入账时写清口径是「本版重建后」还是「既有产物」，两者不可混用；③ 发现旧产物读数时把作废理由一并留痕（写进任务详情），⛔ 静默替换数字——否则下次没人知道那个数为什么变；④ 快照 / 生成物 / 哈希类校验同理：先证明「被检对象是本版生成物」，再谈它合不合格。
  关联：K-111（构建档位错 ⇒ 读数不可作基准）、K-152（假绿与假红的定性）、K-036（门禁跑过 ≠ 检了）。

- **[判据实测][K-161] 「文档值 ≠ 代码值」只是不等，不自动等于「文档落后」；判漂移方向前必须先列该标识的消费点并按被检域检索**（来源 WXG-T-350 体检 / 用户纠正，2026-10-22）
  现象：数值体检把设计真源表声明的 9 与代码常量的 10 判成「文档落后一关」，并建议把真源行补成 10。用户指出真口径：demo 章仍是 9 关，新增那一关属**第二大关的一小关**。照原建议施工会把「demo 关卡数」永久钉成全表长（此后每入一个新高关都得动真源表），还可能诱导后人把存档数组长度与测试上界往 9 收——那正是 K-151 记过的清档事故形状。
  根因：① 只比**值**不比**语义**：同一个标识在大关制落地后承载两个口径——文档侧按**章**读（第一大关关数），代码侧按**全表**读（存档星数组长度、进度上界钳制、关卡数组长度断言、生成期门禁校「声明值 == 关表条目数」）；单大关时代两值恒等 ⇒ 分叉从不暴露，多大关第一单才分开。② 开工前的知识库检索只按**本批动作**关键词（体检、漂移、工具坑）查，没按**被检对象所在域**查，而同域条目（K-151 明写「关表长度即该常量」、K-152 记「全池 = 第一章」这类旧口径要改成按章取数）与当事批次的当场登记（关卡规格 v1.21 写着「第二章投放、第一章零变更／⛔ 零真源冻结值」）三条全在指向正解。
  规避/做法：① 判「谁落后」前先列该标识的**全部消费点**（`rg 'NAME' games/<game>/{src,tests,cocos} tools/scripts`），看它被拿去当什么：数组长度、上界钳制、生成期断言还是门票分母；若消费点全属「总长」，文档那个值大概率是**另一个口径**而非漏同步。② 查有没有**明文禁用**：新制若写着「⛔ 该用途不得取此常量」，说明语义已被摘出，文档行要换的是帽子（语义表述），不是数字。③ 检索词必须含被检对象的域（常量名、系统名、它服务的机制），⛔ 只按本批动作词检索。④ Drift 表分三态落笔：**文档落后 / 语义分叉 / 代码违反文档**——只有第三态才建议改代码，第二态建议拆口径（改名或拆常量），第一态才补文档数值；把「语义分叉」误写成「文档落后」，后续建议的方向会整体反掉。⑤ 订正「语义分叉」类漂移时数值可以不动，但必须同批钉住**分叉时点与恒等期**（「自 X 起两个读数不再恒等；此前只有一个大关、两值恒等故未区分」），并**就地**给历史段的旧措辞加括注——历史段是二次误读的钩子（本条同批实测：只改行首声明不够，v1.46 那句「随表走 = 当前关数」仍会把人带走）。⑥ 同型失效还有**测试侧**的一头：仓库里早就有「否则档位塌缩」的断言 `expect(LEVEL_TIME_MIN).toBeLessThanOrEqual(59)`，但 `59` 是八关时代的最短 3★ 档快照 ⇒ 关表涨到 10 关、3★ 线已降到 30 时，三关真在塌缩而该断言照样绿。防漂移判据要写成**对被检集合逐条成立的性质**（「每张关表关：3★线 < 2★线 < 1★线」），而不是「某个常量 vs 一个当时的极值」；后者是 K-152「本版快照当不变式」的测试侧变体，且比文档漂移更危险——它给人「已经守住了」的错觉。
  关联：K-151（扩池 = 破坏性存档变更，同一常量的代码侧语义）、K-152（本版快照当不变式 ⇒ 批量假红）、K-156（读数先核对产物）、K-036/K-037（跑过 ≠ 检到）、K-106（写了 ≠ 写对了）。

- **[判据实测][K-165] 改判一条冻结规则前，先取证它到底有没有落码：从未实现的纸面规则改了是零返工，已落码的改了成本全在迁移与回归**（来源 WXG-T-359 / commit 3a07b4e，2026-10-23）
  现象：用户令「换皮肤也用豆子吧，星等级只与开启关卡有关」，正把 §3.7 那条**已冻结**的「累计★ 解锁主题」换掉。按常规这会牵动皮肤注册表、存档结构、设置页、单测与时间档回归；实测三处代码事实 = ① 皮肤注册表 `games/beads/src/config/skins/registry.ts` 的 `BeadsSkin` 只有 `id / label / tokens`（无价格、无锁定、无拥有态，切换不扣任何东西），② 设置页 `game/beads-game/game-settings.ts` 的 `cycle-skin` 免费遍历整张注册表，③ 门票判定 `systems/arc-ticket.ts` 读逐关历史最高星**求和**、既不读也不扣 `starsTotal`，全仓 `grep addCoins|spend|-= *stars` 零命中 ⇒ 该规则自 v1.23 立项起**从未落码** ⇒ 本批改判 = 纯文档交付，零代码返工（beads 单测 137 例原样绿、时间档常量与断言逐字未动）。
  根因：冻结表里的行有三种真实状态 —— 已实现且被消费 / 已实现但只当显示值 / 从未实现只活在文档；三态的改判代价差一个量级，而**表格文本本身不携带这个信息**。只看文档会把它估成「要落字段 + 迁移 + 回归」的重批（本批开工前的推演值确曾如此，低估的那一半是白干、高估的那一半会误导排期），也会漏掉「零返工」这个真结论。
  规避/做法：① 改判前三查并写进交付：**结构体的字段清单**（看有没有价格/锁定/拥有态）、**该货币的全部消费点**（扣减、`if (余额 >= 价)`、存档落盘处）、**该判据的读法**（读派生总量还是读逐槽历史）；② 结论按「代码侧返工面 = 0 / > 0」显式落到变更单与提案页头，⛔ 让读者自己推；③ 判为「零返工」时必须同批登记**落码前置**（本例 = 皮肤价格字段 + 存档拥有态 + 存档版本号变更单 + 老玩家 grandfather 迁移 + 购买确认 UI），否则下批落码会把这四项当新发现再估一遍；④ 成本跃迁点是**「派生量 → 落档事实」**：解锁条件若由状态算出来则零存档字段，一旦改成购买/消耗就必须持久化 ⇒ 裁定把「达成」换成「花掉」，存档迁移与降级回归就不可省（K-151 的清档事故正是这条的极端形状）。
  关联：K-161（同为「文档值 ≠ 代码值」，先列消费点再判方向）、K-155（决策条文与施工清单不同页 ⇒ 落码批须逐字段对账）、K-151（存档破坏性变更与降级矩阵）。
